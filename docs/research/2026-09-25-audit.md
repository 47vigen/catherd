# catherd production-readiness audit

Date: 2026-09-25. Commit audited: `c0479cb` (package 0.2.1). Scope: `src/core`, `src/mcp`, `src/routing`, `src/profile`, `plugin/`, CI/release. I skipped TUI UX, but I cover TUI code that writes shared state (`src/tui/profiles.ts`, `watch.tsx` polling).

## 0. Baseline checks (Bun 1.3.11 in this container; the project requires 1.4 or newer)

Experiments I ran with the repo's own fake CLIs (scripts in `scratchpad/exp/`):
1. **Two parallel `dispatch` calls on overlapping lanes both start.** Two parallel calls with the same `name` also both start, and both write the same `roles/w3.*` files, which leaves 2 records for `w3`.
2. **Two concurrent `reconcileLive` callers write duplicate RunRecords** in 10 of 10 trials.
3. **A limit failover of a fix-round dispatch (`thread` set) fails with a raw `ENOENT … roles/w1.md`.**
4. **One corrupt `meta.json` anywhere under the data dir stops `catherd mcp` from starting.** A truncated `runs.jsonl` line makes `status`, `route` and `dispatch` throw `JSON Parse error` for that run.

6. Startup cost: `bun src/cli.ts --version` takes about 450–570 ms. Importing `src/mcp/server.ts` alone takes about 160 ms and the TUI import takes about 380 ms. `loadCatalog()` takes 18–41 ms on every call, because it re-parses and re-validates the 1.4 MB models.dev snapshot.

## 2. Correctness and concurrency

**C1. HIGH: `dispatch` admission is not atomic (overlap and same-name checks are TOCTOU).** `dispatch.ts:68-77` reads the live markers, then `await refreshState(...)` (`:81`) yields. The marker is written only later, in `onSpawn` (`codex.ts:141-156`). The SDK starts handlers for requests from one stdin chunk as separate microtasks. So parallel `dispatch` calls, which is exactly how the skill fans out lanes, all pass the check before any marker exists. I reproduced it: overlapping lanes both ran, and two same-name dispatches both ran on the same `roles/<name>.{md,out,jsonl,err}`. *Fix:* keep a per-run in-process reservation map, and set the reservation synchronously before the first `await`. Across processes, take an `O_EXCL` reservation file (`roles/<name>.live.json` created with `wx` *before* spawn, then filled in with the pid). Release it in `finally`.

**C2. HIGH: duplicate RunRecords from concurrent reconcilers.** `reconcileLive` writes: it appends the record and clears the marker. It runs from `status`/`summarizeRun` (`status.ts:80`), from every `dispatch` (`dispatch.ts:50`), at server start (`server.ts:24`), and from the separate `catherd watch` process on every poll (`tui/watch.tsx:51`). The dispatching server's own finalize (`codex.ts:165`) hashes the owned files, and for opencode it spawns `opencode api`. That leaves a window where another process (watch, or a second Claude session's server) sees "marker present, pid dead" and finalizes the same run too. I reproduced it in 10/10 trials. Double records inflate the budget and `runs_summary`. *Fix:* a read path must never finalize. Claim a marker by `rename(live.json → live.json.finalizing.<pid>)`, which is atomic, and only the winner appends. Give each run a unique `runId` and have readers dedupe by it.

**C3. HIGH: pid reuse makes a stale marker "live" forever.** `reconcile.ts:6-13` treats `kill(pid,0)` success, **or EPERM**, as alive. After a reboot or a long pause, a reused pid (EPERM makes this likely: any root daemon counts) pins the role as running. The results: `dispatch` refuses that name (`dispatch.ts:69`), refuses overlapping lanes, `state.md` says "wait for X", and `watch` shows it live, all indefinitely. *Fix:* store the process start time in the marker (Linux `/proc/<pid>/stat` field 22 plus `/proc/sys/kernel/random/boot_id`; macOS `ps -o lstart= -p`) and compare it. Better still, launch the CLI through a tiny wrapper that writes `roles/<name>.exit` with the exit code, so completion is a file, not a pid probe. That also recovers the real exit code after a restart, which is `null` today (`reconcile.ts:23`).

**C4. HIGH: limit failover on a fix round crashes.** `dispatch.ts:139` calls `runOne(failoverTo, undefined, …)`. With no thread, the runners read `p.brief` (`codex.ts:138`, `opencode.ts:147`), not the `.fix.md` this call wrote. If the role was never dispatched fresh, the result is `ENOENT` (reproduced). If it was, the stand-in silently re-runs the **original** brief instead of the fix. *Fix:* pass the brief path explicitly in `DispatchOpts` and never infer it from `thread`.

**C5. MEDIUM: no cancel, no Codex timeout, SIGTERM-only kill.** Codex runs have no idle or overall timeout: `idleSecs` is used only by opencode (`opencode.ts:151`). A hung `codex exec` blocks `dispatch` forever, and progress ticks keep the MCP call alive. `extra.signal` (MCP cancellation) is ignored. There is no `cancel(run, name)` tool, and `killGroup` (`spawn.ts:34-44`) sends SIGTERM with no SIGKILL escalation. Orphans (by design, children outlive the server) have no GC path. *Fix:* add a `cancel` tool plus `catherd runs kill`, and give both runners an idle and max-wall timeout. Escalate TERM, then KILL after 10 s. Kill the group when `extra.signal` aborts only if the user asked for that; the default should stay "survive".

**C6. MEDIUM: whole-file re-read on every poll (O(n²)) and lost partial lines.** `spawn.ts:70-76` calls `readLines` on the entire stdout file every 1 s (Codex) or 250 ms (opencode). Codex `--json` streams grow to many MB on long runs, and 14 parallel lanes multiply that. A trailing partial line is counted as "seen" (`:72-74`), so it is never re-parsed once complete. *Fix:* tail the file from a byte offset and hold back the unterminated remainder.

**C7. MEDIUM: synchronous blocking calls in the MCP event loop, with no timeouts.** The blocking calls are:
- `Bun.spawnSync` for `opencode api` (`opencode.ts:52`), run every second from the watchdog while a session is quiet but busy;
- `git status --untracked-files=all` on every state refresh (`mcp/runs.ts:70,97`);
- `git rev-parse` and `git cat-file`;
- `codex --version` / `opencode --version` in `catalog_query` (`setup-tools.ts:47`);
- SHA-1 hashing of every owned file, including whole directories, at dispatch start and at finalize (`reply.ts:21-42`).

None has a `timeout`, and each one stalls every other in-flight dispatch's polling, progress notifications and tool calls. *Fix:* use async `Bun.spawn` with `timeout`/`killSignal`, and hash asynchronously or with an mtime+size pre-check.

**C8. MEDIUM: a failed progress notification crashes the server.** `dispatch.ts:112` does `void extra.sendNotification(...)`. If the client has gone (session closed or transport closed), the promise rejects, and Bun exits on an unhandled rejection (checked: exit 1). *Fix:* add `.catch(() => {})` and stop ticking once the transport closes.

**C9. MEDIUM: file writes are not atomic.** Profile, `config.json` and `projects.json` (`profile.ts:77-80`), the catalog override (`catalog.ts:171`), `credentials.json` (`jev.ts:110`), agent files, `meta.json`, `state.md`/`state.json` (`runstore.ts:126`, `mcp/runs.ts:84`) and live markers (`runstore.ts:150`) all use a plain `writeFileSync`. Only the models.dev snapshot uses tmp+rename (`catalog.ts:224`). A crash or ENOSPC mid-write truncates the profile, and then every `route`/`dispatch` fails. *Fix:* one `writeFileAtomic` helper (tmp in the same dir, fsync, rename) used everywhere.

**C10. MEDIUM: readers are not crash-tolerant, and one bad file bricks the server.** `listRuns` (`runstore.ts:62`) JSON-parses every `meta.json` with no try/catch, so one corrupt file makes `findRun` fail for *every* run, and `startMcpServer` crashes at boot (reproduced). `readJsonl` (`runstore.ts:96-102`) throws on a truncated last line. `readLive` (`:157-163`) throws on a half-written marker. *Fix:* skip and warn on bad lines and dirs, ignore an unterminated last jsonl line, and quarantine unreadable runs.

**C11. MEDIUM: lost updates between the TUI, the MCP server and a second MCP server.** Profile saves (TUI editor vs `profile_set`), `setActiveProfile`'s read-modify-write of `config.json`/`projects.json`, `saveTreatLike`'s read-modify-write of the override, and `state.json` notes (`mcp/runs.ts:81-84`) have no cross-process lock and no compare-and-swap. `appendFileSync` for jsonl is fine on local POSIX filesystems. *Fix:* an advisory lock (reuse the `wx` primitive, done correctly) around config writes, plus an mtime/hash check that reports "profile changed since you loaded it".

**C12. HIGH: profile switch does not relink the Claude agents, and repo-bound profiles are never linked.** `tui/profiles.ts:35-37` saves agents *before* `setActiveProfile`, so in `agents.ts:69` `active` is false. The new profile's agents are written but not linked, and the old links stay (reproduced). Separately, `writeClaudeAgents` checks only the *global* active profile (`agents.ts:69`). A repo bound in `projects.json` to a profile with different Claude rungs gets `route` answers naming agents that do not exist in `~/.claude/agents`. *Fix:* link the union of agent files for every profile that is active or bound, and relink after any activation change.

**C13. LOW–MEDIUM: records point at rotated files.** `RunRecord.replyPath` is always `roles/<name>.out` (`codex.ts:120`), and `rotateRound` moves it to `.r<k>.out` on the next round (`runstore.ts:81-90`). So every record but the last one references the wrong file. Briefs are not rotated at all, so the earlier `roles/<name>.md` is overwritten (`dispatch.ts:80`). A role named `w1.r1` or `w1.fix` collides with `w1`'s rotated or fix files, because `ID` allows dots (`lanes.ts:7`). *Fix:* use per-attempt directories, `roles/<name>/<attempt>/{brief.md,out,jsonl,err,exit}`, with `attempt` stored in the record.

**C14. LOW:** a thrown dispatch (PATH missing, ENOENT) leaves `state.md` showing a "starting" role until the next refresh (`dispatch.ts:81`). `refreshState` parses porcelain with `l.slice(3)`, which breaks on renames and quoted paths (`mcp/runs.ts:101`). `climb` has no guard against concurrent calls on one lane (`lane-tools.ts:109-119`). `runChild` leaks 3 fds if `Bun.spawn` throws (`spawn.ts:55-66`).

## 3. Error handling and observability

- **E1. MEDIUM: no error taxonomy.** Every failure is `new Error("catherd: …")` or a raw Node error (`ENOENT`, `JSON Parse error`) that the SDK passes through as `isError` text. The orchestrator skill can only string-match. *Fix:* a `CatherdError {code, message, hint, retryable}` with codes such as `BUDGET_EXHAUSTED`, `LANE_BUSY`, `NOT_ON_PATH`, `CORRUPT_STATE` and `JEV_UNAVAILABLE`, returned as `structuredContent`.
- **E2. MEDIUM: no diagnostic log.** The server writes nothing to stderr or to a file. There is no `CATHERD_DEBUG`, no log of tool calls, spawn argv, exit codes or timings, and no server-crash trace. Per-role `.err`/`.jsonl` files are kept, which is good. Jev failures collapse to `"network error"` or `"unexpected response"` (`jev.ts:138,141`), losing the cause. *Fix:* write a rotating `<data>/logs/mcp-YYYYMMDD.jsonl` with the tool name, args hash, duration and error code. Log spawn argv (never env), exit code and signal. Keep the Jev error body, truncated.
- **E3. MEDIUM: a RunRecord cannot explain its own failure.** It lacks the exit code and signal, the CLI version, the catherd version, the profile name, the argv, and HEAD before and after. A reconciled run gets `code: null` and a `secs` that includes the downtime (`codex.ts:109`).
- **E4. MEDIUM: no `doctor` command** (it is only in `docs/ideas.md`). The backlog already names the real outage causes: CLI drift, codex config parse errors, bunx not on the GUI PATH. *Fix:* `catherd doctor [--json]`. It should check the Bun version (≥1.4), bunx on PATH as Claude Desktop sees it, codex and opencode versions and logins, the Jev key with a live ping, the plugin version against the package version, agent symlinks (dangling or not linked for the active and bound profiles), data dir health (corrupt runs, stale markers, orphaned pids, lost lock slots), and whether the MCP server starts. Expose the same checks as an MCP `doctor` tool.
- **E5. LOW:** `status` shows no stale markers, orphaned processes or corrupt files. The `hints` array is good; extend it with the error codes.

## 4. Security

- **S1. HIGH: preflight runs model-authored shell with no sandbox or confirmation.** `preflight.ts:21` runs `sh -c <Fast check line>` in the user's repo with the MCP server's full privileges. The line comes from a lane file that a model wrote through `write_run_file`. A prompt injection in repo content (dossier, then architect, then lane) turns into arbitrary code execution. That breaks the design's intent that the architect is read-only (spec §4). *Fix:* run checks under the same sandbox a worker gets (`codex sandbox`, `bwrap`/`landlock` on Linux, `sandbox-exec` on macOS) with a timeout. Or require the orchestrator to show the commands to the user once per run. Or both.
- **S2. MEDIUM: argument injection through `thread`.** `thread` is `z.string().optional()` with no validation (`dispatch.ts:43`), and it goes to codex as a bare positional (`codex.ts:67`). `thread: "--dangerously-bypass-approvals-and-sandbox"` would turn a read-only reviewer into a no-sandbox run. The opencode message is also a bare positional (`opencode.ts:45`), so a brief starting with `-`/`---` is parsed as flags, and a brief over 128 KiB fails with `E2BIG` (Linux `MAX_ARG_STRLEN`). *Fix:* validate `thread` against a strict id regex, put `--` before positionals, and pass the opencode brief by file or stdin.
- **S3. MEDIUM: `rung` is not validated against the profile.** `dispatch.ts:42` accepts any `model#effort`, and `backendOf` falls back to guessing codex (`mcp/runs.ts:117`). The orchestrator can therefore run any model at any effort, which bypasses the profile's cost controls, and a typo fails only after spawn. *Fix:* require the rung to be an enabled, scored entry for that role (or a configured failover target).
- **S4. MEDIUM: the Jev key and other secrets reach the workers.** The runners pass the full `process.env` (`codex.ts:137`, `opencode.ts:176`, `mcp/runs.ts` git calls). `TYPESAFE_API_KEY` goes into every Codex and opencode child and every tool they run, although spec §6.1 says it never leaves catherd. *Fix:* strip `TYPESAFE_API_KEY`, and add an env denylist/allowlist option in the profile.
- **S5. MEDIUM: sandbox choices.**
  - `verifier` and `ui-reviewer` run with `danger-full-access` (`types.ts:31,34`): full filesystem and network, with a model-written brief. Prefer `workspace-write` with `sandbox_workspace_write.network_access=true`, plus writable roots for the browser profile and screenshots.
  - The opencode mapping is not a sandbox. `workspace-write` passes no flags (opencode's default permissions apply, with no filesystem confinement), and `danger-full-access` passes `--auto`, which approves everything (`opencode.ts:28-33`).
  - Document that "sandbox" means the actual Codex sandbox only.
- **S6. MEDIUM: third-party data egress.** `route` sends the whole lane file (plan text, file paths, possibly code) to `api.typesafe.ai` (`route.ts:70`). `ask` sends free-form state. An enterprise deployment needs this documented, an opt-out or offline mode, and redaction (strip code blocks, cap the length).
- **S7. LOW–MEDIUM: path handling.**
  - `write_run_file`'s server-owned check is case-sensitive (`mcp/runs.ts:42`), so on the default case-insensitive macOS APFS, `RUNS.JSONL` or `Roles/w1.md` get past it and overwrite server state. Compare case-folded paths.
  - `Owns:` paths are not confined to the repo (`reply.ts:33`): `../../x`, `/`, or a symlink to `/dev/zero` get hashed or read by the server.
  - `read_knowledge(repo)` uses the raw `repo`. `repo=".."` maps to `join(dataDir, "..")`, and a non-toplevel path silently finds nothing (`lane-tools.ts:31,194`). Resolve it with `git rev-parse --show-toplevel`.
  - `repoSlug` collides (`/a/b-c` and `/a-b/c` both map to `a-b-c`, `paths.ts:14-16`), so knowledge and runs mix across repos. Use `<basename>-<sha1(path)[:8]>`.
- **S8. LOW:** `saveJevKey` writes and then chmods (`jev.ts:110-114`), which leaves a short 0644 window when the file already exists. Write to a 0600 tmp file and rename. `jevKey` never checks the file's mode or owner.
- The `~/.claude/agents` handling is sound. `isOurs` refuses to clobber non-catherd files, and pruning touches only links into catherd's own dir. The one edge: if `configDir` moves (an XDG change), old links become "not ours", and every save throws (`agents.ts:72-81`).
- MCP input validation is decent: ids are regex-checked, `runFile` is realpath-confined, and `commit` is hex-checked. The gaps are `thread`, `rung`, `repo` (`read_knowledge`, `runs_summary`) and unbounded `ask.state` and `brief` sizes.

## 5. Data model and compatibility

- **D1. HIGH: no schema version anywhere.** That covers the profile, `config.json`, `projects.json`, the catalog override, `meta.json`, RunRecord (`types.ts:145`), the live marker, routes, jev, harness and `state.json`. There is no migration path.
- **D2. HIGH: profile forward/backward compatibility is broken by construction.**
  - `roles: z.record(z.enum(ROLES), …)` (`profile.ts:31`) is **exhaustive** in zod 4 (checked). Adding a role, such as the planned new ones, makes every existing profile fail to load. Loading a newer profile with an unknown role in an older catherd also fails.
  - `z.object` strips unknown keys (checked), so an older catherd that loads and saves a newer profile silently deletes the new fields (for example `failover` and `budget` written by the TUI).
  - *Fix:* use `schemaVersion` plus `z.partialRecord`/`z.looseObject`, preserve unknown keys on save, and write explicit `migrate(vN→vN+1)` functions.
- **D3. MEDIUM: RunRecords are read with `as` casts and never validated** (`runstore.ts:101,105`). An old record without `tokens` crashes `summarizeRun`. Give each record a unique `runId`/`attempt` (needed for C2 dedupe and C13), plus `schema`, `exitCode`, `signal`, `cliVersion` and `catherdVersion`.
- **D4. MEDIUM: the catalog is re-read on every tool call** (20–40 ms each for the 1.4 MB snapshot). There is no cache and no staleness signal. The "version" is a date string that is never checked against the override. Trim the snapshot (as `ideas.md` already proposes) and memoize by mtime.
- **D5. LOW:**
  - `projects.json` is keyed by `resolve(repo)` (`profile.ts:132`), not by git toplevel or realpath, so binding a subdirectory or a symlinked path silently misses.
  - The ledger is a markdown table that is also parsed as data. Keep `ledger.jsonl` as the source and render the table from it.
  - The config layout (XDG plus `CATHERD_HOME`) is fine. Document `CATHERD_HOME`, `CATHERD_LOCK_SLOTS`, `CATHERD_TICK_MS` and `CATHERD_CLAUDE_AGENTS_DIR`.

## 6. Architecture

- **A1. MEDIUM: there is no backend abstraction.** Backends are hard-coded as unions and ternaries in about 12 places:
  - `types.ts:13,148`, `Profile.harness` keys;
  - `runstore.ts:136`, `reconcile.ts:23`, `dispatch.ts:97,122`, `mcp/runs.ts:117` (unknown model means codex);
  - `harness.ts:59`, `setup-tools.ts:44-49`, `tui/backends.ts:15-33`;
  - the catalog schema enum, and `NOT_REPOS`.

  `codex.ts` and `opencode.ts` duplicate the run/finalize skeleton, and `opencode.ts` imports `DispatchOpts` from `codex.ts`. Adding cursor or grok today means touching all of these. *Fix:* a `BackendAdapter` registry with `id`, `argv(opts)`, `env(isolated)`, `parseEvents(lines) → {thread, tokens, cost, status, lastEvent}`, `finalize`, `interrupt`, `probe()` (version, login, fix command), `sandboxMap` and `isolation`. The dispatch, reconcile and doctor code should iterate the registry.
- **A2. MEDIUM: business logic lives in MCP handlers.**
  - `dispatch.ts:48-152` holds admission, budget, the overlap check, state writes, failover and hints.
  - `lane-tools.ts` holds the knowledge file and ledger formatting.
  - Nothing is reusable from the CLI: there is no `catherd dispatch` and no `catherd wait`, which is the S1 fallback in spec §7.
  - Testing goes through the in-memory MCP client only.

  *Fix:* extract a `RunService` (`start`, `dispatch`, `cancel`, `climb`, `land`, `status`) that owns locking and state. MCP tools and CLI commands become thin adapters.
- **A3. LOW: dead code and duplication.**
  - `LOCK_STALE_MS` is used only by a test (`lock.ts:9`), and `ChildResult.signal` is never read.
  - `pidAlive` exists twice (`lock.ts:33`, `reconcile.ts:6`), and so does `backendOf`, with different fallbacks (`profile.ts:162`, `mcp/runs.ts:114`).
  - `slug` is duplicated (`runstore.ts:24`, `agents.ts:10`), as are `ProjectsSchema` (`profile.ts:52`, `tui/profiles.ts:12`), the git helpers (three copies) and the package.json read (`cli.ts:10`, `version.ts:3`).
  - Reads with side effects (`summarizeRun` calls `reconcileLive`) break command/query separation, and that is the root of C2.
- **A4. MEDIUM: startup coupling.** `cli.ts:8` statically imports the TUI (OpenTUI native core plus React), so `catherd mcp` and `catherd lock`, which run once per heavy worker command, pay about 300 ms extra and require the native OpenTUI binary to load. *Fix:* lazy `await import()` per subcommand.
- **A5. LOW: `status` scales poorly.** A no-argument `status` and `watch` call `summarizeRun` per run, and each call runs `harnessCosts(listRuns())` across all runs (`status.ts:110`). That is O(R²) file reads, and `findRun` scans the whole data dir on every tool call. Add an index, or compute harness costs once per call.

## 7. Testing

- The strengths are good unit and contract coverage, recorded fixtures, and fake `codex`/`opencode` binaries.
- **Gaps:**
  - no concurrency tests (parallel dispatch, concurrent reconcile, lock contention across processes);
  - no crash or corruption tests (truncated jsonl or meta, half-written marker, pid reuse);
  - no test of the real stdio server (`startMcpServer` has 0% coverage) and no plugin-level e2e (bunx and `.mcp.json`);
  - no test that fix-round failover works (C4);
  - no test that activation relinks agents (C12);
  - no macOS runs.
- **Flaky patterns:**
  - Tests use wall-clock sleeps to wait for spawn (`mcp-dispatch.test.ts:107`, `codex.test.ts:104`, `mcp-preflight.test.ts:76`, `lock.test.ts:26`, TUI `tick`).
  - Tests mutate global `process.env` (PATH, `FAKE_*`, `TYPESAFE_API_KEY`) in a single process.
  - The theme test depends on the runtime (§0).
  - React `act()` warnings flood the output.

  Replace the sleeps with poll-until helpers, and give each test an env snapshot and restore.
- **Live tests** are gated by `CATHERD_LIVE` (`test/live/*`). They never run in CI, and `ideas.md` notes that opencode, climb, failover and budget have never run live. *Fix:* a nightly or manual `workflow_dispatch` job with secrets that runs the live suite, plus a recorded-fixture refresh job. Before 1.0, add one scripted end-to-end run on a sample repo (spec §14 release gate).
- **CI** (`.github/workflows/ci.yml`): `bun-version: latest` only, so the declared minimum (1.4) is never tested and a new Bun can break main without any code change. It runs on ubuntu only, although macOS is a supported platform. There is no concurrency or cancellation config and no coverage threshold.

## 8. Distribution and ops

- **O1. MEDIUM: bunx cold start.** `bunx catherd-cli@0.2.1 mcp` installs the full dependency tree, including OpenTUI's native packages (27 MB) and `react-devtools-core` (16 MB), on the first session. That is network-dependent and can exceed Claude's MCP startup timeout. Then it pays about 450 ms per start. Every worker `bunx catherd-cli@x lock -- …` pays the same. *Fix:* lazy imports (A4). Move the TUI dependencies to an optional or peer package, or split the package (`catherd-core` for mcp and lock, `catherd` for the TUI). Trim `models-dev.json`.
- **O2. MEDIUM (unverified, likely HIGH): `catherd lock` inside a Codex `workspace-write` sandbox.** The lock dir is `~/.local/share/catherd/locks` (`lock.ts:70`), outside the workspace's writable roots. `bunx` needs network (off by default in workspace-write) or a warm cache. `acquire` sits outside the try block (`lock.ts:100`), so an EACCES crashes the command, and the heavy command never runs. Verify this live. Likely fixes: put the lock dir under `$TMPDIR`, or make it configurable, and have `lock` fall back to running unlocked with a warning when it cannot take a slot.
- **O3. MEDIUM: plugin and package version drift.** The marketplace serves `./plugin` from `main` HEAD (`.claude-plugin/marketplace.json`), while `.mcp.json` pins the npm version. Any skill edit merged between releases ships at once against the old server. In the window between the version PR merging and `changeset publish` finishing, `.mcp.json` names a version that is not on npm yet. The server never reports its version to the skill. *Fix:* publish the marketplace from a release tag or branch, add a `version` field to `status` or a `version` tool and have the skill check it, and add a CI check that the plugin pin equals `package.json` (possibly already covered by `test/plugin.test.ts`).
- **O4. MEDIUM: releases are not gated on CI.** `release.yml` runs no typecheck, lint or test and does not depend on `ci.yml`, so a red `main` can publish. Add the checks, or `workflow_run` on CI success.
- **O5. MEDIUM: Bun requirement.**
  - `engines.bun >=1.4` is not enforced by bunx, and there is no runtime check. Add a startup guard with a clear message.
  - Claude Desktop launched from Finder or the Dock often lacks `~/.bun/bin` on PATH, so `bunx` in `.mcp.json` is not found. Document this and have `doctor` check it.
  - Windows is a non-goal, but it is not guarded (`process.kill(-pid)`, `sh -c`). Exit early with a message on `win32`.
- **O6. LOW: reproducibility.** Dependencies are caret ranges and the lockfile does not ship, so each `bunx` install can resolve different minors of `@modelcontextprotocol/sdk`, zod and the rest. Use exact pins for runtime dependencies, or `bun build` a single bundled JS file for the `mcp`/`lock` entry. That entry needs no native modules, which also fixes O1. TypeScript 7 raises a peer-dependency warning on install.

## 10. Top 15 fixes, in priority order

1. **Atomic dispatch admission.** Add an in-process reservation before the first `await`, plus an `O_EXCL` reservation file across processes (C1).
2. **Make reads pure, and finalize only after an atomic claim of the marker.** Add a record `runId` and dedupe by it (C2).
3. **Make liveness robust to pid reuse,** with an exit-file wrapper and start time or boot id (C3).
4. **Fix fix-round failover:** pass the brief path explicitly (C4).
5. **Crash-tolerant readers:** skip a bad `meta.json` or jsonl line, and never let one run brick server startup (C10).
6. **One `writeFileAtomic` helper plus an advisory config lock,** for profiles, config, override, credentials, state and markers (C9, C11).
7. **Schema versioning and migrations,** with `partialRecord` roles and unknown-key preservation in the profile (D1, D2), before adding roles or backends.
8. **Relink Claude agents on activation, and for repo-bound profiles** (C12).
9. **Harden inputs:** validate `thread` and `rung` against the profile, put `--` before positionals, send the opencode brief by file, and keep `TYPESAFE_API_KEY` out of child env (S2, S3, S4).
10. **Sandbox preflight and give it a timeout** (S1 plus the known issue). Revisit `danger-full-access` for verifier and ui-reviewer (S5).
11. **Add a `cancel` tool, Codex idle and max timeouts, TERM-then-KILL escalation, and `.catch` on progress notifications** (C5, C8).
12. **Fix the lock:** reclaim race, a slot lost to an empty file, signal forwarding, and verify it works from inside a Codex sandbox (known issue plus O2).
13. **A `catherd doctor` command and MCP tool, a debug log, and error codes in results** (E1, E2, E4).
14. **Budget accuracy:** in-flight spend, wall-clock minutes, opencode tokens, Codex cost estimates, Claude runs via a `record_claude_run` tool or the skill, and a budget gate on failover. Also add ledger minutes and `profile_set` failover/budget (known issues).
15. **Distribution:** lazy TUI imports or a split package, a Bun version guard, a release gated on CI, a marketplace served from the release tag, and a CI matrix covering the minimum Bun and macOS (A4, O1, O3–O5).

After these, extract `BackendAdapter` and `RunService` (A1, A2). That work is what makes cursor and grok cheap to add.
