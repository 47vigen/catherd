## 0. TL;DR

1. **The `confidence` field is a normalized max-probability, not a separate calibrated number.** It fits `confidence = (n·p_max − 1)/(n − 1)` to within ±0.01 on all 6 catherd fixtures and on every documented example. TypeSafe's own demo gives this formula for n=3 ([Confidence](https://docs.typesafe.ai/confidence)). Two consequences:
   - The same threshold means different things for questions with different option counts. `0.75` requires p_max ≥ 0.80 for `kind` (5 options), p_max ≥ 0.8125 for `difficulty` (4), and p_max ≥ 0.833 for `finding` (3). `same-defect ≥ 0.70` requires p ≥ 0.85.
   - `difficulty` at confidence 0.4 means p_max ≈ 0.55. That mass may well have been split between `copy` and `build`, and **the default catalog routes those two identically** (same bars). catherd was falling back on a distinction it does not use.
2. **The calibration claims are about `probabilities`, measured across groups of predictions.** TypeSafe publishes no ECE or Brier numbers ([System One](https://docs.typesafe.ai/concepts/system-one), [AI primer](https://docs.typesafe.ai/introduction/machine-learning-primer)). The model is **not deterministic**: in TypeSafe's own test, 90.8% of repeated Choice labels held and 2 of 8 questions flipped ([Self-consistency: choices](https://docs.typesafe.ai/cookbooks/consistency_choice_cookbook)).
3. **`difficulty` is a poorly posed question by TypeSafe's own rules.**
   - It is ordinal, so it should be a **Score**, not a Choice.
   - It bundles several judgments: is there a pattern, is there state or concurrency, is the cause unclear, is it cross-system.
   - Its options are not mutually exclusive: a lane can "follow an existing pattern" *and* "touch state".
   - It needs indirection ("hard *for a coding agent*").
   The docs name all of these as causes of low confidence ([Score](https://docs.typesafe.ai/primitives/score), [Primitives](https://docs.typesafe.ai/primitives), [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)). The 2026-09-24 spike result (numeric tables answered at 0.14–0.52) matches the documented "Math and Numbers" weakness.
4. **There is no official calibration, feedback, fine-tuning or dataset-upload feature.** "Jev is not fine-tuned or LoRA-adapted with customer data… the same weights serve every account" ([Models](https://docs.typesafe.ai/models)). Instead, TypeSafe recommends decomposing into atomic questions and learning the combination in your own code or a classical model ([Composite scoring](https://docs.typesafe.ai/patterns/composite-scoring), [Autoresearch cookbook](https://docs.typesafe.ai/cookbooks/autoresearch_feature_discovery)).
5. **An official TS SDK exists: `@typesafe-ai/sdk` 0.6.0** (MIT, zero dependencies, Node ≥ 20). It has typed answers, an injectable `fetch`, and retries 408/429/5xx while honoring `Retry-After`. It is at 0.x and shipped a breaking change 4 days after its first release. Recommendation: keep catherd's thin client, but adopt the SDK's retry semantics and log `model`, `usage` and the `x-typesafe-request-id` response header.
6. **Access risk:** TypeSafe **paused new signups on 2026-09-22** ([X post](https://x.com/typesafeai/status/2102281508950307159), [flaviocopes](https://flaviocopes.com/jev-api-key/)). catherd's `init` refuses to finish without a live Jev key (spec §6.1), so new users cannot currently finish setup. Jev is also reachable through the Vercel AI Gateway (`https://ai-gateway.vercel.sh/typesafe`) and OpenRouter (`typesafe/jev-1.13`).
7. **Cost is negligible.** At $42 per billion input tokens with free output, a 600-token route call costs about $0.000025, and a whole run is well under $0.001. Asking 6–10 more questions per call is effectively free and barely changes latency (13 questions: 0.27 s batched vs 2.71 s serial, [Parallel questions](https://docs.typesafe.ai/cookbooks/parallel_questions)).

## 1. What Jev is

### 1.1 Model and positioning
- Jev is TypeSafe's first **"System One model"**. It returns typed decisions with probabilities and does not generate text. It was trained with **RLCD** (Reinforcement Learning for Calibrated Decisions), which optimizes probabilities against outcomes rather than human preference. Sources: [Introducing System One Models & Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev), [AI primer](https://docs.typesafe.ai/introduction/machine-learning-primer).
- It is designed for fast "snap judgments a knowledgeable person makes in a second": classification, routing, scoring, verification and guardrails. It is not a coding or chat model ([Jev with coding agents](https://docs.typesafe.ai/introduction/coding-agents)).
- **Versions** ([Models](https://docs.typesafe.ai/models)):
  - The only model is `jev-1.13.0`.
  - Aliases: `jev-latest` → `jev-1.13.0` (the stable release, and the SDK default) and `jev-preview` → `jev-1.13.0` (no preview build exists yet).
  - The response's `model` field reports the versioned ID that answered.
  - TypeSafe's advice: "If you have tuned confidence thresholds against a specific version, pin that version's ID." catherd already pins.
  - A search for jev-1.14 or jev-2 found nothing.
- **Timeline** (third-party): out of stealth and early access on 2026-09-15; open signup with $5 credit on 2026-09-20; signups paused on 2026-09-22; existing accounts keep working. Sources: [explainx](https://explainx.ai/blog/jev-general-availability-no-waitlist-2026), [X post](https://x.com/typesafeai/status/2102281508950307159).
- **Other ways in (third-party):**
  - Vercel AI Gateway, model `typesafe-ai/jev` ([flaviocopes](https://flaviocopes.com/jev-api-key/)).
  - OpenRouter `typesafe/jev-1.13` and `typesafe/jev-latest` ([openrouter.ai/typesafe](https://openrouter.ai/typesafe)).
  - Integrations exist for LiteLLM ([litellm](https://docs.litellm.ai/docs/pass_through/typesafe)) and Pydantic AI ([pydantic](https://pydantic.dev/docs/ai/models/typesafe/)).
  - LangChain ships an experimental `ModelRouterMiddleware` that asks Jev to "Choose the least costly model that can complete the task" across `fast` and `powerful` models ([LangChain blog, 2026-09-17](https://www.langchain.com/blog/building-a-harness-with-jev)). This is direct prior art for catherd.

### 1.2 API contract (source: [API reference](https://docs.typesafe.ai/api))

```
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer <API_KEY>
Content-Type: application/json
```

**Request body**

| field | type | notes |
|---|---|---|
| `model` | string, required | `jev-1.13.0`, `jev-latest` or `jev-preview` |
| `state` | string \| object \| array, required | Text only. An object with named fields is recommended ([State](https://docs.typesafe.ai/concepts/state)). The SDK also allows `null`. |
| `questions` | map<id, Question>, required | **The id is not sent to the model.** Put the full meaning in `instructions`. |

**Question types.** There are exactly three. There is no `number`, `boolean`, `multi-select` or `ranking` type.

| type | `criteria` | limits | answer |
|---|---|---|---|
| `choice` | map option → description (string \| object \| array \| null). **Option names and descriptions are both sent to the model.** | ≤ 255 options | `{type, choice, probabilities{option→p, sums to 1}, confidence}` |
| `score` | *ordered array* of level descriptions, low → high | 2–10 levels | `{type, score (probability-weighted mean level index, may be fractional), legend{"0"→desc…}, probabilities{"0"→p…}, confidence}` |
| `noul` | optional `{true: …, false: …}` | — | `{type, noul: P(yes)}`. **No `confidence` field.** |

- A **boolean** is a Noul.
- **Multi-select** is one Noul per label. TypeSafe explicitly says a Choice is *relative* and a set of per-option Nouls is *absolute* ([jaggedness §8](https://docs.typesafe.ai/model-jaggedness/jev-1.13)).
- **Ranking** is a per-item Noul or Score, sorted in code ([Re-ranking cookbook](https://docs.typesafe.ai/cookbooks/rerank_typesafe)).
- **Numbers** should be computed in code.
- `instructions` and every criterion can be a structured object, for example `{what, not_for, examples}`. Questions can reference state paths in backticks, such as `` `lane.body` `` ([Advanced: structure](https://docs.typesafe.ai/primitives/advanced), [Choice](https://docs.typesafe.ai/primitives/choice)).

**Response body:** `{ model: "jev-1.13.0", answers: {id → Answer}, usage: {input_tokens, output_tokens} }`. The catherd fixtures match this shape, including the per-answer `type`.

**What the answer does not have:**
- No `abstain`, `explanation` or `rationale` field. "System One models do not … generate explanations of their reasoning" ([System One](https://docs.typesafe.ai/concepts/system-one)).
- Abstaining is done in code: threshold on the probabilities, or add an explicit `other` / "none of the above" / `unclear` option ([Choice](https://docs.typesafe.ai/primitives/choice)).

**Batching:**
- Many questions go in one request. They are evaluated in parallel and independently: one answer is never context for another.
- Adding questions "barely changes the response time" and costs only the question tokens ([Primitives](https://docs.typesafe.ai/primitives), [Speculative fan-out](https://docs.typesafe.ai/patterns/fan-out)).
- Measured: 13 questions in one call cost $0.000497 and took 0.27 s; 13 separate calls cost $0.006090 and took 2.71 s ([Parallel questions](https://docs.typesafe.ai/cookbooks/parallel_questions)).

**Limits** ([Models](https://docs.typesafe.ai/models)):

| | jev-1.13.0 |
|---|---|
| Price | **$42 per billion input tokens ($0.042 per million). Output is free.** |
| Rate limits | 250,000 tokens/s and 1,200 requests/min. "Adjusting dynamically… can change without notice." |
| Context | 64k tokens per request. **32k tokens for `state` plus the longest single question.** |
| Input | Text only. English is primary; other languages, including CJK, are "handled but not equally well". |

**Latency:**
- TypeSafe claims "70ms–500ms end-to-end" from the US West Coast, most around 100 ms ([blog](https://typesafe.ai/blog/introducing-system-one-models-and-jev), [flaviocopes deep dive](https://flaviocopes.com/jev/)).
- catherd's spec says "about three seconds". That figure probably includes cold connections, a non-US network, or load in the early-access period. **UNVERIFIED**; measure it with the latency field proposed in §5.
- The opencode-jev-router plugin uses a 4 s classification timeout ([repo](https://github.com/robertn702/opencode-jev-router)).

**Errors.** The API doc lists 401 (bad key), 422 (validation, with a body naming the field), 429 (rate limit) and 529 (overloaded). It says to retry 429 and 529 with exponential backoff. The SDKs add 400 `BadRequest`, 403 `PermissionDenied`, 404 `NotFound`, 408 and other 5xx (`InternalServerError`), plus `APIConnectionError` and `APITimeoutError` ([JS API](https://docs.typesafe.ai/sdk/javascript/api), [Python exceptions](https://docs.typesafe.ai/sdk/python/api/exceptions)).
- Error bodies look like catherd's `auth-error.json`: `{"detail":{"error_type":…,"message":…}}`.
- Responses carry an **`x-typesafe-request-id`** header, and the servers can send `Retry-After` / `retry-after-ms` ([JS RetryPolicy](https://docs.typesafe.ai/sdk/javascript/api/interfaces/RetryPolicy)).

**Other endpoint:** `GET /v1/models` lists the aliases available to the account, with description and release date. Versioned IDs are accepted even when they are not listed.

**Versioning and deprecation:**
- Aliases move on release. Pinning a version ID protects tuned thresholds.
- **No deprecation or retirement policy is published.** How long `jev-1.13.0` will stay served is **UNVERIFIED**.
- There is no API changelog page, only SDK changelogs.
- A "migration guide" linked from the official agent skill (`/migrating-to-v1`) returns 404.

**Data handling:** "Jev is not trained on customer requests or responses." Zero data retention is available only for enterprise customers. See the Data Processing Agreement and privacy policy at [Legal](https://docs.typesafe.ai/legal).

**Key storage:** the official SDKs read only `TYPESAFE_API_KEY` (plus `TYPESAFE_BASE_URL`, `TYPESAFE_DEFAULT_MODEL` and `TYPESAFE_LOG_LEVEL`). **`~/.config/typesafe/api_key` is not a documented TypeSafe convention (UNVERIFIED)**. It may come from a third-party CLI such as [jev-cli](https://github.com/jtsang4/jev-cli) or [typesafe-key-cli](https://github.com/mooshee/typesafe-key-cli). The comment in catherd's `jev.ts` calling it "the key file TypeSafe's own tools use" should be softened.

## 2. Confidence, calibration and question-writing

### 2.1 What `confidence` is
- TypeSafe: "`confidence` is a statistic computed from the probability distribution… All of it on one option gives 1.0; the more evenly it spreads, the lower the confidence." Its interactive demo uses `(3 × largest − 1)/2` for three options ([Confidence](https://docs.typesafe.ai/confidence)).
- **Empirical check** of the generalization `(n·p_max − 1)/(n − 1)`:

  | example | n | p_max | predicted | reported |
  |---|---|---|---|---|
  | fixture route-confident difficulty | 4 | 0.96 | 0.947 | 0.95 |
  | fixture route-unsure kind | 5 | 0.79 | 0.738 | 0.73 |
  | fixture route-unsure difficulty | 4 | 0.84 | 0.787 | 0.78 |
  | fixture finding-unsure | 3 | 0.66 | 0.49 | 0.50 |
  | API doc `department` | 3 | 0.88 | 0.82 | 0.81 |
  | Score doc severity | 3 | 0.57 | 0.355 | 0.35 |
  | Score doc severity (combined) | 3 | 0.76 | 0.64 | 0.64 |
  | Quickstart department | 3 | 0.85 | 0.775 | 0.78 |

  The differences are rounding of the displayed probabilities. Treat the formula as **empirically confirmed**, with the doc's word "approximate" as the caveat.
- **Implications:**
  - **Confidence is per question.** Nothing is joint, and the doc says every answer is independent. catherd's `min(kind, difficulty) ≥ 0.75` is a conjunction of two marginals. It is not a calibrated joint probability, and the two answers are not independent evidence either.
  - **The threshold → p_max mapping depends on n:**

    | question | n | catherd threshold | required p_max |
    |---|---|---|---|
    | kind | 5 | 0.75 | 0.80 |
    | difficulty | 4 | 0.75 | 0.8125 |
    | finding | 3 | 0.75 | 0.833 |
    | same-defect | 2 | 0.70 | 0.85 |

    Adding or removing an option silently changes what a threshold means.
  - **Confidence penalizes splits between options that lead to the same action.** For routing, threshold on the **aggregated probability of the action**: P(Track A) = p_copy + p_build. The raw `probabilities` are returned so that you can do exactly this. "You are never locked into our definition" ([Confidence](https://docs.typesafe.ai/confidence)); "Ignore uncertainty on unused branches… low confidence need not invalidate a harmless preference choice" ([official agent skill](https://raw.githubusercontent.com/typesafe-ai/skills/main/skills/typesafe-ai/SKILL.md)).
  - A Noul has no confidence. Its value *is* P(yes). Do not carry a Noul threshold over to a Choice ([jaggedness §8](https://docs.typesafe.ai/model-jaggedness/jev-1.13)).

### 2.2 What "calibrated" promises
- "Outcomes assigned 0.8 should occur about 80% of the time… These rates describe groups of predictions, not a guarantee about any single answer" ([AI primer](https://docs.typesafe.ai/introduction/machine-learning-primer)). "Calibration is measured across groups of predictions" ([System One](https://docs.typesafe.ai/concepts/system-one)).
- Calibration is **against the correct label of the question as written**, on TypeSafe's training distribution. It says nothing about whether a Luna worker will succeed. catherd has to calibrate the mapping from Jev's probabilities to lane outcomes itself (§3).
- **No public calibration metrics** exist: no ECE, Brier or reliability plots. TypeSafe's evals ([evals.typesafe.ai](https://evals.typesafe.ai/)) report accuracy, cost and time against labels from a consensus of large LLMs. They do not measure calibration.
- **Non-determinism** (TypeSafe's own tests with a changing `uid` field in state, n=15 repeats):
  - Choice: 90.8% of plurality labels repeat; the top label flips on 2 of 8 questions; requiring top p ≥ 0.60 raises agreement to 99.2% with 74.2% of answers automated ([Self-consistency: choices](https://docs.typesafe.ai/cookbooks/consistency_choice_cookbook)).
  - Noul: mean per-question SD of 0.0102, though one question spanned 0.43–0.53 across a 0.5 threshold ([Self-consistency: nouls](https://docs.typesafe.ai/cookbooks/consistency_noul_cookbook)).
  - Whether *byte-identical* requests return identical answers is **UNVERIFIED**; the cookbook "cannot separate" the two effects.
  - Recommendations: cache answers per run for reproducibility, and put dead bands around thresholds.

### 2.3 Best practices from the docs
- **One snap judgment per question.** Split multi-factor judgments into atomic questions and combine them in code with weights ([Primitives](https://docs.typesafe.ai/primitives), [How to build](https://docs.typesafe.ai/concepts/how-to-build-with-system-one): "probably the most important concept in this guide").
- **Pick the type by the shape of the answer:**
  - Choice for unordered categories. Add an `other` / "none of the above" option when the list may not cover every input.
  - Score for ordered spectra. "Describe situations, not degrees." Each level is judged on its own: the model does not see level numbers or neighbours, so "worse than the previous level" means nothing. Use as many levels as you can describe distinctly (≤ 10). Keep one dimension per Score ([Score](https://docs.typesafe.ai/primitives/score)).
  - Noul for one yes/no condition. Phrase it so high means yes. Avoid negations. Make the boundary unambiguous; "any" works well ([Noul](https://docs.typesafe.ai/primitives/noul)).
- **Criteria are an extension of the instruction.** Contradictions between the two hurt accuracy.
  - When two options get confused, make each criterion an object with the same field names on every option, such as `what`, `not_for` and `examples` ([Choice](https://docs.typesafe.ai/primitives/choice)).
  - **Examples (few-shot) go inside the criteria.** They help only when they resemble real inputs. An unrelated example left the Safari report at 0.35 confidence, while a matching one raised it to 0.96 ([Score §Structured level descriptions](https://docs.typesafe.ai/primitives/score)).
  - "Higher confidence alone does not show that a description is better." Always validate against labels.
- **State:**
  - Use an object with descriptive field names and reference fields by backticked path.
  - "Include only the context relevant to the current questions… Jev suffers from context rot" ([How to build](https://docs.typesafe.ai/concepts/how-to-build-with-system-one), [jaggedness §5](https://docs.typesafe.ai/model-jaggedness/jev-1.13)).
  - State is untrusted data: adversarial text in it can steer answers (jaggedness §6).
- **Language:** English is best.
- **Thresholds:** "Start with conservative thresholds, test with your own data" and "Test thresholds by plotting confidence against accuracy on your data." Scale thresholds with risk ([Confidence](https://docs.typesafe.ai/confidence), [Confidence-gated routing](https://docs.typesafe.ai/patterns/confidence-routing)).
- **Rollout:** community practice is to run in shadow mode for 1–2 weeks, label the mistakes, adjust the questions, then automate the low-risk paths ([flaviocopes](https://flaviocopes.com/jev/)).

### 2.4 Known weaknesses of jev-1.13 ([Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13), reviewed 2026-09-17)
1. **Literal reading.** It answers the question as written. "When you find yourself explaining what you really meant, that explanation is the missing half of the instruction."
2. **Math, numbers and counting.** It is not a calculator. Numeric representations do worse than semantic ones. Score expectations are weak for numeric interpolation. This is why the spike's numeric score tables came back at low confidence.
3. **Dates.**
4. **Indirection.** Properties of properties and multi-hop questions lose accuracy. "How hard is this *for a coding agent*" is one hop of indirection.
5. **Large state full of irrelevant detail.** Filter the state first.
6. **Adversarial content in state.**
7. **Contradictory instructions and criteria.**
8. **No structural invariants.** A Noul and the equivalent Choice give different numbers, and P(q) + P(not q) ≠ 1.
9. **Text generation.**

### 2.5 Why `difficulty` came back at 0.4
This diagnosis is inferred from the docs. Confirm it with the logged `probabilities`, which `jev.jsonl` already stores.
- **Hidden multi-dimensionality.** Each option's criterion mixes several conditions: `logic` = "state, concurrency, data invariants, edge cases", and `hard` = "unclear cause, cross-system design, or no pattern". A lane that is high on one and low on another cannot be placed. The Score docs say this is exactly what lowers confidence.
- **Options that are not mutually exclusive.** A lane can follow an existing pattern (`build`) and also touch state (`logic`).
- **Ordinal asked as a Choice.** A Score is the documented primitive for a spectrum. A split across neighbouring levels is then a legitimate middle position rather than "uncertain".
- **An irrelevant split is penalized.** `copy` and `build` have identical bars in `catalog/catalog.json` (`repo_code: 55`), so a copy/build split costs nothing in routing but still drops confidence below 0.75.
- **Indirection:** the question asks "for a coding agent".

## 3. Calibration methodology for catherd

### 3.1 What counts as the outcome (label)
- **Primary label per routed lane: `start_ok`.** True if the lane landed on its start rung with no *capability* climb.
  - Capability climbs: `check-failed-twice`, `blocker`, `same-defect`, `refused`, `unchanged`.
  - Classify `blocked` by its evidence. Environment problems (a missing service, a broken tool, a preflight failure) are **not** capability failures. Mark them `env` and exclude them from the label.
- **Secondary label:** `min_ok_rung_index`, the ladder index at which the lane first succeeded. It is **censored** when the lane fails on the top rung or is abandoned.
- **Counterfactual gap (important).** You only observe success at the rung you chose. A lane started on Track B never tells you whether Luna would have succeeded.
  - Remedy 1: **exploration.** For lanes in the uncertain band, start at the cheapest Track A rung with a small probability ε (e.g. 0.1–0.2) and log `explore: true`. The expected cost is one failed cheap attempt.
  - Remedy 2: **post-hoc labels.** A human or the retro labels the lane `difficulty` and the binary features in §3.3. This labels the *questions* directly, which is a different target from worker success.
- Keep the two targets apart:
  - **Question accuracy:** does Jev's answer match a human label? This tunes wording.
  - **Routing utility:** does the decision minimize cost plus time given worker outcomes? This tunes thresholds and weights.

### 3.2 Logging schema (proposed)

**`jev.jsonl`** (per run). Extend the existing row:
```json
{"ts":"…","call":"route","lane":"M1.L2","qset":"route-v2#3f9a1c","model":"jev-1.13.0",
 "request_id":"…","latency_ms":212,"usage":{"input_tokens":742,"output_tokens":160},
 "state_sha256":"…","cached":false,
 "answers":{ "kind":{"type":"choice","choice":"repo_code","probabilities":{…},"confidence":1.0},
             "difficulty":{"type":"score","score":1.2,"probabilities":{"0":…},"confidence":0.4},
             "names_pattern":{"type":"noul","noul":0.93}, "…":{} },
 "derived":{"p_trackA":0.91,"p_trackB":0.09,"kind":"repo_code"},
 "decision":{"track":"A","difficulty":"build","rule":"pA>=0.80 & kind>=0.80","source":"jev","explore":false},
 "used":"worker gpt-6-luna#high","why":"…"}
```
- `qset` is a stable hash of the `QUESTIONS` object and the rule version.
- `model` is the versioned ID copied from the response. Warn if it differs from the pin.
- `request_id` comes from the `x-typesafe-request-id` header.
- `state_sha256` makes it possible to match a lane to the corpus without storing its text in the run log.

**`routes.jsonl`**: add `lane_sha256`, `qset`, `explore`, `p_trackA`, and `climb_class: "capability"|"env"|null` on climb rows.

**New `outcomes.jsonl`** (per run). Append one row when the lane lands, is abandoned, or the run ends:
```json
{"v":1,"at":"…","run":"…","lane":"M1.L2","lane_sha256":"…","qset":"route-v2#3f9a1c",
 "start":{"rung":"gpt-6-luna#high","index":0,"track":"A","source":"jev","explore":false},
 "attempts":[{"rung":"gpt-6-luna#high","secs":412,"tokens":{"in":280000,"out":9000},"end":"climb","reason":"check-failed-twice","class":"capability"},
             {"rung":"gpt-6-sol#medium","secs":655,"tokens":{…},"end":"pass"}],
 "final":{"status":"landed","rung":"gpt-6-sol#medium","index":1},
 "labels":{"start_ok":false,"min_ok_index":1,"censored":false,"env_excluded":false},
 "human":{"difficulty":null,"names_pattern":null,"shared_state":null}}
```

**Local corpus** at `<data>/jev-corpus/<lane_sha256>.md`: a copy of each routed lane file, kept **only on the user's machine**, so the eval harness can replay lanes with new question sets. It never leaves the machine except in the live calls the user runs.

### 3.3 Tuning question wording and options (a), and replacing ordinal difficulty (c)
- **Replace or augment `difficulty` with atomic questions, all in one call.** They cost fractions of a cent and add no latency. Keep the Score version of `difficulty` too during migration, for comparison. Draft set (Nouls unless marked):

| id | question (instructions) | why |
|---|---|---|
| `names_pattern` | "Does `lane` name an existing file, function, endpoint or test in the repository that the new work should copy or follow?" true: "Names a concrete existing example by path or name"; false: "Names no existing example, or only says to follow conventions in general" | The strongest Track A signal. Avoids indirection. |
| `mechanical` | "Is the work in `lane` only mechanical: renaming, moving, deleting or copying code, or changing constants, with no new behaviour?" | Separates `copy` from everything else. |
| `shared_state` | "Does the work in `lane` involve concurrency, caching, shared mutable state, transactions, or the ordering of events?" | Track B trigger. |
| `unclear_cause` | "Does `lane` ask the worker to find the cause of a bug or failure that the lane does not already explain?" | Track B trigger. |
| `open_design` | "Does `lane` leave an interface, data shape or algorithm for the worker to decide?" | Track B trigger. |
| `cross_boundary` | "Must the work in `lane` keep two or more services, processes or data stores consistent, such as a schema migration together with the code that reads it?" | Track B trigger. |
| `outside_repo` | "Does the work in `lane` depend on something outside the repository: a running service, credentials, network access, hardware or CI configuration?" | `terminal`/env risk; also predicts `env` climbs. |
| `difficulty` (Score) | 4 levels written as situations: "Mechanical change: rename, move or copy existing code" → "New code that follows a named existing example" → "New logic with state, concurrency, invariants or tricky edge cases" → "Unclear cause, cross-system design, or no example to follow" | Ordinal done the documented way. The probabilities map directly onto the old `copy`/`build`/`logic`/`hard`. |

- **Compute in code, never ask Jev:**
  - Fast check present: `fastCheckOf()`.
  - Owned-file count: `ownedFilesOf().length`. Jev cannot count.
  - Test files among the owned files.
  - Owned-file extensions (`.tsx`/`.css` suggests `ui`).
  - Lane length.
  These go into the decision rule and the outcome model as features. They can also go into state as named facts (e.g. `"owned_files": [...]`), but stay out of any numeric question.
- **Keep `kind`**. It came back at 1.0. Consider adding `other: "None of the above"` so a lane outside the five kinds is not forced into one.
- **Wording iteration loop** (offline, with the harness in §3.6):
  1. Label about 30 corpus lanes by hand for each Noul. The labels are cheap, since each is a yes/no about the lane text.
  2. Run each variant's wording.
  3. Keep the wording with the best **log loss / Brier against the human labels**, not the one with the highest confidence. The docs are explicit that confidence alone does not prove a wording is better.
  4. For a Choice or Score whose options get confused, move to structured criteria (`what` / `not_for` / `examples`), with examples taken from real lanes.
- **Combining.** Start with a transparent hand rule (§5.1). Once there are ≥ 40 or so non-censored outcomes, fit a **regularized logistic regression**: `P(start_ok on Track A rung) = σ(w·x)`, where x holds the Noul values, the Score probabilities and the code features.
  - With so few samples, use an L2 penalty, few features, and leave-one-out or grouped-by-run cross-validation.
  - This is TypeSafe's own recommendation: "use the probabilities as features in a downstream classical machine-learning model" ([How to build](https://docs.typesafe.ai/concepts/how-to-build-with-system-one), [Autoresearch cookbook](https://docs.typesafe.ai/cookbooks/autoresearch_feature_discovery)). In that cookbook, asking Jev for the target directly scored RMSE 2.15; 38 atomic questions plus a learned model scored 1.77.

### 3.4 Tuning thresholds per question (b)
- **Decide on the aggregated action probability, not on `confidence`.** Track A iff P(A) = P(copy) + P(build) is at least t. For the new set, use P(A) from the rule or the fitted model.
- **Derive t from costs** instead of picking 0.75. Let:
  - c_A = expected cost of a successful cheap-rung run;
  - c_Af = cost of a failed cheap attempt (tokens, wall time, the two fast-check failures);
  - c_B = cost of starting on Track B.

  Starting on A is worth it iff p·c_A + (1−p)(c_Af + c_B) < c_B, which rearranges to **p > c_Af / (c_B − c_A + c_Af)**.
  - Example: c_A = 1, c_B = 3, c_Af = 1.5 gives t ≈ 0.43. Starting cheap can be right well below 0.75, as long as p is a *calibrated* success probability.
  - Fill the costs in from `runs.jsonl` (tokens, seconds) per rung. The profile's `objective` (cost or speed) chooses which of the two to weight.
- **Before there is outcome data:** treat Jev's P(A) as an uncalibrated score. Use a conservative threshold with a **dead band** (e.g. Track A ≥ 0.80, Track B ≤ 0.20, default in between) to absorb the non-determinism in §2.2.
- **With outcome data:**
  - Sweep t on the logged corpus to minimize total expected cost, with leave-one-run-out cross-validation.
  - Report the sweep as a table: fallback rate, capability-climb rate and cost at each t.
  - Recalibrate with a two-parameter Platt fit on logit(P(A)) → start_ok. Do not use isotonic regression below about 200 samples.
- **`finding` and `same-defect`:** their labels come from what actually happened.
  - `finding`: did the architect change the plan, or did a code fix resolve it?
  - `same-defect`: did the fix round actually address the finding?

  Express each threshold as a probability: same-defect p_yes ≥ 0.85 matches today's confidence 0.70. Tune by cost asymmetry: a false `same-defect: yes` causes an unneeded climb, and a false `no` causes one more fix round.

### 3.5 Measuring calibration with small samples (d)
- **Proper scoring rules first:**
  - **Brier score** = mean (p − y)². Also report its Murphy decomposition (reliability − resolution + uncertainty).
  - **Log loss.**
  - Both work at n ≈ 20–50 and compare variants on the same lanes. Use a **paired bootstrap over lanes** (resample lanes, 2,000 draws) for a 90% CI on the difference, or a paired permutation test.
- **Reliability diagram:**
  - Use **3–5 equal-mass bins**, not 10 fixed bins.
  - Put **Wilson 95% intervals** on each bin's observed rate.
  - With n < 100, read it as a sanity check only.
- **ECE:**
  - Report the equal-mass-bin version with a bootstrap CI.
  - Note that it is biased upward at small n and depends on the binning.
  - Also report **Spiegelhalter's Z** test for calibration, which is binning-free and a better fit for small n.
- **Discrimination:** AUC of P(A) against `start_ok`. A calibrated but non-discriminating question is useless for routing.
- **Stability:** replay each lane k = 3 times, with the cache disabled or a nonce in state. Report the flip rate of the *decision*, not of the label.
- **Operational metrics per `qset`** (these are what the user sees):
  - fallback rate (the first real runs had 3 of 4);
  - capability-climb rate by start track, which is the "Jev hit-rate review" idea already in `docs/ideas.md`;
  - tokens and seconds per landed lane.

### 3.6 `catherd jev eval`: offline harness
```
catherd jev eval [--runs <glob|all>] [--lanes <dir>] [--qset route-v1,route-v2 | --qset-file q.ts]
                 [--mode replay|record] [--repeats 1] [--max-tokens 200000] [--labels labels.jsonl]
                 [--json out.json] [--md out.md]
```
- **Corpus.**
  - Lanes come from `<data>/jev-corpus/*.md` or `--lanes`.
  - Outcomes come from every run's `outcomes.jsonl`, joined on `lane_sha256`.
  - Optional human labels live in `labels.jsonl` as `{lane_sha256, names_pattern: true, difficulty: "build", …}`.
- **Request cache.**
  - Key: `sha256(canonical_json({model, state, questions}))`.
  - Value: the raw response, `request_id`, `latency_ms` and `ts`.
  - Location: `<data>/jev-cache/<key>.json`.
  - `replay` never hits the network and fails on a cache miss. `record` calls live only on a miss, stops at `--max-tokens`, and prints the projected cost before it starts ($0.042 per million tokens).
  - With `--repeats k > 1`, each repeat adds `{nonce: i}` to state, so the draws are independent (the method from TypeSafe's consistency cookbooks).
- **Replay pipeline:** for each `qset` and lane, build the state exactly as `route()` would, using the same helper so it cannot drift, then fetch or replay the answers. Run the decision rule, map the decision to a rung with the current profile and catalog (`select()`), and compare against the labels and outcomes.
- **Report, per `qset`:**
  - fallback rate;
  - per-question Brier and log loss against human labels, and P(A) against `start_ok`;
  - AUC;
  - a threshold sweep table;
  - a 3-bin reliability table with Wilson intervals;
  - Spiegelhalter Z;
  - decision flip rate across repeats;
  - mean input tokens, cost and latency;
  - a list of lanes whose decision changed between `qset`s, which is the review queue.
- **CI use:** `bun test` runs `replay` against a small committed fixture corpus of synthetic lanes, not users' lanes. It asserts that the decisions and metrics are unchanged. This locks the `qset` the same way `JEV_MODEL` is locked. A bump to `jev-1.14` then becomes `record` + `eval` + a diff.

  - The TypeSafe [agent skill](https://github.com/typesafe-ai/skills) (Claude Code plugin `typesafe@typesafe-ai`) is documentation for agents writing integrations.
- **TypeScript SDK: `@typesafe-ai/sdk`.** Sources: [npm](https://www.npmjs.com/package/@typesafe-ai/sdk), [repo](https://github.com/typesafe-ai/typesafe-sdk-js), [docs](https://docs.typesafe.ai/sdk/javascript).
  - Version 0.6.0 (2026-09-15), MIT, **no runtime dependencies**, Node ≥ 20, ESM + CJS + type declarations.
  - `new TypeSafeClient({apiKey, baseURL, defaultModel, fetch, timeout, retry, logger})`.
  - `client.systemOne({state, questions, model})`, with builders `choice()`, `score()` and `noul()`. Answer types are inferred from the questions. `client.models.list()` is also available.
  - Retry defaults: `maxRetries` 2; statuses 408, 429 and 500–599; backoff starting at 500 ms, doubling to at most 5,000 ms, with 25% jitter; honors `Retry-After` and `retry-after-ms` up to 60 s; retries connection errors and timeouts.
  - `timeout` is **10,000 ms per attempt, with no total budget**. Pass an `AbortSignal` for an overall deadline.
  - Sends `X-TypeSafe-Retry-Count` on retries. Errors are typed: `AuthenticationError`, `RateLimitError` and so on.
  - Risks: 0.x with a breaking change within 4 days (`Score.criteria` changed from a dict to an array); Bun is not a listed runtime (**UNVERIFIED**, likely fine because it uses global `fetch`); its `debug` log level prints request bodies, i.e. lane text.
  - **Recommendation:** keep catherd's `callJev`. It is about 60 lines, already test-covered with fixtures, and uses ofetch + zod. Port the SDK's behaviour:
    - retry 408 as well;
    - honor `Retry-After`;
    - jittered exponential backoff;
    - a per-attempt timeout of about 10 s and a total deadline;
    - log `x-typesafe-request-id`, `model` and `usage`;
    - extend the zod `Reply` to a discriminated union over `choice`, `score` and `noul`.

    If catherd later adopts the SDK, pin the exact version and inject `fetch` so the fixtures still work.
- **Other SDKs:** [Python `typesafe-sdk`](https://docs.typesafe.ai/sdk/python) 0.7.1, and an [LLM-backed stand-in client](https://github.com/typesafe-ai/system-one-adapter-python) (Python) that could act as a fallback judge. Not needed.

## 5. Recommendations for catherd

### 5.1 Question set and decision rule (`route-v2`)
- **One call per lane.** The state is structured and trimmed:
  ```json
  {"lane": {"title": "# M1.L2 — …", "owns": ["src/routes/jobs.ts","test/jobs.test.ts"],
            "fast_check": "bun test test/jobs.test.ts", "body": "<lane body, code fences stripped or capped>"}}
  ```
- **Questions:** `kind` (Choice, as today plus `other`), `difficulty` (Score, 4 situational levels), and the Nouls from §3.3. That is about 8 questions and roughly 700–900 input tokens, around $0.00004 per lane.
- **Decision rule.** Hand-written for v2, replaced by the fitted model once there is data:
  - `pA = p(level0) + p(level1)` from the difficulty Score, and `pB = 1 − pA`.
  - **Track B** if `kind == terminal` (p ≥ 0.8), or `pB ≥ 0.8`, or any of `shared_state`, `unclear_cause`, `open_design`, `cross_boundary` has noul ≥ 0.8. Choose `hard` over `logic` when `p(level3) ≥ 0.5` or `unclear_cause ≥ 0.8`, because the bars differ (`repo_code 56 / terminal 18` vs `55 / 15`).
  - **Track A** if `pA ≥ 0.8`, `names_pattern ≥ 0.7` or `mechanical ≥ 0.8`, and a fast check exists (computed in code). Pass `difficulty = mechanical ≥ 0.8 ? copy : build` to `select()`.
  - Otherwise use the profile default and log the rule that failed.
  - Keep `kind` gated at p ≥ 0.8. It is reliably near 1.0.
- **Keep `select()`/bars unchanged.** The rule only changes how `kind` and `difficulty` values are produced, so the spec's §6.3 ladders still hold.
- **Store the thresholds as data** (`ROUTE_RULE` next to `QUESTIONS`) and hash both into `qset`.
- **`finding` / `same-defect`:** keep them, but threshold on probability (`p_design ≥ 0.833`, `p_yes ≥ 0.85` reproduce today's behaviour). The instructions already reference state keys in backticks, which is good.

### 5.2 Fallback
- The current fallback (profile `defaultRung` = `sol#medium`, the bottom of Track B) is the safe choice for an uncertain lane. Keep it.
- In the uncertain band, add **optional exploration** (profile flag `jev.explore: 0.1`, default off): start at the Track A rung and log `explore: true`. This is the only way to learn whether lanes routed to Track B would have succeeded cheaply.
- **Access risk.** Signups are paused. Consider making the key *recommended* rather than *required* in `init`, with default routing and a warning, and consider accepting a gateway base URL (`TYPESAFE_BASE_URL`, e.g. Vercel) as the SDK does. Both are spec changes (§6.1) for the user to decide.

### 5.3 Privacy: what is sent
- Today `route()` sends the **whole lane file** as `state.lane`. `askFinding` sends the lane plus the finding text, and `askSameDefect` sends two findings.
- Lane files can hold code excerpts, paths, internal hostnames and occasionally secrets.
- TypeSafe does not train on requests. Zero data retention is enterprise-only ([Models](https://docs.typesafe.ai/models), [Legal](https://docs.typesafe.ai/legal)).
- **Recommendations:**
  1. Say this plainly in `init` and the README.
  2. Send the structured, trimmed state from §5.1: strip fenced code blocks and cap the body at about 4–6k characters. This also helps accuracy, per jaggedness §5.
  3. Run a simple secret scrubber (regexes for `sk-…`, `ghp_…`, `AKIA…`, `-----BEGIN`) before sending.
  4. Never log the state. The current tests already assert this. Log only `state_sha256`.

### 5.4 Cost per run
- Recorded route calls use 566–621 input tokens, and finding and same-defect calls use 382–434 (`/home/user/catherd/test/fixtures/jev/*.json`).
- A 20-lane run with 10 finding checks costs about 20 × 900 + 10 × 450 ≈ 22.5k tokens, **≈ $0.001**.
- Cost is not a design constraint. Do not trim questions to save money; trim the *state* to improve accuracy.

### 5.5 Caching
- Cache within a run by `sha256({model, state, questions})`.
  - It makes `route` idempotent when the orchestrator re-calls it (the same lane gets the same decision despite non-determinism).
  - It avoids repeated calls on resume.
- Share the cache format with `catherd jev eval` (§3.6) so production calls become replayable eval data for free.
- Invalidate automatically on any change to `qset` or `model`, since both are part of the key.

### 5.6 Timeouts and retries
- **Today:** `timeout: 30_000` with `retry: 3` and delays of 3, 2 and 1 s. The worst case is about 4 × 30 + 6 ≈ **126 s** blocking a `route`, while the vendor claims 70–500 ms.
- **Recommended:**
  - 10 s per attempt, 2 retries;
  - jittered exponential backoff starting at 500 ms;
  - honor `Retry-After` up to 10 s;
  - a **hard total deadline of about 25 s**, after which catherd falls back to the default and logs `why: "deadline"`.
- **Retry:** 408, 429, 529 and other 5xx, plus network errors.
- **Do not retry:** 400, 401, 403, 404 or 422. Log 422 with the body's field name (it is a catherd bug), and 401/403 as `auth`.
- Route calls for all lanes are fired in one message, which is well under 1,200 requests/min.

### 5.7 Testing
- **Keep the recorded-response unit tests.** Add fixtures for the Score and Noul answer shapes, for 422, 429 with `Retry-After`, and 529, and for a response whose `model` differs from the pin.
- **Add a `record` script** that makes a live call for a *synthetic* lane and writes the fixture with the state redacted. It uses the same cache format as the eval harness.
- **Pure-function tests for the decision rule.** Probabilities in, `{track, difficulty, source, rule}` out, with boundary cases at the thresholds and in the dead band.
- **Contract test:** zod-parse each answer as a discriminated union on `type`, and reject a choice outside the criteria (already done).
- **Live smoke test** (`CATHERD_LIVE`): run the new `qset` on 3 synthetic lanes (a copy, a build and a hard lane). Assert the *decisions*, not the exact probabilities.
- **Eval regression:** `catherd jev eval --mode replay` on the committed synthetic corpus runs in CI.

### 5.8 Small code-level fixes spotted
- `route.ts` logs `why: "kind …, difficulty …: below 0.75"` but does not record which rule failed or the aggregated probability. Add `derived` and `decision` as in §3.2.
- The `callJev` zod schema drops `model` and `usage`. Keep them and log them.
- The `jev.ts` comment about `~/.config/typesafe/api_key` being "TypeSafe's own" convention is unverified; see §1.2.
- `testJevKey` spends about 380 tokens on a real question. That is fine, but `GET /v1/models` checks a key without inference and without depending on the question set ([Models](https://docs.typesafe.ai/models)).
- `difficulty` fallback rate: the first-runs data (3 of 4 routes fell back) is consistent with a copy/build split. Before redesigning, check the logged `probabilities` in the existing `jev.jsonl` files. If the mass sits in `copy` + `build`, the aggregation rule alone fixes most fallbacks.
