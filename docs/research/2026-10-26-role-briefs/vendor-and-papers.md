# External research: briefing agents in a multi-role coding orchestrator

Date of research: 2026-10-26. Every claim carries a source URL. "Inference" marks my own reasoning, not a source claim. "Unverified" marks claims I could not confirm from a primary source. Pages were read through a fetch tool that summarizes them, so quotes are paraphrases.

## 1. Context engineering (vendor and lab guidance)

- Context rot: recall accuracy falls as the token count grows, in every model, at different rates. Anthropic says the smallest set of high-signal tokens wins. Start with a minimal prompt and add rules only after observed failures. Prefer a few examples to long edge-case lists. Source: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
  Means for a brief: every line must have caused a failure or be a hard requirement. Cut anything the worker can read from the repo.
- Just-in-time retrieval: agents keep light references (paths, queries) and load content with tools when needed. Claude Code does this, often with a hybrid (some data up front). The cost is slower exploration, so the agent needs guidance on where to look. Same source as above.
  Means: put file paths and the one command to read the contract in the brief, not the contract text. Inline only what the lane cannot work without.
- Claude Code best practices: "context window is the most important resource"; performance drops as it fills. Prune CLAUDE.md with the test "would removing this cause a mistake?". Bloated rules get ignored. Emphasis on many lines makes none stand out. Source: https://code.claude.com/docs/en/best-practices
  Means: do not ship 15 run-wide acceptance lines to every role. Use emphasis on at most one or two lines.
- Claude Code best practices on specs: the best specs are self-contained, name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step. Same source.
  Means: a lane brief = goal, files, interfaces, out-of-scope list, one "done when" check.
- Subagents start with a fresh context. They see only the delegation message, their own system prompt, CLAUDE.md, and listed skills. A rule that must apply inside the subagent must be restated in the delegation prompt. Source: https://code.claude.com/docs/en/sub-agents
  Means: no implicit inheritance. State scope rules in the brief, but only the ones that apply to that role.
- Agent teams (Claude Code): teammates do not inherit the lead's history. Put task-specific detail in the spawn prompt. Size tasks as self-contained units with a clear deliverable. Too small = coordination overhead; too large = long unchecked work. Give each teammate its own files. Source: https://code.claude.com/docs/en/agent-teams
  Means: lane = clear deliverable plus exclusive file ownership.
- Anthropic's multi-agent research system: each subagent needs an objective, an output format, tool and source guidance, and explicit task boundaries. Vague delegation caused duplicate work and gaps. Token use explained about 80% of performance variance on BrowseComp. Anthropic notes that tightly coupled work, "most coding tasks", fits multi-agent poorly. Source: https://www.anthropic.com/engineering/multi-agent-research-system
  Means: use exactly those four fields (objective, output format, tools, boundaries) as the brief skeleton.
- Anthropic "Building effective agents": orchestrator-workers lets the orchestrator derive subtasks from the input. Tool and interface design deserves as much care as prompts. Poka-yoke the tools. Keep the design simple. Source: https://www.anthropic.com/engineering/building-effective-agents
  Means: make the correct action easy (a single script that prints the lane contract) instead of describing it at length.
- Cognition, "Don't build multi-agents": share context and full traces, not just the subtask, because actions carry implicit decisions that conflict across agents. Default to single-threaded agents. Source: https://cognition.com/blog/dont-build-multi-agents
  Means: a counterweight. A stripped brief must still carry the decisions that shape the lane (chosen design, naming, shared interfaces). Strip noise, keep decisions. Parallel lanes need an explicit interface contract.
- Cursor, scaling agents: planners explore and create tasks; workers "focus entirely on the task" and do not worry about the big picture; judge decides continue or stop. Prompts mattered more than harness or model. Different models fit different roles (GPT-5.2 better at long autonomous work; Opus 4.5 "tends to stop earlier and take shortcuts"). Too little structure causes drift, too much causes fragility. Source: https://cursor.com/blog/scaling-agents (fetched via summary; the post gives few prompt details)
  Means: workers get the task only. Role-split by model strength.
- Factory Missions: orchestrator plans milestones; each feature gets a fresh worker session with clean context; each milestone ends in a validation phase that runs tests and drives the real app (computer use). Different models per role (validation on a Codex model). Handoffs go through git. Source: https://factory.com/news/missions
  Means: validators run the app and the suite; they are a separate phase with their own tools and model.
- Anthropic, long-running agents harness: failure modes were declaring victory early and marking features done after only unit tests or curl. Remedies: a JSON feature list with a `passes` flag the agent may only flip, one feature per session, end-to-end tests "as a human user would", a startup routine that runs a basic check first. Source: https://anthropic.com/engineering/effective-harnesses-for-long-running-agents
  Means: give the verifier a machine-readable checklist it must flip with evidence. JSON resists casual rewriting.

## 2. Prompt length vs quality and speed

- Lost in the middle: accuracy is highest when the relevant fact is at the start or end of the input and drops in the middle, even for long-context models. Source: https://arxiv.org/abs/2307.03172 (2023; newer models may be better, see the Opus 5 note below).
  Means: put the role-critical duty list at the start or the end, not in the middle of a 100 KB block.
- Chroma context rot: performance becomes less reliable as input grows even on simple tasks. A focused ~300-token prompt beat a ~113k-token one on LongMemEval. One distractor lowers accuracy, four lower it more, and the effect grows with length. Claude models abstained under distractors; GPT models hallucinated confidently. Thinking modes helped but did not close the gap. Source: https://www.trychroma.com/research/context-rot
  Means: irrelevant sections (other roles' duties, other lanes) act as distractors. A GPT-class worker is the most likely to act on them confidently. Strip them.
- IFScale: instruction-following accuracy decays as instruction count grows (10 to 500). Best frontier models reached about 68% at 500 instructions. Models favor earlier instructions. Decay shapes differ (threshold for reasoning models, linear or exponential for others). Source: https://arxiv.org/abs/2507.11538 (keyword-inclusion task, not coding; treat as directional).
  Means: fewer, role-specific duties. Fifteen mixed acceptance lines is exactly the density where misreading rises. Put the most important duties first.
- AGENTS.md study (ICLR 2026, arXiv 2602.11988): repository context files did not improve task success on average, raised cost by more than 20%, and agents did follow the extra instructions (more testing and exploration). Repo overviews did not help. Context files help for non-standard practices only. Authors say unnecessary requirements make tasks harder. Source: https://arxiv.org/abs/2602.11988
  Means: this is the closest evidence for coding agents. Extra instructions are obeyed, so wrong or off-role duties cost real work. Inline only non-obvious rules.
- SWE-ContextBench (arXiv 2602.08316): reusing context helps only when compact and well selected; free retrieval can hurt when irrelevant. Source: https://arxiv.org/pdf/2602.08316 (from search snippet only). SWE-Explore (arXiv 2606.07297) reports that missing core context hurts more than extra irrelevant context. Source: https://www.emergentmind.com/papers/2606.07297 (snippet only, unverified in full).
  Means: precision matters, but do not cut so far that the core contract is missing. Cut distractors, never the decisive facts.
- Opus 5 long context: Anthropic says Opus 5 has a 1M window and keeps instruction following, tool calling and reasoning consistent throughout. Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5
  Means: the Claude lanes tolerate length better than DeepSeek flash is likely to (inference). Length is still cost: see section 5 on repeated reads.
- Placement advice for long inputs: put long data at the top, the query and instructions at the end; Anthropic reports up to 30% better quality from queries at the end in tests. Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices
  Means: reference material first, then the lane task and the duties last. This also matches cache order.
- Effort and thinking: Anthropic says `low`/`medium` effort gives strong quality at a fraction of tokens and latency on Opus 5; use effort as the main cost control. Sonnet 5.5: start at `medium` for well-specified agentic tasks, `high` for harder ones. At `low` it may skip verification; at `low`/`medium` it may stop to check in. Sources: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5 and https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5
  Means: a precise short brief lets you lower effort. A bloated brief tends to need higher effort to sort out.
- Token cost grows with the brief across turns (inference): an agent loop re-sends the whole prefix every turn, so a 100-145 KB brief (roughly 25-40k tokens, my estimate at ~4 bytes per token) is paid again on every tool call, either at full price or at the cache-read rate. 38M input tokens on one lane is consistent with a long loop over a large prefix. Not a sourced figure.

## 3. How mature orchestrators brief sub-agents

- Superpowers `subagent-driven-development`: the implementer gets one task's text plus a one-line "where this fits", interfaces and decisions from earlier tasks, resolved ambiguities, the report-file contract, and the global constraints. It explicitly excludes the full plan and accumulated history ("99% pasted history" is called out as a mistake). The implementer writes a full report to a file and returns status, commits, a one-line test summary and concerns. The implementer must not spawn helpers or reviewers. The reviewer gets three paths (brief, report, diff) plus the binding constraints, and a BASE..HEAD diff recorded before dispatch, never HEAD~1. Source: https://raw.githubusercontent.com/obra/superpowers/main/skills/subagent-driven-development/SKILL.md
  Means: the model to copy. Worker brief = task + interfaces + constraints + report contract. Reviewer brief = paths, not pasted text.
- Reviewer distrust rule (same source): the controller must not tell a reviewer to ignore or downgrade an issue. Implementer self-review never replaces the independent review. Reviewers are told not to re-run what the implementer ran (the source's wording; see the conflict in section 4).
- Aider architect/editor: the architect describes the solution freely; the editor turns it into edits. Pairing improved scores (o1-preview + o1-mini/DeepSeek editor 85.0% vs 79.7% solo; DeepSeek was a good editor). Source: https://aider.chat/2024/09/26/architect.html
  Means: a cheap model does well when the hard thinking is done and handed over as a clear description. Lane files from the architect should be that description.
- SWE-agent: interface design for the agent (the ACI) strongly affects results. Source: https://arxiv.org/abs/2405.15793 (abstract only; details not confirmed).
- Anthropic subagent guidance for Opus 5: it delegates more readily; cap spawns; remove "use a subagent to verify" lines. Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5
  Means: in each worker brief say "do not spawn subagents" if your harness lets them.
- OpenAI Codex workers: a short focused prompt naming the area, the goal and validation criteria; safeguards up front; the deliverable stated; evidence demanded for each change; start with one small task and widen. Source: https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family
- opencode agents: per-agent `prompt` file, `permission` map (allow/ask/deny per tool), `steps` cap (the agent is asked to summarize at the cap), `mode`, `temperature`. The page does not say what context a subagent inherits. Source: https://opencode.ai/docs/agents/
  Means: for the DeepSeek-via-opencode lane use a `steps` cap and a permission map as hard guards, not prose.
- OpenHands, Devin, MetaGPT/ChatDev, Codex cloud tasks: I did not retrieve primary briefing details for these. Unverified. MAST (below) covers the multi-agent failure patterns in MetaGPT/ChatDev-style systems.
- Amp: the oracle is a read-only subagent on a strong model used for review and debugging, deliberately not pushed hard in the system prompt to limit cost. Subagents have their own context and the main thread sees only the final result. Sources: https://ampcode.com/news/oracle and https://ampcode.com/podcast/episode-7 (from search snippets).

## 4. Role-specific briefs: reviewers and verifiers

- MAST (multi-agent failure taxonomy): task-verification failures are a top-level category: premature termination 6.2%, no or incomplete verification 8.2%, incorrect verification 9.1%; reasoning-action mismatch 13.2%; unaware of termination conditions 12.4%. Fixes: explicit termination conditions, multi-level checks including test output, verifiers that check high-level task objectives and not only compilation. A ChatDev change adding a high-level objective check raised task success by +15.6% on ProgramDev. Source: https://arxiv.org/html/2503.13657v3
  Means: give each role an explicit "you are done when" and tell the verifier to check the objective, not only that it builds.
- Vercel agent-harness lesson: agents will claim "all tests pass" without running them. Fix by a verification contract: report what ran, what was blocked, what was unavailable; name the command and its specific result; never present partial verification as full. Past tense with a result suggests it ran; "should be fine" suggests it did not. The lesson says this makes reports honest but does not enforce execution, and enforcement needs gates outside the prompt. Source: https://blog.vercel.com/academy/build-ai-agent-harness/verification-gates.md
  Means: require an evidence table (command, exit code, key output line). Enforce it in the harness: reject a verifier report with no executed-command records.
- Claude Code best practices: give a check the agent can run; ask for evidence (output, command, screenshot); a Stop hook can block the turn until a check passes; a fresh-context reviewer sees only the diff and the criteria, not the reasoning behind it. Warns that a reviewer asked for gaps will always find some, so tell it to report only gaps affecting correctness or stated requirements. Source: https://code.claude.com/docs/en/best-practices
  Means: reviewer brief = diff + criteria + a severity threshold. Verifier brief = the run commands + required evidence.
- Opus 5 code review: high precision and recall; do not tell it "only report high-severity" because it will follow literally and report less; ask for everything and filter later. Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5
  Conflicts mildly with the Claude Code advice above; resolution (inference): have the reviewer report everything with a severity label, and let the judge filter.
- Sonnet 5.5 verification: at `low` effort it can report done without running a check (for example skipping tests because dependencies are missing). Anthropic gives a paragraph that fixes this: run a real check that exercises the change; a syntax-only check or a command that failed to start does not count; install declared dependencies with the project's own package manager; if no real check can run, say which was not run and why. Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5
  Means: paste a near-copy of that paragraph into every verifier brief (it is a vendor-tested wording).
- Opus 5 over-verification: explicit "verify" or "use a subagent to verify" instructions cause over-verification on Opus 5; remove them from worker prompts. Same Opus 5 source.
  Means: workers do not get verification duties beyond "run the lane's own checks"; that is the verifier's job, in a separate session.
- Agent self-validation varies by model: one single-author study reports self-validation rates falling from 100% (Sonnet) to 0% (Gemini Flash). Source: https://arxiv.org/abs/2608.21747 (abstract only; single author; weak evidence). Typed, code-like contracts (TypeScript, OpenAPI) helped weaker models most.
  Means: a cheap worker will not check itself. Hand it an explicit command to run and a typed interface file instead of prose.
- LLM-judge bias: one coding-agent study found a GPT-5 judge more lenient than a Sonnet judge across code families, with no same-family favoritism; another study of verifiable tasks found stronger models show more self-preference. A 2026 NeurIPS listing says blinding judges to authorship and juries both fail to fix reliability (abstract only). Whether an agent ran its own tests is a judge-free signal. Sources: https://arxiv.org/pdf/2604.22891, https://arxiv.org/pdf/2608.21747, https://neurips.cc/virtual/2026/loc/sydney/178251 (all from search snippets; unverified in full).
  Means: use a different model family for the verifier than the worker where you can; treat "ran its tests" as a hard input to the judge.
- Rubric-based verification without execution works but can be sensitive to surface cues; execution-based verification is more grounded but needs environment setup. Source: https://arxiv.org/pdf/2601.04171 (snippet).
  Means: read-only review and execution-based verification are different jobs. Keep both and do not let the first stand in for the second.
- Factory validators run the suite and drive the real app as a QA tester would. Source: https://factory.com/news/missions
- Codex best practices: verification works only if the prompt or AGENTS.md defines what "good" looks like. Source: https://learn.chatgpt.com/guides/best-practices
- How to stop a verifier from passing on reading alone (synthesis, mostly inference): (1) brief it with exact commands and the expected observable result; (2) require a per-check evidence record; (3) tell it that a check with no execution is "NOT RUN", never "PASS" (Vercel wording above); (4) give it a tool allowlist that includes a shell and the run environment, and a reasonable step budget (the opencode `steps` cap or a time budget); (5) have the harness reject a report with zero executed commands; (6) give it a JSON checklist whose `passes` field it may flip only with attached evidence (Anthropic harness). Supporting sources are cited in this section.

## 5. Prompt caching and brief ordering

- Anthropic: the cache prefix order is tools, system, messages. A hit needs an exact prefix match up to the breakpoint. Put static content (tools, system instructions, reference documents, examples) first; put the breakpoint on the last block that is identical across requests, not on timestamps or per-request text. Changing tool definitions, system text, thinking or `effort` settings invalidates later layers. Default TTL 5 minutes (1 hour at 2x write cost); cache reads cost 0.1x base (0.05x on Opus 5.5 and Sonnet 5.5); 5-minute writes cost 1.25x. Minimum cacheable prefix is 512 tokens for Opus 5.5 and Sonnet 5.5. Parallel requests share a cache entry only after the first response starts. Caches are per workspace. Source: https://platform.claude.com/docs/en/build-with-claude/prompt-caching
  Means: the run-wide shared block (plan preamble, shared contract) goes first and stays byte-identical across all lanes; lane text goes last. Start parallel Claude lanes only after the first one's response begins if you want them to hit the cache.
- Claude Code subagents and teammates run on a 5-minute cache bucket by default; the `subagentPromptCacheTtl` setting can raise it to 1 hour. Source: https://code.claude.com/docs/en/agent-teams (Token usage section).
- OpenAI: caching stores KV tensors for the longest matching prefix; the entire rendered prefix must match. GPT-5.6 and later: 1,024 visible-token minimum; cached reads 0.1x (0.05x on GPT-6.1 Sol); writes 1.25x for a 30-minute lifetime. Put stable instructions first, volatile content last; append instead of rewriting earlier turns; keep tool definitions stable. Changing request-level `reasoning.effort` breaks the cache, so use `configuration_update` items. Sources: https://developers.openai.com/api/docs/guides/prompt-caching and https://developers.openai.com/api/docs/guides/latest-model
  Means: the same ordering rule applies to Codex. Do not vary effort per request within one cached prefix.
- DeepSeek: disk-based caching is on by default; only a full match of a stored "prefix unit" hits, partial overlap does not; units are saved at request boundaries, at shared prefixes and at fixed token intervals; the system is best-effort, with no hit-rate guarantee; caches clear after hours to days; usage shows `prompt_cache_hit_tokens` and `prompt_cache_miss_tokens`. Source: https://api-docs.deepseek.com/guides/kv_cache. Prices were not on that page, so cache price is unverified.
  Means: a byte-identical shared prefix across lanes and across turns pays off for DeepSeek too. Check the hit/miss counters in your run logs.
- Cross-vendor ordering for a role brief (inference from the sources above): (1) role-independent stable block: project facts and shared contract, identical for all roles of one run; (2) role-stable block: duties of this role; (3) per-lane block: the lane task and files; (4) last, a short restatement of "done when" and the output format. Never put timestamps, run IDs or per-lane text above the stable block.
- Conflict to note: "long data first, instructions last" (Anthropic prompting guide) and "stable prefix first" (caching) point the same way only if the stable part is the reference material and the per-lane task is the "query". Duties that differ per role should sit after the shared block, so the shared block still caches.

## 6. Model-specific notes

Codex / GPT-6.1 Sol (OpenAI):
- OpenAI states each instruction once, trim repeated rules, unrelated tools and redundant examples; remove one group at a time and re-run evals. It reports, in internal coding-agent evals, that leaner prompts raised scores about 10-15% and cut tokens 41-66% (directional; validate on your tasks). Source: https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6 (page is for GPT-5.6; the GPT-6 page points the same way, so treat as applying to GPT-6.1 Sol with moderate confidence).
- Structure: short sectioned prompt: Role, Goal, Success criteria, Constraints, Tools, Output, Stop rules. The page gives no XML-versus-markdown rule; its example uses an XML-style block for tool routing. Describe the destination and stop conditions, not the route; reserve ALWAYS/NEVER for true invariants. Contradictory rules cause more instability than missing detail. Same source.
- Codex best-practice prompt skeleton: Goal, Context, Constraints, Done when. Short accurate AGENTS.md beats a long vague one; add rules only after repeated mistakes. Source: https://learn.chatgpt.com/guides/best-practices
- GPT-6 guide: the model may stop to ask where earlier models assumed; tell it to infer intent and finish unless the action is destructive. It may delegate less than you need; say when. Astra (a sibling model) follows longer instructions better but is more sensitive to what is in context; audit AGENTS.md and skill files for stray instructions. Sol supports `low` to `max`, not `none`. Source: https://developers.openai.com/api/docs/guides/latest-model
- GPT-6 tends to test thoroughly, sometimes broader than a small change needs; tell it to run tests suited to the change. Same source.
- Chroma found GPT-family models hallucinated most under distractors. Source in section 2. Weak evidence for Sol specifically (the test used older models). Unverified for GPT-6.1 Sol.
- Cursor reports GPT-5.2-class models were better at long autonomous work and instruction following. Source: https://cursor.com/blog/scaling-agents (older model generation; unverified for Sol).
- Third-party claims that I could not confirm from OpenAI primary pages: exact "outcome-first" numbers beyond those on the OpenAI page above (https://codex.danielvaughan.com/2026/07/26/gpt56-outcome-first-prompting-lean-system-prompts-codex-cli-agents-md-strategy/ cites OpenAI and a Decrypt article). Treat as secondary.

Claude Sonnet 5.5 / Opus 5.5 via Claude Code (Anthropic):
- Opus 5 does best when given the full task spec up front and left to run; constrain scope explicitly for narrow tasks (Anthropic gives a ready paragraph); drop verification and double-check instructions; cap delegation. Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5
- Sonnet 5.5: scope-limiting paragraph ("when the work is done and checked, stop and report; don't add features, tests, files or docs not asked for"); at `xhigh`/`max` add a line to stop it launching reviewer subagents (Anthropic reports a cost cut of about one third at `max` with no quality change). Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5
- XML tags help parse prompts that mix instructions, context and inputs; explaining why an instruction exists helps; avoid aggressive emphasis on many lines. Sources: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices and https://code.claude.com/docs/en/best-practices. Anthropic also says the exact format may matter less as models improve (context-engineering post).

DeepSeek v4.1 flash via opencode:
- Official docs (thinking mode): thinking on by default with effort `high`; `reasoning_effort` accepts low/high/max (none disables thinking; xhigh and medium map to high); with tools, `reasoning_content` must be passed back in every later request or the API returns 400; `required`/named tool choice is unsupported in thinking mode; temperature has no effect in thinking mode. The page has no prompting advice. Source: https://api-docs.deepseek.com/guides/thinking_mode/
  Means: check that opencode passes reasoning back. A broken round trip causes errors and retries (inference; not a documented cause of your slowness). Reduce the effort for mechanical lanes: effort drives thinking tokens and time.
- Hugging Face encoding README for V4.1-Flash describes a numeric effort scale (low=50, high=75, max=100), noted by a search snippet; applies to the model's chat format, not necessarily the API. Source: https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/blob/main/encoding/README.md (snippet only; unverified).
- No DeepSeek-published guidance on XML vs markdown, brief length or instruction format. Anything on this from third-party guides (for example https://deepseekai.guide/tutorials/deepseek-prompt-engineering/ , https://docs.apiyi.com/en/news/deepseek-v4-launch.md) is unverified. Those guides recommend a tight system prompt and a stable prefix for cache hits.
- Weaker or cheaper models gain most from structured, code-near specs and wasted more tokens in compile-debug loops than strong models (single-author study, weak evidence): https://arxiv.org/abs/2608.21747
- Cheap-model fit: OpenAI reports a cheaper model at high effort got about 92% of findings at about 14% of the cost on a discovery task, and medium effort suits well-scoped tasks. Source: https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family (OpenAI models, not DeepSeek).

Gaps I could not close (all unverified): Devin, OpenHands, Codex cloud, MetaGPT briefing details; an official GPT-6.1 Sol statement on XML vs markdown; DeepSeek cache pricing and any official brief-length guidance; direct measurements of agent-loop slowdown from long briefs in SWE tasks (I found only context-rot and AGENTS.md evidence, not a controlled brief-length study for agent loops).

## Ten most actionable principles, ranked by evidence strength

1. Give each role only the duties that are its own; delete the rest. Evidence: instruction-following decays with instruction count (IFScale, arXiv 2507.11538), extra instructions in context files are obeyed and raise cost 20%+ without raising success (arXiv 2602.11988), distractors lower accuracy (Chroma), and OpenAI and Anthropic both advise stating each instruction once and removing what does not change behavior. Strong, from several independent sources.
2. Worker brief = this lane's task only, plus interfaces from other lanes, resolved decisions, constraints that bind this lane, and a report contract. Leave out the whole plan and other lanes. Superpowers subagent-driven-development, Cursor workers, Factory fresh-per-feature sessions, Claude Code agent-team guidance. Medium-strong (practitioner evidence, one measured study on context files). Keep the decisions that shape the lane (Cognition's warning).
3. Make the verifier execute: give exact commands, require an evidence record (command, exit code, key output), treat an unrun check as NOT RUN, and reject reports with no executed commands in the harness. Evidence: MAST (no or incomplete verification 8.2%, incorrect verification 9.1%), Vercel verification-gates lesson, Anthropic harness (marking done after only unit tests or curl), Sonnet 5.5 verification paragraph. Strong on the failure, medium on the fix (prompt-only fixes are admitted to be unenforced; enforce in the harness).
4. Put a stable, byte-identical prefix first and the per-lane and per-role text last. Evidence: documented prefix-match rules at Anthropic, OpenAI and DeepSeek, with read prices of 0.1x or less (0.05x on Opus 5.5, Sonnet 5.5, GPT-6.1 Sol). Very strong (vendor docs). Do not vary effort, tools or timestamps inside the prefix.
5. Reference by path and let the agent fetch on demand; inline only what the lane cannot start without. Evidence: Anthropic just-in-time retrieval, Claude Code best practices, superpowers (task text inline, plan by path for reviewers). Strong as vendor practice; trade-off is slower exploration, so name the files.
6. Define the destination and the stop condition per role ("done when"), not the route. OpenAI prompt guidance, Codex best practices, MAST (premature termination, unaware of termination conditions 12.4%). Strong.
