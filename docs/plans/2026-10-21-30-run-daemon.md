# catherd 2.0, plan 30: the run daemon, its state machine and the judge — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the run loop moves out of the session into catherd. `run_start` launches a detached daemon per run; the daemon replays the run's `events.jsonl` into a state, feeds each new event to a pure `next(state, event) → actions[]`, and carries the actions out through the 1.5 services. A model is called only to plan, to place findings no lane owns, to answer a worker's question and to decide an unexpected case, each as a short headless `judge` dispatch. The session sees six tools; a question parks one unit and reaches the owner's phone through `notify.url`; a crash or a reboot resumes by replay.

**Architecture:** Domain: the event union and its replay (`run-events.ts`, `run-state.ts`), the machine (`run-machine.ts`), the judge contract (`judge.ts`), the phone message (`notify.ts`). Infra: one detached launcher for supervisor and daemon (`launch.ts`), the ntfy sender (`ntfy.ts`). Services: the event store, the daemon process, the effects (actions → 1.5 services), the briefs, the run report, the failover rung, the phone notices, the panel's read API and the session's client. Entry: `daemon-bin.ts`, `session-tools.ts`, `catherd answer`.

**Tech Stack:** Bun ≥ 1.4, TypeScript, zod 4, citty, `@modelcontextprotocol/sdk`. No new dependency.

**Spec:** `docs/specs/2026-10-12-catherd-2.0-design.md`, decisions 1–8, 16, 18, 19 and the landing rules of 21. Inputs: `docs/plans/drafts-1.6/2026-10-12-29-gate-evidence.md`, `…-30-blocked-recovery.md`, the landing part of `…-33-milestone-branches.md`; t3herd 71cbb6a `src/step.ts` (`roundCall`, `findingKey`, `recover`).

**Two files.** This one (30) is the engine: decisions 1–5, 7 and 16, the 30-minute hold of 6, and a Produces block that declares **every** event and action type of both files. `docs/plans/2026-10-21-30b-unattended.md` (30b) adds the six blocked reasons and Jev (8), recovery (19), failover to any configured backend (6), gate evidence (18) and the landing rules of 21. 30b executes after 30 merges, as its own PR, and adds no event or action type.

## Design

- **D1. The daemon is the supervisor's pattern, one level up.** Workers run under `launchSupervisor` (`src/infra/launch.ts:12-25`: a thin bin, `detached: true`, own log, `unref()`), and `supervise()` (`src/infra/supervisor.ts:145-156`) holds `tryLock(supervisorLockTarget(dir))` for its life, so a dead holder is reclaimed and a second one exits touching nothing. The daemon is the same: `launchDetached` (factored out of `launchSupervisor`) spawns `src/entry/daemon-bin.ts <run id>`; `runDaemon` holds `tryLock(<run>/daemon)` until the run ends. Liveness is `lockHeld` (pid plus start time), never the heartbeat. Workers keep their own supervisors in their own sessions, so a dying daemon never takes a worker with it.
- **D2. Events are facts, actions intents.** Only effects and clients append events; the machine never does. State is `replay(events)`, a fold of `reduce`. Each event has `v`, a dense `seq` (assigned under the lock from the file's last line) and `at`.
- **D3. `next` is level-triggered; the daemon deduplicates.** `next(state, e)` returns the reactions to `e` plus every step the state is ready for. The daemon keeps an in-memory set of issued `actionKey`s, drops an action already issued, and clears a key when an event `confirms` it. A restart empties the set, which is right: an action whose event exists is no longer ready; one whose event is missing must run again. Resume = replay silently, append `daemon.started`, execute `next(state, daemonStarted)` (watch every live dispatch, re-issue what never got its event).
- **D4. Effects are the 1.5 services.** `dispatch` → `admit` + `launcher.launch` + a daemon watcher (`waitForFinish`, `finalizeDispatch`, `dispatch.ended`), not `dispatch()`, whose watcher's `settle` fails over on its own; `route` → `routeLanes` + `preflight`; `climb`, `land` (its `gate()` stays the last word), `park` (milestone: `questions.jsonl`, which `land` reads), `cancel`. A long effect appends its event when done; a throw becomes `effect.failed`.
- **D5. The 1.5 protocol becomes transitions.** Each branch of `protocolNext` (`src/services/protocol.ts:126-196`) and each step of the skill's "The sequence" is a row of Task 2's table: dossier → architect → `readPlan` (planning); "route and preflight" → `route`; ready lanes with After: held (`unfinishedAfter`) → lanes `pending` whose `after` are `done`; the orchestrator's fast check → `fastCheck`; "out of rungs" → judge `unexpected`; reviewer and the partial second pass → `reviewer-<M>`, `reviewer-<M>-2`; "one fix round" (`openFindings`) → convergence (D8); the verifier, BLOCKED: environment and the fresh re-check → `verifier-<M>` with its verdict in `dispatch.ended` (`replyVerdict`, `blockedByEnvironment` of `milestones.ts`); "commit, then land" → `commit` before reviewer and verifier, `land` after a PASS. `protocol.ts` stays for `peek` and the TUI until plan 31; no 2.0 caller reads it.
- **D6. The judge is a role** (`judge`, read-only, default `claude-code:claude-opus-5-5#medium`, routed with no lane like any lane-less role). A call is a dispatch `judge-<id>` whose brief holds only its input; its reply becomes `judge.decided`, or `judge.failed` (asked once more, then the unit parks). Kinds: `triage`, `question`, `unexpected`. `report.md`'s "Audit" lists every decision.
- **D7. The session is a client.** The services stay where the daemon or roles call them; the registration modules go:

  | 1.5 session tools | 2.0 |
  | --- | --- |
  | `run_start`, `status`, `answer`, `cancel`, `result` | session tools, new shapes |
  | `profile_get`, `profile_validate`, `profile_set` | one `profile` tool |
  | `dispatch`, `route`, `preflight`, `climb`, `land`, `park` | internal: effects |
  | `peek`, `set_next`, `record_agent_run`, `run_pin`, `runs_summary`, `lane_set`, `owns_add`, `ask`, `test_push`, `catalog_*`, `workspace_*` | off the session; services and CLI stay |
  | `read_run_file`, `write_run_file`, `read_knowledge`, `gate_check`, `gate_pass` | role server only (`role-server.ts`, unchanged) |
- **D8. Fix rounds converge.** After review round `r` with `n_r` open BLOCKER and BUG lines (`none`, `n/a`, `-` are no finding): `n_r = 0` → verifier; `r ≥ softCap(lanes)` or (`r ≥ 2` and `n_r ≥ n_{r−1}`) → stop: an open BLOCKER parks the milestone, else the open lines, verbatim, become known issues and the verifier runs; otherwise a fix round, each finding to the lane owning its file, the rest to the judge, and a lane whose `findingKey` survived its fix climbs first. A verifier FAIL's lines enter as BLOCKERs, so a FAIL that does not converge parks.
- **D9. Quota.** A `limit` holds its quota until `at + 30 min`; an `ok`/`complete` end on that quota clears it. The unit goes back `pending` with `failoverFrom`; the `dispatch` effect asks `failoverRung` (30: the profile's stand-in, Claude last; 30b: every configured backend); with none free it appends `dispatch.refused{ code: "E_ALL_HELD" }` and the unit waits for `wakeAt` (the daemon appends `tick`). A limit never parks.
- **D10. Crash and reboot.** Only files: `events.jsonl`, `daemon.json`, the lock. Boot reconcile, every session tool, the read API, `summarizeRun` (so `catherd status` and the TUI) and `catherd answer` call `ensureDaemon`; two at once launch two processes and the lock lets one run.
- **D11. 1.5 runs are not migrated.** A 2.0 run has `events.jsonl`. Without it, the daemon, client and read API refuse to drive the run (`engine: "1.5"` in `status`); reconcile, the notifier and `settle` keep their 1.5 paths for it.
- **D12. Every role runs headless.** The `dispatch` effect runs a `claude:` rung as `headlessRung(rung)` (`claude-code:<model>#<effort>`); routes keep the profile's rung.
