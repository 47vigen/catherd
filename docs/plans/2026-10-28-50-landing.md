# Plan 50 — landing, the one verifier, and the 2.0 gate deleted (architect-led runs, stage 1, slice 5)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Never read the whole plan: take your task brief.

Setup: bun install --frozen-lockfile

**Goal:** a run with a `base` lands (spec D11). It works in one tree of its own on a branch named after the run; the
architect's `land {final?, why}` commits that tree, pushes the branch and opens or updates one MR per run, with no
park. `land {final: true}` needs a green full check and a verifier PASS on the pushed commit, merges a base that moved
under the run's files, and asks the owner one question, merge?, whose answer ends the run `done`. One verifier runs
commands on the integrated product, and a PASS with no command run is a FAIL (D8). Everything the 2.0 land gate kept
alive is deleted: the gate service and CLI, the verifier's role lock, the milestone branches and parks, `protocol.ts`,
`route.ts` with `routes.jsonl` and `outcomes.jsonl`, and the answer mirror into `questions.jsonl`.

**Architecture:** landing is one more reducer action. `land` appends `land.requested`; `architectNext` emits a `land`
action for each queued land; `realEffects.perform` claims the run's tree, calls `runLand` and appends `land.done`
(plus a run-unit `question.parked` for a final land that passed). `applyArchitect` folds `land.done` into
`ArchState.lands` and an inbox line, and ends the run when the merge question is answered. The tree is
`<run>/trees/run`, claimed lazily by the first dispatch, check or land of a base run. The verifier rule is read from
its reply: no backend list, no ladder filter.

**Tech stack:** Bun ≥ 1.4, TypeScript, zod, SQLite (`checks`, `events`), git, `gh` / `glab` when present.

**Spec:** `docs/specs/2026-10-27-architect-led-runs-design.md` — D5 (stage 1: one integration tree), D8 (one verifier,
`RAN:` lines), D11 (landing), the `land` row of D3's tool table, "What the daemon keeps" (landing mechanics), the
deletion table rows "Landing parks", "The verifier role lock" and "milestone per branch", and the stage table, stage 1.

## Global Constraints

- Version stays 2.0 (unreleased): the plan's one changeset is `"catherd-cli": minor`.
- `land` never pushes the base, `main`, `master` or origin's default branch, and never force-pushes. A rejected push
  is reported, not retried with force.
- Gate only the outcome: the final land checks a check row and a verifier verdict, nothing about how the run got there.
  Non-final lands are never gated and never park.
- Deletion follows replacement: the reviewer contract, the ui-reviewer fold, `PARK_REASONS`, `DispatchDetail.route`
  in the panel schema and the metric views stay for plan 51. No OpenAPI change in this plan.
- Layers `domain → infra → adapters → services → entry` (`test/architecture.test.ts`).
- Tests never reach the network and never sleep on the wall clock; git remotes in tests are local bare repos; the
  forge CLI is the `forge.open` seam, never a real `gh` or `glab`.
- No personal infrastructure, hostnames or absolute home paths in code, tests or docs.

## Review Focus

- A forge CLI that is missing, not signed in, or prints "already exists": the branch stays pushed, the MR is updated
  or the message gives the exact command; the land is `pushed`, not an error (Task 4, land.test case 4).
- A base that moved under files the run did not touch: no merge, the final land goes on; moved under the run's files:
  merge, push, refuse final, ask for the check again; a conflict: `merge --abort`, refuse (Task 4, case 3).
- A dirty tree at final: the commit `land` makes is the sha the check and the verifier must name; an earlier green
  check on a "worktree" ref never counts (Task 4, case 2; Task 3, architect-check).
- A daemon restart between `land.requested` and `land.done`: the action replays once (`actionKey land:<id>`,
  `confirms` on `land.done`), and a second push of the same sha is a no-op (Task 5).
- The run's tree folder deleted by hand while the run lives: the next claim re-adds the run's own branch; a folder
  with another branch, or a same-named branch that is not this run's, is refused with E_TREE (Task 3).

## Rulings

Each is `R<n>: what — why — cost if wrong`. They bind every task.

- R1: the landing target is the run's own feature branch, `runSlug(title)`, made from `origin/<base>`; one branch and
  one MR per run — D11 says so, and stacked milestone MRs are what it drops — a change too big for one MR is split
  across runs by the owner.
- R2: `land` refuses to push a branch named `base`, `main`, `master` or origin's HEAD branch, and never passes
  `--force`; a rejected push returns `refused` with "fix the remote (a rejected push is never forced), then land
  again" — protected branches are production-touching and stay the owner's (O6) — an owner whose base is called
  something else and is protected only on the forge relies on the forge's own protection, which also refuses.
- R3: catherd never merges the MR; the owner's answer to the merge question (any answer) ends the run `done` — D11:
  "it does not wait on the merge itself" — a run reads `done` while its MR is still open; that is the contract.
- R4: non-final lands are free: no check, no park, no question — the architect is the brain and a checkpoint push is
  reversible — a red branch on the forge between checkpoints is visible to anyone watching the MR.
- R5: the final gate is two records on the pushed sha: a `checks` row with scope `full`, base exit 0 and `ref` equal
  to the sha with exit 0, and a `dispatch.ended` verifier verdict `pass` whose head is a prefix (≥ 7 chars) of the
  sha — outcome, not process; the D11 text — a verifier that names a short sha of another commit with the same prefix
  passes (7-hex collision inside one run: negligible).
- R6: a check on a dirty tree records `ref = "worktree"` and never satisfies R5; `land` commits a dirty tree first, so
  the architect checks after landing — the proof must name the commit the owner merges — one extra check per run when
  the architect checks before landing.
- R7: when `origin/<base>` moved, `land` computes the overlap of the run's changed files with the base's changes since
  the merge base; only an overlap merges (`git merge --no-edit`), pushes, and refuses final with "the base moved
  under the run's files: check and verify again"; a conflict aborts and refuses — D11's "merges it when the base
  moved under the run's files" — a semantic clash in files the run did not touch reaches the owner's MR untested
  against the new base.
- R8: a forge CLI failure is `pushed` with "the MR was not opened (<why>): open it with <mrCommand>" — the push
  is what matters; tokens are not catherd's to hold — the owner opens one MR by hand.
- R9: the MR body is problem first (title, A-lines), then the change (ledger tasks done), one proof line (the full
  check), the audit last (Known issues, Tests deleted or skipped, Change log of every architect `why`); D11's
  "oracle overrides" line is omitted: stage 1 has no oracle — the owner reads the problem before the audit — plan 51
  adds the oracle line with converging reviews.
- R10: the run's tree is claimed lazily by the first dispatch, check or land of a base run, inside the effect, not at
  `run_start` — `run_start` must return fast and a run may finish without touching code — the first task of a base run
  waits for `Setup:` (bounded by `treeLimits.setupMs`).
- R11: a run without `base` works in the checkout as in plans 47–49, and `land` refuses it — the owner's checkout is
  not catherd's to push — the owner commits by hand.
- R12: one verifier, enforced as an outcome: a `VERDICT: PASS` with no `RAN:` line carrying an exit code is read as a
  FAIL (`NO_COMMAND_RUN`); no list of "command-capable" backends — the ladder holds only rungs whose reply shows a
  command ran, which is what D8 asks — a verifier that lies in its RAN lines passes; R5's check row is the
  independent proof.
- R13: `route.ts`, `routes.jsonl` and `outcomes.jsonl` are deleted with their writers; `DispatchDetail.route` stays in
  the panel schema as `null`, the run index's climbs and the scorecard's lanes read 0 — no OpenAPI change in this
  plan — the panel's route view is empty until plan 51.
- R14: `questions.ts` (park, answer) stays: it reads earlier runs' parks; only `run-client.ts`'s mirror into
  `questions.jsonl` goes — read-only views of finished 2.0 runs must keep working — none.
- R15: `infra/memory.ts` and `limits.memory` stay — stage 2's per-writer trees need them — dead config for one plan.
- R16: `.env*` files are not copied into the run's tree; the plan's `Setup:` line is the hook — catherd does not move
  secrets — a repo whose check needs `.env` fails until its `Setup:` copies it.
- R17: `dispatch` now requires a rung ("pass rung: the coordinator names the rung of every dispatch") — the routing
  fallback was `route.ts` — a 1.5-era caller that omitted it gets a clear refusal.
- R18: `catherd lock` keeps only `[--slots N] -- <command>`; `--role` and `--run` go with the role lock — D8's one
  verifier runs once, there is nothing to serialise — none.
- R19: `docs/handoff/process/` contracts have no lane wording and stay; the reviewer prompt stays (plan 51).

## Edge cases

- `land` on a run whose tree was never claimed: the effect claims it first (R10), so `land` on a fresh base run pushes
  an empty branch and opens an MR with no change — allowed; the architect should not.
- Two `land` calls queued at once: each is its own action, run in order; the second finds nothing to commit and pushes
  the same sha (no-op).
- `land {final}` refused, then fixed: the architect calls `land {final: true}` again; `mergeAsked` is set only by a
  final land that passed.
- The owner answers the merge question with "not yet": still ends the run `done` (R3); the MR stays open.
- `run_start` with `base` equal to the run's slug: `claimRunTree` refuses (`branch === base`).
- A branch of the run's name exists on origin but not from this run: refused with E_TREE; rename the run.
- An effect failure inside `land` (git crash): the land's state becomes `done`, the inbox line says what failed, and
  the architect decides.
