# Plan 49 — role ladders, and the decision model deleted (architect-led runs, stage 1, slice 4)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Never read the whole plan: take your task brief.

Setup: bun install --frozen-lockfile

**Goal:** each role's rungs, in profile order, are its ladder (spec D7). The architect names any rung on a role's
ladder through `delegate_task {rung?}`; with none, the task runs on the ladder's default, and a ledger task tried
before runs on its last attempt's rung, one step up when that attempt failed, timed out, was too hard or drew a
review BLOCKER. `capabilities` reports each ladder. The decision model is deleted with everything that exists only for
it: its client, questions, levels, floors, probe, key and credentials file, its profile block, its doctor row, its
`init` step, its panel section and Decision tab. The retired `judge` role leaves `ROLES` and every profile. A profile
an earlier 2.0 build wrote still loads, and is migrated once.

**Architecture:** the climb is a pure read of the run state: `ladderRung(arch, role, ledgerTask, ladder, default)` in
`architect-state.ts`, called by `delegate_task` inside the events lock, over a new `ArchTask.climbs` flag that
`applyArchitect` sets when a `dispatch.ended` names a rung reason. Nothing new is stored and no event changes. The
routing port shrinks to `checkStart` and `catalog`. `migrateProfileDoc` gains one guarded step (D16) and loses its
TypeSafe key argument.

**Tech stack:** Bun ≥ 1.4, TypeScript, zod, the MCP SDK; the panel in `web/` (React, generated openapi client,
Playwright e2e).

**Spec:** `docs/specs/2026-10-27-architect-led-runs-design.md` — O5, D3 (the architect's access), D7 (ladders), the
`capabilities` and `delegate_task` contracts in D3's tool table, D16 (profile migration), the deletion table rows "The
decision model" and "Routing by bars and objective", and the stage table, stage 1.

## Review Focus

1. The climb reads observed facts only: `failed`, `timeout`, `too_hard`, or a reviewer/ui-reviewer BLOCKER on the same
   ledger task ending at or after the attempt; a `provider_error`, `no_access`, `needs_user` or `limit/*` end never
   climbs; the top rung stays the top (Task 1).
2. The attempt read is the one that ended last by `endedSeq`, not the one delegated last (parallel attempts), and the
   stall rule uses the same read (Task 1).

   typecheck` and `bun run lint` (unused imports are errors) prove it (Tasks 3–5).
5. The panel: no Decision tab, no Decision model section or tile; an earlier run whose questions a judge answered

## Rulings

Each is `R<n>: what — why — cost if wrong`. They bind every task.

- R1: the ladder is the role's `rungs` in the order the profile stores them; the migration never re-sorts by
  intelligence — the owner wrote that order, `profile validate` already warns "the ladder goes down", and sorting
  needs the catalog inside a pure migration — a stored ladder that descends climbs to a weaker rung until the owner
  reorders it.
- R2: the default is `defaultRung` when set, else the first rung; the worker's built-in `defaultRung` goes, so a fresh
  profile starts coding workers on Luna high (the flash-class rung, spec D7 defaults) — 95% ok at ~$0.01 in the 14
  runs — a profile written before this plan that stored `defaultRung: Sol medium` keeps it.
- R3: a climb is one step from the last attempt of the same role on the same ledger task, never from the default:
  a retry after a provider error stays on that attempt's rung, and a rung no longer on the ladder falls back to the
  default — the spec's "next rung up the ladder" — two failures from the default reach the third rung, not the second.
- R4: a review BLOCKER climbs when the review (role `reviewer` or `ui-reviewer`) is an attempt on the same ledger task
  and ended at or after the worker's attempt; a NIT or a passing review does not — the review is the observation —
  a review delegated without `ledgerTask` never climbs anything.
- R5: `limit/*`, `provider_error`, `no_access`, `needs_user` and a cancelled or refused attempt never climb and never
  count for the stall rule's "failed" read — spec D7 "a reason outside the rung" — a quota-limited task retries on
  the same rung (quota failover on a hold stays an ideas.md item).
- R6: at the top of the ladder a further failure keeps the top rung, and the stall rule then refuses a retry with no
  news — escalation has nowhere to go, and D10's stall is the stop — the architect must add news (a ledger edit) or
  name another role.
- R7: the architect's explicit `rung` always wins and is checked against the ladder only — O2 — none.
- R8: `capabilities` reports `{ladder, default}` per role (`rungs` renamed) and `delegate_task` returns the `rung` it
  chose — the architect sees what it got without a `task_status` — a prompt that said `rungs` reads `ladder`.
- R9: the decision model is deleted whole: `decision.ts`, `decision-client.ts`, `decision-service.ts`,
  `credentials.ts`, `catalog/decision.json`, `test/fixtures/decision/`, the live decision test, `decide`, `verdict`,

## Edge cases

- A ledger task's attempts ran in parallel: the climb and the stall read the one with the highest `endedSeq`.
- The last attempt was another role's (a reviewer): the worker's own last attempt sets the base rung; the review only
  decides whether it climbs.
- A role's ladder lost the last attempt's rung (profile edited mid-run): the default.
- A ladder of one rung: always that rung; a failure then a retry with no news is `stalled`.
- `delegate_task` with no `ledgerTask`: always the default.
- A 1.5 profile (`jev`, `bars`, `objective`): unchanged from plan 44; it never had `decision`, so the D16 step runs only
  when it also has `roles.judge` (a 2.0 default write does).
- A profile file that cannot be parsed: `migrateProfiles` skips it and the command that names it reports it, as before.
- `catherd init` piped: one answer per question fewer than three (the decision url, model and key are gone).
- An earlier run whose question a judge answered: the Questions page still says `Judge`.
