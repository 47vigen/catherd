# Plan 51 — reviews that converge, the ui-reviewer folded, and the stage-1 metrics (architect-led runs, stage 1, slice 6)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Never read the whole plan: take your task brief.

Setup: bun install --frozen-lockfile

**Goal:** reviews catch real bugs and converge fast (spec D8). A reviewer reports `IMPORTANT | NIT | PRE-EXISTING`,
each finding naming its bug class; a review with no rung runs on another model family than the work it reads, and
says `same-family` when its ladder has none; a re-review of a ledger task reads only the diff since the last review
and never repeats its findings; a fourth review round on one task is refused until the architect replans it. The
architect logs what it did with each finding (`findings`), and a bug a review missed joins the reviewer eval set.
The `ui-reviewer` role folds into the reviewer (a UI pass is a reviewer brief that names screens); old profiles
migrate once and earlier runs still read. The stage-1 metrics of D17 are computed from each run's rows and shown in
the panel, `catherd runs metrics` and the scorecard, and `catherd scorecard stage` compares two stages task by task
on two or more runs each.

**Architecture:** everything is a read of what the run already records, plus two events. `delegate_task` for a
reviewer picks the rung (`crossFamilyRung`), counts rounds (`reviewRounds`) and snapshots the tree
(`snapshotTree`: a commit no ref holds, made through a throwaway index); `task.delegated` carries `sameFamily` and
`snapshot`. `applyArchitect` keeps a review's findings on its `ArchTask`; `taskBrief` gives a re-review the diff
between two snapshots and the earlier findings. New events `findings.handled` and `review.missed` come from one new
architect tool, `findings`. `knownIssues(arch, ledger)` feeds the MR body. Metrics are a pure
`runMetrics(input)` over records, events and `checks` rows, read by `metricsOf(run, now)`.

**Tech stack:** Bun ≥ 1.4, TypeScript, zod, SQLite (`checks`, `events`), git; the panel in `web/` (React, generated
openapi client, Playwright e2e).

**Spec:** `docs/specs/2026-10-27-architect-led-runs-design.md` — D8 (reviewers: cross-family, the fold, convergence,
depth by the change, the reviewer measured), D16 (profile migration, earlier runs), D17 (metrics, the per-task stage
comparison), the contract lines "Reviewer scope" and "No silent substitution", the deletion table, and the stage
table, stage 1.

## Review Focus

1. A snapshot never touches the owner's index or files and includes untracked files: a copy of the real index under
   `GIT_INDEX_FILE`, `add -A`, `write-tree`, `commit-tree -p HEAD`; `--git-path index` is read without
   `GIT_INDEX_FILE`, which it would echo back (Task 2, review-rounds case 5).
2. The cross-family pick: from the ladder's own pick upward, then from the bottom; the author is the ledger task's last
   work attempt, else the run's; an explicit `rung` is never replaced, only marked (Task 2).
3. The attempts cap counts work, not reviews: worker, review, worker, review is two attempts, so the third round is
   reachable under the default cap of 4 (Task 2, review-rounds case 4).
4. An earlier run whose architect delegated a `ui-reviewer` at events schema 2 still reads: the event parses as
   `reviewer` instead of failing the read as corrupt (Task 4).
5. Metrics: idle and concurrency leave pauses out; blocked minutes key on the reply's reason; a run with no `checks`
   rows reads `checkShare: null` unless it is an architect run (Task 6).

## Rulings

Each is `R<n>: what — why — cost if wrong`. They bind every task.

- R1: reviewer severities are `IMPORTANT | NIT | PRE-EXISTING (<bug class>) file:line — problem — input — fix`;
  `BLOCKER` and `BUG` stay readable (the verifier's failing lines are BLOCKERs; earlier runs' reviews are BUGs) — D8's
  scale and its reviewer-scope line — a reviewer on an old habit writing BUG is still parsed, as BUG.
- R2: an IMPORTANT review finding climbs the worker's ladder, as BLOCKER did (plan 49 R4) — it is the only level that
  asks for a fix — more climbs than under BLOCKER only, since IMPORTANT includes what was a BUG.
- R3: a model family is the model id's first name part with the provider dropped (`gpt`, `claude`, `kimi`), not the
  backend — D8 is about the model (Cognition: same-family judges share errors) and the catalog is impure in a
  reducer path — one lab under two prefixes reads as two families (a `shortcut:` comment says so).
- R4: with no `rung`, a review takes the first rung of another family from the ladder's pick upward, then from the
  bottom; with none, the pick, marked `sameFamily`; an explicit `rung` is kept and only marked — O2 and the contract
  line "No silent substitution" — the mark rides `task.delegated`, the digest line and the MR change log.
- R5: the shipped reviewer ladder stays `codex:gpt-6-sol#high`, so a default review of the default (gpt) workers is
  `same-family` — a headless Claude rung in the shipped ladder made a Codex-only machine need Claude Code (doctor and
  three Codex-only doctor tests failed in the scratch) — the owner adds a rung of another family to his profile.
- R6: a re-review reads only `git diff <last snapshot> <this snapshot>`: catherd snapshots the tree when a reviewer is
  delegated (a commit on HEAD that no ref holds, untracked files in, the owner's index untouched) and the next review
  of the same ledger task gets that diff and the earlier findings, numbered, with their handling — stage 1 has one
  shared tree and writers do not commit, so only a snapshot names "the diff since" — a `git gc --prune=now` mid-run
  loses a snapshot; that review then reads the whole tree.
- R7: a review without `ledgerTask` is never a round and never a re-review — rounds are per task (D8) — the architect
  that wants convergence names the ledger task.
- R8: a fourth review on one ledger task since its last ledger edit is refused ("replan it: rewrite its goal or split
  it with ledger") — D8: after three rounds the architect re-plans — editing the task is enough to go on, which the
  architect may do without a real replan.
- R9: D10's attempts cap counts work attempts only (not reviewer, verifier or researcher dispatches) — under the old
  count a worker–review–worker–review sequence hit the default cap of 4 before the third round — a task can now take
  four work attempts plus three reviews.
- R10: one new architect tool, `findings`, logs a review's handling (`fix`, `rejected`, `intentional`,
  `not-worth-it`, `known-issue`) and a missed bug (`missed`); logging is never required — D8 "each finding records how
  the architect handled it" and the eval set — an architect that logs nothing leaves its IMPORTANT findings in Known
  issues as "(no handling logged)".
- R11: Known issues in the MR = ledger tasks impossible or blocked, every PRE-EXISTING finding, every finding logged
  `known-issue`, and every IMPORTANT finding with no handling logged — outcome visible to the owner, no gate — an
  IMPORTANT finding fixed without a log shows as a known issue.
- R12: the reviewer eval set is the `review.missed` events across runs, listed by `catherd runs metrics` with each
  reviewer rung's reviews, findings by severity, handling and misses — D8 "the reviewer is measured" — replaying the
  set against a rung is not built (stage 4, ideas.md).
- R13: depth by the change (a second, cross-family reviewer only for money, auth, migrations or CI), one reviewer per
  call, a disputed finding to the architect after two replies, and "a fix round prefers the change that deletes or
  narrows code" are contract text (architect, reviewer, worker), not mechanism — O2: the architect decides — none.
- R14: `ui-reviewer` leaves `ROLES`, `DEFAULT_ACCESS`, `BUILTIN_ROLES`, `ROLE_NEEDS`, the role prompts, the run graph,

## Edge cases

- A review delegated before a base run's tree exists: `runTree` throws, no snapshot; that review and the next read the
  tree, not a diff.
- A review whose author never ran (no work attempt yet): no family to differ from; the ladder's pick, not marked.
- Two reviews of one ledger task in flight: the second has no ended review to diff from; it reads its own snapshot.
- `findings` with `handled` on a non-review task, or `n` past the review's findings: refused (`E_INPUT_INVALID`).
- `findings {missed}` naming no review: listed under "(no review named)" in the reviewer table.
- A profile with `ui-reviewer` disabled: only the entry is dropped; with no stored reviewer rungs: nothing appended
  (the shipped ladder resolves).
- A `PRE-EXISTING` finding: never climbs, never counts as an unhandled IMPORTANT, always a known issue.
- An earlier 2.0 (milestone) run's metrics: rounds per milestone from `reviewRounds`, check share null, climbs 0.
