## Decisions

- D1 — a mid-stream `aborted` error is recovered when a `text` part follows it and the final reply has a `STATUS:` line; the run then ends `ok` whatever the exit code — rejected: re-dispatching on the same thread after a `failed` stop — the work is done and the reply is complete; a retry only re-reads it (the evidence: 2 min 41 s and a second dispatch for no change). Any other error type, and an abort with no later reply (test/fixtures/adapters/opencode/permission-rejected.jsonl), still fails.
- D2 — the opencode fold's cost is `null` when any step that used tokens carried no positive cost, and settle keeps that `null`; finalize then prices it from the catalog (plan 39 D10) — rejected: trusting opencode's 0 — opencode reports 0 for a model with no configured price, and a price added mid-run left half the steps at 0.
- D3 — the opencode transcript follows the stream shape above: `step_start` → none; `text` → text; shell → shell (exit from `metadata.metadata.exit`, 1 for an errored call with none, else null); edit → file `update` with `files[0].patch`, else a hunk from oldString/newString; write → file `add`, `+` lines capped at 400; an errored edit or write, read and any other tool → tool (`input` as JSON, `output` = output or error, `error` = status is error); `step_finish` → turn only when `reason !== "tool-calls"` (tokens `{input, cached, output}` from `opencodeTokens`, cost when positive else null); `error` → error; anything else → raw — rejected: a turn per step — 258 "turn ended" cards for one dispatch.
- D4 — slack is computed from the run's last `plan.ready` and its `milestone.landed` events, with unit weights (a lane 1, a milestone's gate 1), when the milestone is routed — rejected: weights from task counts or past durations — no field carries them reliably, and the plan DAG's shape is what decides who waits; rejected: passing slack in `RouteRequest` — it would change lane-service.ts and run-effects.ts (plan 40's files) for data the routing service can read from its own `runDir`.
- D5 — the slack rule: a lane with zero slack starts no lower than the role's default rung (by intelligence), except a copy lane, which keeps the cheapest rung that clears copy's bar; a lane with slack starts on the cheapest rung that clears the next easier difficulty's bar; a lane with no slack value (no plan, a 1.x run, a lane added after plan.ready) routes as today — rejected: `objective: speed` for the critical path — speed is tokens per second, and the slow cheap rungs lost on tool calls, not on tokens per second; the copy exception because copy lanes on the cheap rung were also the fastest (2.7 min against 5.0 min each).
- D6 — a chore lane is marked by a header line `Chore: yes` in its lane file, and in a plan's lanes section by the word `chore` after the task list (`- M1.L2 — Task 3 — chore — owns …`); routing starts it on the cheapest capable rung whatever its bar, slack or record, and Jev is not asked — rejected: `Difficulty: chore` — every bar, Jev rule and outcome keyed by difficulty would need a fifth value; the lane keeps its real Kind and Difficulty.
- D7 — the order in decide is chore, slack bar, learned start, critical-path floor; the floor runs last so neither a lowered bar nor a record puts a critical lane below the default rung — rejected: learning before the slack bar — a record says nothing about the critical path's speed.
- D8 — learning is on for every run with no profile key: a cheaper rung is preferred only when both it and the chosen start have at least 5 finished lanes of this difficulty on this machine and the cheaper one is at least as good on first-pass rate and rounds per lane; the why names both records — rejected: a `routing.learn` profile key — `ProfilePatchSchema` is part of the panel API document, so a key regenerates web/openapi.json and the web client (plan 42's files); the relative rule cannot pick a rung with a worse local record. This overrides spec 1.2 §8 ("run evidence never routes") for the learned start, by the owner's acceptance item 6; `runEvidence` stays display only.
- D9 — "first pass" is a lane that landed on its start rung with one dispatch (no retry, no fix round, no capability climb); rounds count every dispatch of the lane; findings count reviewer BLOCKER and BUG findings on files the lane owns — rejected: `start_ok` alone — a lane that needed three fix rounds on its start rung is not a first pass.
- D10 — the summary keys a rung's model and effort apart (`codex:gpt-6.1-sol` `high`) so max and high can be compared later; it reads only daemon runs (with events.jsonl) — rejected: also reading 1.x runs — they have no findings or dispatch events, and a row with zeros would read as a good record.
- D11 — cheap-first fix rounds: a lane armed for a fix whose notes are all mechanical (`mechanicalFix`) runs once on the profile's cheapest capable rung, on a fresh thread; if that dispatch fails, its fast check fails, or one of its findings survives the next review, the lane goes back to its own rung once, and that failure counts toward no climb (`attempts`, `checkFails` and `same-defect` are left as they were) — rejected: a `lane.climbed` down and up the ladder — a ladder only goes up, and routes.jsonl would read the cheap try as the lane's route. NITs never start a fix round today, so the cases that matter are a BUG about convention or lint and a lint or type-check fast-check failure.
- D12 — M22 changes plan 40's run-state.ts, run-machine.ts, run-effects.ts, role-prompts.ts and run-briefs.ts, so it runs in a later run than plan 40, on a base where plan 40 has merged (`After: M21` only) — rejected: M22 beside plan 40 — two plans editing the reducer at once. Its tasks describe behaviour by function name; the worker reads the code as plan 40 left it.
- D13 — no new event: `cheapFirst` and `cheapRan` are derived in the reducer from `dispatch.started` (its `rung` against `l.rung`), `check.ran`, `dispatch.ended` and the fix round, so a replay gives the same state — rejected: a `lane.cheapened` event — the facts are already in the log.

## Edge cases

- An abort followed only by tool calls and no text: not recovered, failed as today.
- An abort, a reply with no STATUS line: failed as today.
- A recovered abort whose reply is `STATUS: blocked`: status ok; the reply's own status decides the lane, as for any ok run.
- An opencode run with no step_finish at all: `costUsd` stays null only when a step used tokens; no steps → 0 as today.
- A free model priced 0 in the catalog too: null from the adapter, $0 from finalize's catalog price.
- An opencode line with an unknown `type`, or a tool_use with no `state`: one raw item, never a throw.
- A write longer than 400 lines: the diff keeps the first 400.
- A lane added by an architect delta after plan.ready: no slack value, routed as today.
- A plan with one milestone and one lane: slack 0; a copy lane keeps its cheap start.
- Every lane of a run on the critical path (a chain): only chore and copy lanes start below the default rung.
- A profile with no default rung: the critical-path floor is the cheapest candidate, so it moves nothing.
- A chore lane on a role with one rung: that rung.
- A chore lane's outcomes: kept in the summary with `chore`, left out of learning.
- Outcome records from another repo on the same machine: counted (the summary is machine-wide, as run evidence is).
- A start rung with fewer than 5 finished lanes: nothing is learned.
- A cheap fix whose cheapest rung equals the lane's rung: `cheapRan` false; the dispatch is an ordinary fix.
- A cheap try that hits a usage limit: failover moves it as any dispatch; it still counts as the cheap try.
- A fast-check note whose tail mixes a type error and a failing test: not mechanical.
- A replay of a run recorded before plan 41: no `cheap` actions owed, both fields false.
