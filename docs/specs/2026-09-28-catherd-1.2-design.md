# catherd 1.2 — scores and catalog from public sources

Status: approved by the owner 2026-09-28. Builds on the 1.1 spec (`2026-09-28-catherd-1.1-design.md`) and the 1.0
spec, which stay binding where this one is silent. Research and the curl evidence behind every source are in
`docs/dev/ideas.md`, section "Scores and catalog from public sources (2026-09-27)".

## 1. Why

Scores and model facts are typed by hand in `catalog/scores.json` and `catalog/models.json`. A release such as
2026-09-22 (Opus 5.5, GPT-6 Sol/Luna/Astra) leaves every new rung unscored until someone reads blog posts, and each
unscored rung needs a hand `treat-like`. Those hand mappings then break profiles: on 2026-09-28, clearing three of them
made the owner's profile invalid, and no `profile set` could repair it, because each save validates the whole profile.

Routing is also nearly blind today. Every kind × difficulty shares one bar, `repo_code ≥ 55`, plus `honesty ≥ 90` on
logic and hard; the `terminal` kind has no terminal bar at all. So Jev's kind judgement barely changes which rung runs.

Success: when a vendor ships a model, nobody types a number; no profile ever becomes invalid because a rung lacks a
score; and a lane's kind changes which rung it gets.

## 2. Scope

In 1.2:

1. Source sync: seven keyless sources, one optional keyed source (Artificial Analysis), a 12 h cache (§3).
2. Calibration onto each dimension's anchor unit, and a six-level confidence (§4).
3. Three new dimensions and default bars per kind × difficulty that use them (§5).
4. Unscored rungs are a warning with an automatic inferred stand-in, never an error; profile repair; `treat-like
   --suggest|--clear|--reset` (§6).
5. The shipped `scores.json` carries the keyless sources' values with attribution, refreshed by a weekly workflow (§7).
6. Evidence from catherd's own runs, shown per rung and kind, not used for routing (§8).
7. `doctor`, `init`, TUI and MCP surfaces (§9).

Out of scope: BFCL, LiveBench and Design Arena (data exists, no endpoint pinned; a later spike); run evidence
changing routing (1.3, once there is data); weighted composite scores (bars stay per-dimension thresholds that must
all clear).

## 3. Sources and the sync

### 3.1 Sources

Keyless, always on:

| Source | Endpoint | Used for | License |
|---|---|---|---|
| models.dev | `GET https://models.dev/api.json` | efforts, context, output limit, price, tool calling, modalities, release date | MIT |
| OpenRouter models | `GET https://openrouter.ai/api/v1/models` | price and context cross-check; day-one presence | public API |
| OpenRouter endpoints | `GET https://openrouter.ai/api/v1/models/{author}/{slug}/endpoints` | latency and throughput facts | public API |
| LiteLLM | `GET https://raw.githubusercontent.com/BerriAI/litellm/main/model_prices_and_context_window.json` | price and effort support cross-check | MIT |
| Arena (LMArena) | `GET https://datasets-server.huggingface.co/rows?dataset=lmarena-ai/leaderboard-dataset&config=<c>&split=latest&length=100` for configs `agent`, `agent_task_outcome_explicit`, `agent_bash_recovery_steps`, `agent_steerability`, `agent_tool_hallucination`, `webdev` | agentic, steer, frontend, honesty | CC-BY-4.0 |
| Vectara hallucination | `GET https://raw.githubusercontent.com/vectara/hallucination-leaderboard/main/README.md` (markdown table) | honesty | Apache-2.0 |
| Epoch AI | `GET https://epoch.ai/data/benchmark_data.zip` (CSV per benchmark) | repo_code (FrontierCode), terminal, frontend (WebDev) | CC-BY; external tables keep their own license |

Keyed, optional:

| Source | Endpoint | Used for | Terms |
|---|---|---|---|
| Artificial Analysis | `GET https://artificialanalysis.ai/api/v2/data/llms/models`, header `x-api-key` (one row per effort) | terminal, repo_code, agentic (all calibrated), speed, cost per task, and the similarity features of §6.3 | free key, 100 requests/day, internal use, attribution |
| same, fallback | `GET https://artificialanalysis.ai/api/v2/language/models/free?page=N` | used when the first path answers 403 or 404 | same |

AA values are read with the user's own key and never shipped (§7).

### 3.2 When it runs

- **Background, at MCP server boot.** The plugin's MCP server starts with each Claude Code session; its boot starts
  the sync without awaiting it. The handshake and the first tool call never wait on the network.
- **TTL.** One TTL for every source, 12 hours: a source is fetched only when its cached file is older. A lock file in
  `<data>/sources/` stops two sessions opened together from fetching twice. AA costs 2 requests a day (10 on the
  fallback path).
- **On demand.** `catherd catalog sync [--force]` runs it in the foreground (`--force` ignores the TTL); `init` runs
  it; the MCP tool `catalog_sync` runs it from a session and returns what changed; the TUI's profiles view gets an `r`
  key that runs it and shows each source's age and last error.
- **Mid-run.** `route` reads whatever is cached when it is called. A sync that lands mid-run is picked up by the next
  `route`.

### 3.3 Fetching and caching

- All sources in parallel, with the Jev client's retry policy and one timeout per source. Requests honour
  `HTTPS_PROXY`/`HTTP_PROXY` like every other catherd request.
- Each raw answer is written atomically to `<data>/sources/<source>.json` with its fetch time. A source that fails
  keeps its last good file; the sync records the error and goes on. A failed background sync logs at debug level.
- Parsers live one per source in `src/infra/sources/<source>.ts` and return rows `{ rung, field, value, date, url }`.

### 3.4 Id and effort mapping

- Ids: lowercase, `.` → `-` (`gpt-5.6-sol` → `gpt-5-6-sol`), then an alias table in `catalog/sources.json` for the
  irregular ones (AA `claude-4-5-haiku` → `claude-haiku-4-5`).
- Effort: the AA slug suffix (none means `max`), Arena's `(Max)`/`(xHigh)`/`(High)`, Epoch's `_max`-style suffix. A
  model with no effort in its name maps to the family's default effort and the value is marked `effortAssumed: true`.
- An unmatched id is never guessed. `catherd catalog sync --unmatched` lists them.

### 3.5 Catalog facts

models.dev fills `efforts`, `context`, `price` and capabilities for families on the user's backends. OpenRouter and
LiteLLM only cross-check: a price that differs by more than 10 % is a sync warning. The shipped `models.json` stays
the floor, and the backend's own listing still decides what is callable.

## 4. Calibration and confidence

### 4.1 Dimensions and anchors

| Dim | Anchor (the unit its bars are in) | Other sources, calibrated onto the anchor |
|---|---|---|
| `repo_code` | shipped DeepSWE values | AA `livecodebench`, `scicode`, coding index; Epoch FrontierCode |
| `terminal` | Epoch `terminalbench_external` | AA `terminalbench_v2_1` |
| `honesty` | shipped Broken Search Tool values | Vectara factual consistency; Arena `agent_tool_hallucination` |
| `agentic` (new) | Arena `agent` net improvement | Arena task outcome and bash recovery; AA `tau2` |
| `steer` (new) | Arena `agent_steerability` | none |
| `frontend` (new) | Arena `webdev` | Epoch WebDev |
| `speed` (fact) | AA output tokens/s, time to first token | OpenRouter latency and throughput |
| `cost` (fact) | models.dev price | AA `cost_per_task` |

`speed` and `cost` are facts shown by `route`, `catalog list` and the TUI; they never carry a bar.

Every anchor is a keyless source, because the shipped bars are derived in CI without an AA key (§7). AA values are
always calibrated onto an anchor, never used as one.

### 4.2 Calibration

A value from a non-anchor source is never compared with a bar raw. On the rungs both sources cover, catherd fits
`anchor = a·x + b` by least squares. A source needs at least 5 shared rungs for a dimension, else it is not used for
that dimension. Fits are stored with their R² in `<data>/sources/calibration.json`; a fit with R² < 0.5 is not used. A
calibrated value carries its source and the fit.

### 4.3 Confidence and precedence

`Score.confidence` becomes, best first:

1. `verified`: a vendor or the benchmark's official source.
2. `measured`: an independent source for this exact rung, in the anchor unit.
3. `calibrated`: an independent source for this rung, mapped onto the anchor.
4. `adjacent`: the same model at another effort, from any source.
5. `secondary`: as today.
6. `inferred`: a stand-in (§6).

Rules:

- The user's override (`catalog.override.json`) always wins, as today.
- Between two values at the same level, the newer `date` wins.
- A value older than 90 days drops one level.
- Every value keeps `benchmark`, `version`, `url`, `date` and its source, so `route` and the TUI can say where a
  number came from.

The 1.0 schema's three levels map onto the new enum unchanged (`verified`, `secondary`, `inferred`), so existing
override files stay valid.

## 5. Dimensions and bars

### 5.1 Bars span several dimensions

`DIMS` grows to `repo_code, terminal, honesty, agentic, steer, frontend`. A bar is still a set of per-dimension
thresholds, and a rung clears a kind × difficulty only when it clears every threshold in it. Default bars:

| Kind | copy / build | logic / hard |
|---|---|---|
| `repo_code` | repo_code | repo_code, honesty, agentic |
| `terminal` | terminal | terminal, honesty, agentic |
| `ui` | frontend, repo_code | frontend, repo_code, honesty, agentic |
| `prose` | repo_code | repo_code, honesty |
| `research` | repo_code | repo_code, honesty |

`steer` ships with no default bar; it is shown and may be set in a profile.

### 5.2 Bar values

Bar values are derived at release from the day's data and written into `scores.json` with a `barsWhy` line each:

- `copy`: the 25th percentile of scored rungs on that dimension.
- `build`: the median.
- `logic`: the 60th percentile.
- `hard`: the 75th percentile.

Percentiles are taken over rungs whose value is `measured` or better. A profile overrides any threshold through the
existing `bars` path, and `null` removes it.

### 5.3 Routing changes

`route` is unchanged in its method (the cheapest enabled rung that clears the bar, under the profile's objective). It
now reports, for the chosen rung, each threshold, the value used, its confidence and source, and marks any `inferred`
value.

## 6. Unscored rungs

### 6.1 A warning, never an error

An enabled rung with no value on a dimension its bars need is a validation **warning**, not an error. The rung uses
its best stand-in (§6.3) as `inferred`, and `profile validate` and `doctor` list each such rung as "stand-in to
confirm". A run never stops because a rung is unscored.

The existing error "an unscored rung without a treat-like" is removed. A failover stand-in that is unscored becomes a
warning on the same terms.

### 6.2 Repairing a profile

A profile save goes through when it removes at least one error and adds none, even if errors remain. The result lists
the errors still open. This applies to `catherd profile set`, `profile_set` and the TUI's save.

### 6.3 Suggesting a stand-in

- For each unscored rung, catherd ranks scored rungs by similarity on the features every source has for new models: AA
  intelligence index, `hle`, `scicode`, `lcr`, `cost_per_task`, tokens/s, models.dev price and context, and same vendor
  and family.
- The distance is a z-scored Euclidean distance over the features both rungs have. A pair sharing fewer than 3
  features is not suggested.
- Without an AA key, the features are price, context, release date, vendor and family, plus any Arena or Epoch value.

### 6.4 treat-like

`catherd catalog treat-like` gains:

- `--suggest <rung>`: prints the top 3 stand-ins with their distance and the features they rest on.
- `--clear <rung>`: removes the user's mapping.
- `--reset`: removes every user mapping.

The TUI's treat-like picker opens with the same top 3 first. A user's pick is written to `catalog.override.json` as
today, marked `source: "user"`.

Before a mapping is removed, catherd names the profile rungs it leaves on an inferred stand-in.

When a later sync brings real data for a rung that has a user mapping, the sync reports "stand-in no longer needed".
A user's mapping is never removed silently.

## 7. Shipped scores and the weekly refresh

- `catalog/scores.json` carries the keyless sources' values at release time, with their source, date and confidence.
  Values that come from AA are never shipped.
- `catalog/ATTRIBUTION.md` names each shipped source, its license and the attribution line it requires. It is
  included in the npm package.
- The runtime sync layers on top of the shipped values. First run, offline machines, CI and cloud sandboxes without
  network therefore still route on real data.
- `.github/workflows/catalog-refresh.yml` runs weekly (and on `workflow_dispatch`). It runs `catalog sync` with no
  AA key and rebuilds the shipped values and the bars. If anything changed, it opens or updates a PR titled
  `chore(catalog): refresh scores` with a patch changeset. The PR body lists the rungs newly scored, the values that
  moved by more than 5 %, and every bar that moved. Merging it releases a patch through the existing Release workflow.

## 8. Evidence from catherd's own runs

For each rung and kind, catherd counts lanes, climbs, `partial`/`blocked`/`refused` replies and verifier FAILs from
the run records of every repo on this machine. `route`, `catalog list` and the TUI's rung detail show it, for example
"12 lanes, 2 climbed, 1 partial". It does not change scores, bars or routing in 1.2.

## 9. Surfaces

- **init.** After the Jev step: `ARTIFICIAL_ANALYSIS_API_KEY` in the env wins, else the saved key, else a prompt
  (Enter skips). The key is tested with one request to `/language/models/free?page=1`: a 200 saves it, a 401 does
  not, and neither stops `init`. Then `init` runs a foreground sync.
- **Credentials.** The key is saved in `credentials.json` as `artificialAnalysisApiKey`, mode 600. The env name joins
  `SECRET_ENV`, so workers never see it and logs redact it.
- **doctor.** A `sources` row shows each source's age and last error, the AA key presence and requests left today
  (`x-ratelimit-remaining`), and the stand-ins to confirm.
- **MCP.** A `catalog_sync` tool (26 tools in total) returns rungs newly scored, stand-ins no longer needed, and the
  sources that failed. `catalog_query` and `route` show confidence, source and run evidence.
- **CLI.** `catherd catalog sync [--force] [--unmatched]`; `treat-like --suggest|--clear|--reset`.
- **TUI.** An `r` key in the profiles view syncs and shows source ages; the treat-like picker lists suggestions first;
  the rung detail shows values with confidence, source and run evidence.

## 10. Where it lives

- `src/infra/sources/<source>.ts`: fetchers and parsers.
- `src/services/source-sync.ts`: fetch, cache, lock, id mapping, calibration, merge into `catalog-service.ts`.
- `src/services/standins.ts`: similarity ranking.
- `src/services/run-evidence.ts`: the §8 counts.
- `src/domain/catalog.ts`: new `DIMS`, the confidence enum and `RANK`, the value provenance fields.
- `src/domain/profile-rules.ts`: unscored becomes a warning; the repair rule of §6.2.
- `src/entry/init-command.ts`, `catalog-command.ts`, `entry/mcp/`, `entry/tui/`: the surfaces in §9.
- `catalog/sources.json` (aliases, sources, licenses), `catalog/ATTRIBUTION.md`,
  `.github/workflows/catalog-refresh.yml`.

## 11. Testing and acceptance

Tests:

- One recorded fixture per source, parsed; no test reaches the network.
- The id and effort mapping table, including the unmatched list.
- Calibration: a fit from five or more shared rungs, a rejected source below five or below R² 0.5.
- Precedence: the override wins, a newer date wins at the same level, the 90-day drop.
- Stand-in ranking on the 2026-09-27 fixture data. On that day Opus 5.5 has no coding or terminal value in any source,
  so it must get a stand-in.
- Profile repair: a save that removes one of two errors goes through; one that adds an error does not.
- Offline: with no network and no cache, routing uses the shipped values.
- The background sync never delays the MCP handshake.

Acceptance, run by the owner on 1.2.0:

1. On a fresh `init` with and without an AA key, `doctor` shows every source fresh.
2. Clearing every user treat-like leaves the profile valid, with warnings.
3. A `route` for a `terminal` lane and a `ui` lane picks by the terminal and frontend bars and shows each value's
   source.
4. The first weekly refresh PR opens with a readable change list.
