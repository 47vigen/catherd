# catherd 1.1 — design

Date: 2026-09-28. Status: decisions approved by the owner in three grilling rounds on 2026-09-28; this document awaits
the owner's review of the written text.
Builds on `docs/specs/2026-09-25-catherd-1.0-design.md`. Everything there that this document does not change still
holds. Authority order for 1.1 work: this spec → the 1.0 spec → the plan → rulings.

Evidence behind every item: `docs/dev/reports/2026-09-27-auth-build.md` (five 0.2.1 runs, 16 MRs), and the 1.0.0
sections of `docs/dev/ideas.md` (fresh install, headless test, platform run). Model scores from public sources are
**not** in 1.1; they are 1.2.0 (`ideas.md`, "Scores and catalog from public sources").

## 1. Why 1.1

1.0 fixed serial dispatch, but real use on 2026-09-27/28 showed:

- **`wait` freezes the main thread.** An MCP call does not background, so the session blocks until the lanes finish;
  the user cannot even ask how it is going. Two roles ran side by side, but the orchestrator could do nothing else.
- **The protocol is optional.** In a 5-minute headless run with no compaction, `route` ran for 1 lane of 4, no
  reviewer and no verifier ran, and every reply had `replyStatus: null`. The orchestrator wrote `Kind: code` and
  `Difficulty: easy`, values the catalog does not know, so routing fell back to the default rung.
- **Workers cannot run their checks.** The Codex `workspace-write` sandbox denies the network, loopback ports, the
  Docker socket and the lock dir. In the auth build 60 of 171 replies were `partial`/`blocked` for this, and the Opus
  main thread ran 156 Go test commands itself.
- **The verifier is the bottleneck.** In auth plan 5 MR A, workers and reviewer took about 9 min and the verifier about
  85 min: gate items run one after another, unchanged checks rerun, an image is built twice, and `status` cannot show
  where the verifier is.
- **One owner question stops everything** (4.5 h in the auth build).
- **Setup breaks.** The plugin does not install without GitHub SSH (`git-subdir` shorthand URL), and the MCP server
  dies when macOS half-cleans the bunx folder in `$TMPDIR` (seen in 0.2.1 and 1.0.0).
- **The runs page lists runs flat.** One `/catherd` job (the whole auth build) became several runs; the user wants to
  open the session that drove the job and watch everything in it, live.

## 2. Scope

In 1.1.0 (one minor release):

1. Push results to the main thread over the Claude Code peer inbox; remove `wait`; add `peek` (§3).
2. Sessions as a first-class grouping; the runs page by session, live (§4).
3. Worker access that can run real checks (§5).
4. The protocol enforced by the tools: routing, the reply contract, lane headers, review and verification before
   `land` (§6).
5. A faster, visible verifier: a gate ledger and step reporting (§7).
6. `park`/`answer` for owner questions (§8).
7. Climb only for capability (§9).
8. Protocol re-entry after compaction and a per-milestone digest (§10).
9. Failover and profile validation fixes (§11).
10. Install and launch: the plugin source URL, a stable MCP launcher, `doctor` probes (§12).
11. Small items (§13).

Out of 1.1: model scores from public sources (1.2.0); a branch and MR per milestone and stacked milestones (1.2.0);
batch `route`, Jev hit-rate review, race mode, automatic retro, `catherd bench`, standalone binaries, first-turn cost
(remain ideas); Cursor and Grok adapters (held by the owner).

## 3. Push results to the main thread

### 3.1 Facts it rests on (verified in the Claude Code 2.1.283 binary, 2026-09-28)

- Every live session registers an inbox: `~/.claude/sessions/<pid>.json` (`sessionId`, `name`, `hostSessionId`,
  `messagingSocketPath`, `status`) and a Unix socket. A frame is two JSON lines: `{"type":"auth","token":…}` then
  `{"msgV":1,"msg_id":<uuid>,"type":"user","message":{"role":"user","content":"<cross-session-message …>\n…\n</cross-session-message>"},"priority":…}`.
- MCP servers and their children get `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_MESSAGING_SOCKET` and
  `CLAUDE_CODE_MESSAGING_TOKEN` in their environment, and `CLAUDE_CODE_HOST_SESSION_ID` when a host (Desktop) set it.
  The session id there goes stale after `/clear`; the session file holds the live one.
- **Self-sent rule.** With no `crossSessionInbound` setting, a receiver accepts a message whose sender process has
  the session's pid among its ancestors (macOS: a `ps -o ppid=` walk, 10 levels, 32 on retry; Linux: a `/proc` walk,
  12 levels, from the socket's peer pid). The MCP server is a direct child of the session, so its messages pass. A
  detached process reparented to launchd or init does not. (Corrected by plan 10's spike,
  `docs/research/2026-09-28-cross-session-messaging.md`.)
- `priority`: `later` waits for the receiver's turn to end (native background-task notices use it), `next` drains at
  the next tool round (immediately when idle), `now` aborts the running turn.
- The envelope attributes must re-serialise byte for byte, in the order from, from-session, hop-chain, from-name,
  from-mode, from-plugin. A sender may declare `from-mode="bypass|prompting"`; a matching receiver accepts it.
- This protocol is undocumented and can change in any Claude Code release (see §3.9).

Reference: agora's `.workspace/references/claude-code-cross-session-messaging.md`; the plan copies the facts it needs
into `docs/research/2026-09-28-cross-session-messaging.md` so the repo stands alone.

### 3.2 Principles

- **Disk stays the source of truth.** The supervisor writes `exit.json`; finalize writes the record; the `collect`
  marker still means "not yet read". A message only announces that a record exists. A lost message loses nothing.
- **The MCP server is the only sender.** It is the session's child, so it passes the self-sent rule without any
  setting. The supervisor never sends.
- **Only non-native roles notify through catherd.** Native Claude roles (architect, verifier) are Claude Code
  subagents and keep their own notices.

### 3.3 Session identity and run ownership

- At start the MCP server reads `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_HOST_SESSION_ID`,
  `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` into `deps.session` (all optional; absent outside
  Claude Code). Its display name comes from the matching `~/.claude/sessions/*.json` (`name`), read live when needed.
- `run_start` writes the session into `meta.json`: `startedBy: {sessionId, hostSessionId, name}` (additive, the meta
  schema is loose).
- Each run has one **owner session** at a time, in `state.json` (`owner: {sessionId, since}`). `run_start`,
  `dispatch` and `peek` on a run set the owner to the calling session when it differs, and append
  `{sessionId, hostSessionId, name, at}` to `R/sessions.jsonl`. That is how a run "moves" when it is continued from
  another session.
- `admit.json` gains `sessionId` (the dispatching session). Records copy it.

### 3.4 Delivery

- A new `infra/peer-inbox.ts` writes one frame to a socket path with a token and closes after 150 ms. It never throws
  into callers: it returns `sent | no-session | refused | error` with a reason.
- A new `services/notifier.ts`, run only inside the MCP server:
  - Watches, for every run whose owner is this server's session, the dispatches it knows (the existing finalize
    watcher already sees each dispatch finish; the notifier hooks the same point, plus a scan on start).
  - When a dispatch is finalized and still has its `collect` marker, it queues a notice. Notices that arrive within
    3 s of each other for the same session are sent as one message.
  - After a send returns `sent`, it writes `notified` (the message id and time) in the dispatch folder, so a restart
    does not send it twice. The `collect` marker stays until a tool reads the record (§3.6).
  - On start, it sends one message for records of owned runs that are finalized, still marked `collect` and not yet
    `notified` (for example, workers that finished while Claude Code was restarting).
  - With no session env, or when the socket is gone, notices are not sent; the records wait for `peek`/`run_start`.
- **Failover moves here.** Today only `wait` fails a limited role over. In 1.1 the notifier runs the same `failover()`
  as soon as a record has status `limit`, before notifying. The notice says what happened ("limit on X; failed over
  to Y", or "paused: no stand-in").

### 3.5 The message

Envelope `<cross-session-message from-name="catherd">`, no `from` (the server has no reply address). Body:

```
catherd · <run title> · <name> <role> · <rung> · <status> · <STATUS or "no STATUS"> · <secs> · <n> owned files changed
<the worker's reply, capped at 2,000 characters, cut on a line boundary, "…(cut; result(run, name) has the rest)">
Record: result(run: "<run id>", name: "<name>")
```

- The first line stands alone: the Desktop preview shows only it.
- Several roles in one message: one header block per role, separated by a blank line; the preview line becomes
  `catherd · <run title> · 3 roles finished: M1.L1 ok, M1.L2 ok, M1.L3 limit`.
- Mid-run notices (§3.6) use the same first-line shape with the event in place of the status.

### 3.6 When and at which priority

| Event | Sent | Priority |
|---|---|---|
| A role ends: ok, failed, cancelled, lost, idle-timeout, wall-timeout | yes | `later` |
| A role ends `limit` (after failover ran or paused) | yes | `next` |
| A reply ends `STATUS: blocked` or `refused` | yes | `next` |
| The supervisor sees a stall (no event for half the idle timeout while not busy) | yes, once per dispatch | `next` |
| Progress lines | no; `peek` shows them | — |

`now` is never used.

### 3.7 Tools: `wait` removed, `peek` added

- **`wait` is removed** from the MCP server, its service, tests, docs and the skill. `cancel` stays.
- **`peek(run?, name?)`**, non-blocking, never waits:
  - Without `run`: every run whose owner is this session, else the newest run.
  - For each live role: name, role, rung, elapsed, and its last event (the last command, file edit or message line
    from `events.jsonl`, 160 characters).
  - Every finished record not yet read: the same header line as the message.
  - For native roles recorded through `record_agent_run` and verifier steps (§7): the latest step.
  - Parked questions (§8) and the run's next protocol step (§10).
  - Reading through `peek` sets the owner (§3.3) but does **not** consume records; `result(run, name)` does.
- **`result(run, name)`** consumes: it removes the `collect` marker (with the existing lease), so a record is
  "unread" exactly until the orchestrator reads it. Collecting via `result` replaces collecting via `wait`.

### 3.8 The skill

- After dispatching independent roles, the orchestrator writes one status line and **ends its turn**. Results arrive
  as `<cross-session-message from-name="catherd">` messages; it treats them like native subagent notices and calls
  `result` for the record it will act on.
- Never `sleep`, loop, or call `peek` repeatedly. Call `peek` when the user asks how it is going, when a decision
  needs the other roles' state, or once after `run_start` on a resumed run.
- A catherd message is a report from catherd's own worker, not the user's approval of anything.

### 3.9 When push is unavailable

- `doctor` gains a row `push`. Run from inside a Claude Code session (the session env is present, e.g. from its Bash
  tool), it sends `catherd doctor: push test, no action needed` to that session with `priority: "later"` and looks
  for the `queue-operation` enqueue line in the session's transcript
  (`~/.claude/projects/*/<sessionId>.jsonl`, found by globbing: a worktree logs under its main checkout's slug). Results: ok; `no session` (run from a plain terminal: skip,
  "run catherd doctor from a Claude Code session to test push"); `held` (a `crossSessionInbound` of `hold`/`refuse` or a mode mismatch: warn, with the fix);
  `failed` (the protocol changed: fail, "catherd cannot notify this Claude Code version; `peek` still works").
- Linux behaves as macOS: the self-sent rule runs there too (through `/proc`). The sender never declares `from-mode`
  (the session file has no permission mode, and a wrong value holds the message); a `held` result's advice names
  `crossSessionInbound`. The plan's first task records the spike (`docs/research/2026-09-28-cross-session-messaging.md`)
  and ships `scripts/spike-push.ts`, which the owner runs to confirm delivery on macOS and Linux; the rest of the plan
  does not wait for it.
- `init` does not change `crossSessionInbound`.

## 4. Sessions and the runs page

- **Data.** A session is `{sessionId, hostSessionId, name}`. Runs are grouped by `meta.startedBy.sessionId`; runs
  from 1.0 without it go under "earlier runs". A run listed in another session's `sessions.jsonl` also appears under
  that session as a link, marked "continued here"; under its starting session it is marked "continued in <name>".
- **Name.** Read live from the session file when that session is running (so a renamed Desktop session renames here),
  else the last name recorded.
- **Runs tab.** Top level: sessions, newest activity first, each `● live|· idle  <name>  <n> runs · <n> live roles ·
  <n> landed  <ago>`. Opening a session shows, on one screen: its runs (newest first), each run's milestones (from the
  ledger and plan), and every role with rung, status, elapsed and last event, live ones first. Opening a role shows
  its brief, reply and record. Esc goes back one level.
- **Live.** The open screen redraws when a run file changes (`fs.watch` on the run folders involved, falling back to
  the current 1 s poll where watching fails); live elapsed times tick every second. `p` still pauses.
- `catherd runs list` and `status` group by session the same way (`--json` gains `session`).
- `docs/tui-frames.md` and its stories cover: empty, one session with two runs (one continued elsewhere), a live
  session with three live roles, a role opened.

## 5. Worker access

- **Intent**, for roles with `workspace-write` access (worker, writer, artist by default): write the repo; read the
  disk; outbound network; loopback bind; write the lock dir (`<data>/locks`) and the temp dir; talk to a local Docker
  socket. Everything else stays closed. `read-only` and `full` are unchanged.
- **Codex:** add to `plan()` for `workspace-write`: `-c sandbox_workspace_write.network_access=true` and
  `-c sandbox_workspace_write.writable_roots=[<locks dir>, <real TMPDIR>]` (for `exec` and `exec resume` alike, and in
  isolated mode). Verified 2026-09-28 on Codex 0.157: lock-dir write, `docker ps` over the OrbStack socket, a loopback
  `bind()`, an HTTPS fetch and a `/tmp` write all pass.
- **opencode and headless Claude Code:** the same intent through their own mechanisms (opencode's agent permissions
  and the environment it runs shell commands in; Claude Code's `--allowedTools`/settings). The plan's research task
  pins each down against the installed versions; where a backend cannot express part of the intent, `doctor` says
  which probe fails for it.
- **Profile:** a new optional field `roles.<role>.network: false` removes the network and loopback grants for that
  role (Codex: no `network_access`).
- **`doctor`** runs five probes per backend used by a `workspace-write` role, with the exact flags workers get:
  lock-dir write, temp write, loopback bind, outbound HTTPS (to the npm registry, honouring `HTTPS_PROXY`), and
  `docker version` when Docker is installed. Rows `access:<backend>` report each failure with its fix.

## 6. The protocol, enforced by the tools

- **Lane headers.** `preflight`, `route` and `dispatch` (with a `lane`) parse the five header lines and refuse a lane
  whose `Kind:` or `Difficulty:` is not in the catalog's enums (`E_LANE_INVALID`, the fix lists the allowed values:
  kinds `repo_code|terminal|ui|prose|research`, difficulties `copy|build|logic|hard`).
- **Routing.** `dispatch` with a `lane` whose lane has no `routes.jsonl` entry routes it first (same as calling
  `route`) and uses the routed start rung when the caller's rung is not on the routed ladder, with a hint. `route` stays
  callable.
- **Reply contract.** `dispatch` appends the role's reply contract to every brief it writes (the tail of the matching
  `rolePrompt`: reply length, `STATUS: complete|partial|blocked|refused — <why>` as the last line). The skill no longer
  asks the orchestrator to write it. Failover stand-in briefs get it too.
- **`land` gate.** `land(run, milestone, …, skip?)` refuses a milestone unless the run has, since the milestone's
  lanes started:
  - a reviewer record for it (a dispatch whose name starts `reviewer-<milestone>` with status ok), and
  - a verifier verdict: an `agents.jsonl` row from `record_agent_run` with role `verifier` and a name containing the
    milestone, status ok.
  - `skip: "docs-only"` is accepted only when every file changed in the milestone's commit range is under `docs/`,
    `*.md` or the repo's configured docs paths; `skip: "no-code"` only when no file under the repo's source roots
    changed and the caller gives evidence (e.g. a green pipeline). Refusals use `E_LAND_GATE` with the missing piece
    and the fix.

## 7. The verifier

- **Brief.** The verifier's role prompt and the skill say: run independent gate items side by side, within the lock's
  slots (`catherd lock` already queues); build each commit's images once and reuse them for the boot check and the
  acceptance suite; report each step.
- **Gate ledger** (`<data>/repos/<repo key>/gates.jsonl`, next to `knowledge.md`). Two tools:
  - `gate_check(run, item, command, paths)` → `{carried: true, passedAt, commit}` when a pass exists in this repo
    with the same `command` and the same content hash of `paths` (git tree hashes of those paths at HEAD), and none of
    `paths` is changed in the current milestone's diff; else `{carried: false}`. Calling it also records "verifier
    step: <item>" for `peek`/`status`.
  - `gate_pass(run, item, command, paths, evidence)` records a pass with the hash, commit and time.
- The verifier reports a carried item as "carried over from <commit>" in its verdict. `land` accepts carried items as
  part of the verdict.

## 8. Owner questions: `park` and `answer`

- `park(run, milestone, question)`: marks the milestone parked in `state.json`, appends to `R/questions.jsonl`, sets
  state.md's next to include "parked: M2 waits on the owner", and returns a hint telling the orchestrator to push the
  full question (the skill sends `PushNotification` with it) and continue with the milestones and runs that do not
  depend on it.
- `answer(run, milestone, answer)`: records the answer and unparks. The owner answers in the main session; the
  orchestrator calls `answer`.
- `run_start` (on resume), `peek` and `status` list unanswered questions first.

## 9. Climb only for capability

`climb(run, lane, reason, evidence)` first asks Jev the existing `finding` question on the evidence (when Jev is on).
When the answer is `design` (plan contradiction, file ownership outside the lane, a cross-lane interface), `climb`
refuses with `E_CLIMB_DESIGN` and the fix "send it to the architect (ask/architect delta), not up the ladder". With Jev
off it climbs as today. `reason: "blocked"` evidence mentioning ownership ("outside lane ownership", "owned by") is
refused the same way without Jev.

## 10. Re-entry after compaction; the milestone digest

- `state.md` always ends with `Protocol next: <step>`, derived from the run's state: e.g. "route and preflight M2's
  lanes", "dispatch M2.L1–L3", "M2: reviewer", "M2: verifier", "land M2", "M2 parked". `run_start` and `peek` return
  the same line plus a six-line checklist of the milestone loop.
- **Digest.** `land` writes `R/digests/<milestone>.md`: A-lines touched, commits, lanes with rung and climbs, reviewer
  findings count, the verifier's verdict with carried items, minutes and tokens. The milestone push links it; the runs
  page shows it when a milestone is opened.

## 11. Failover and profile validation

- **Default failover** (`DEFAULT_FAILOVER`) maps each shipped worker rung to a stand-in that clears the same bars as
  the rung; a rung with no such stand-in has none. Claude-billed rungs rank last as stand-ins.
- **`validate`** warns (never errors) when:
  - a stand-in scores below its rung on a dim the rung's bars use ("downgrade: X stands in for Y");
  - a stand-in bills to the Claude plan while another backend could stand in ("spends Claude quota");
  - a ladder's rung scores below the rung before it ("the ladder goes down at X").
- **Labels.** `profile show` and the TUI say "scores borrowed from X" instead of "inferred: treated like X", and show
  it only when the stand-in's own scores are missing.

## 12. Install and launch

- **Plugin source.** `.claude-plugin/marketplace.json` uses `"url": "https://github.com/47vigen/catherd.git"` (keeping
  `path` and the stamped `ref`), so installs work without GitHub SSH. `stamp-plugin-version.mjs` keeps stamping `ref`.
- **MCP launcher.** `plugin/.mcp.json` runs `plugin/bin/catherd-mcp` (a POSIX `sh` script, stamped with the version):
  if `catherd --version` prints the stamped version, `exec catherd mcp`; else `exec bunx catherd-cli@<version> mcp`
  with `TMPDIR` set to `${XDG_CACHE_HOME:-$HOME/.cache}/catherd/bunx` so macOS never half-cleans it.
- **`init`** installs the global CLI at its own version (`bun add -g catherd-cli@<version>`, skippable with
  `--no-global`) and says "installing catherd…" before any resolve it triggers.
- **`doctor`**:
  - `sandbox:codex` uses `codex sandbox [--config …] -- <cmd>` (the current CLI), falling back to the old
    `codex sandbox <os> --full-auto` form; the five probes of §5 replace the lock-dir-only probe.
  - `mcp` starts the server the way the plugin does and reports "reinstall: <command>" when a module is missing.
  - `push` (§3.9).

## 13. Small items

- `doctor` shows the shipped defaults' access rows (full access for verifier and ui-reviewer, advisory access for the
  Claude roles) as info (`i`), and as warnings only when the profile departs from the defaults.
- The TUI's Status tab does not render a profile count before the first profiles read ("…" until then).
- The skill's references to `wait`, "same message", and a verifier in the background are rewritten for §3 and §7; the
  verifier runs in the foreground as the gate owner.
- `README.md`, `MIGRATION.md` (a 1.0 → 1.1 section: `wait` is gone, `peek` and `result` replace it) and the changelog.

## 14. MCP tools (1.1)

  2. The real run: in a fresh Desktop session, merge `sanitell/platform` MR !54 and run auth plan 5 MR B (kit
