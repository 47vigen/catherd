# catherd 2.0: the run drives itself

Date: 2026-10-12. Status: owner-approved through a four-round design review (decisions Q1–Q29, all settled).
Binding where it differs from the earlier specs; they stay binding elsewhere. Replaces the 1.6 draft of the same
day, whose items are folded in below.

## Intent

A run starts, works through every milestone, and ends in a merge request without the owner watching it, overnight
included. Quality never drops below the 1.5 gate. Speed and quota cost come after that, in that order.

Today the run loop lives in the conductor: a Claude or Codex session that follows a 435-line skill and drives about
40 MCP tools by hand. That one choice causes most of what real runs reported. When the session is compacted or
closed, the loop stops. The skill, the tool descriptions and the briefs share one context. The protocol is prose,
so it bends. Every step waits on a model. 2.0 moves the loop into catherd.

catherd is the main line again. t3herd (`47vigen/t3herd`) is frozen as a T3 Code experiment. Its proven fixes from
the shop and demo12 runs are ported here (the 1.6 items), and t3herd supplies behavior, not structure.

## Decisions

### The run loop

1. **A detached daemon per run.** `run_start` launches it. It survives the session that started it closing or being
   compacted. It keeps a heartbeat file, and any catherd call (`status`, the TUI, the session's tools) revives a dead
   one. There is no launchd and no system service.
2. **An event-sourced state machine.** The transitions are a pure domain function,
   `next(state, event) → actions[]`. Every event is appended to the run's `events.jsonl`, and the state is rebuilt by
   replay, so a crash or a reboot resumes exactly where the run was. The machine is tested by feeding it events and
   reading its actions, with no live model.
3. **Judgment is a role.** The loop calls a model only to plan, triage findings, answer a worker's question, or
   decide an unexpected case. Each call is a short headless `judge` dispatch, routed by the profile like every other
   role (Opus by default), with only the context it needs. Every judge decision is an event and appears in the MR's
   audit section.
4. **The session is a client.** It starts a run, receives reports, and answers questions. The tools it sees are
   `run_start`, `status`, `answer`, `cancel`, `result` and `profile`. The rest (`dispatch`, `land`, `climb`,
   `set_next`, `lane_set`, `owns_add`, `park` and the others) become internal to the daemon. Roles keep their own
   tools (`read_run_file`, `gate_check`, …) as today.

### Unattended by design

5. **A question parks one unit.** When a role answers `needs_user`, only that lane or milestone parks and the rest
   of the run continues. A phone notification goes out through `notify.url`, a generic ntfy-compatible endpoint
   (default ntfy.sh with a random topic). It carries only the run name, the unit and the answer command, never code
   or secrets.
6. **Quota never ends a night.** A limit fails over to any backend the user has configured, not only those the
   profile uses. It never steps down, and Claude rungs go last. A limit holds for 30 minutes, or less once a role on
   that quota finishes cleanly.
7. **Fix rounds follow convergence.** Rounds continue while the findings shrink, up to a soft cap of
   max(3, 2 + ⌈lanes/3⌉). Past the cap the milestone lands with every remaining finding listed under Known issues in
   the MR. Only a BLOCKER stops the run. This replaces "no third review round".
8. **Every blocked reply names its reason:** `needs_user | too_hard | provider_error | no_access | check_broken |
   out_of_scope`. The machine maps each reason to a transition: climb, retry then fail over, park, or wait. A stop
   with no reason is classified by Jev, and with Jev off it is handled as in 1.5.

### Catalog and routing

9. **Slopalytics is the only source.** catherd reads `https://slopalyticsproxy.vercel.app`, as t3herd does. Every
   benchmark source sync is deleted, with the Artificial Analysis key, arena, epoch, vectara, openrouter, litellm,
   models.dev, `scores.json`, `sources.json`, calibration and provenance.
10. **Only indexed pairs exist.** A model#effort without an intelligence index in Slopalytics does not appear in
    the listing, the catalog, the TUI or `init`. There is no hand override and no `treatLike`.
11. **Single-scale routing.** Bars are intelligence percentiles, one per difficulty, and a role may set its own.
    The six dimensions are deleted. A lane's `Kind:` shapes its brief, not its ranking. Jev's yes/no answers set a
    floor at logic and a cap at build. A missing price counts as unpriced: it goes last in budget mode and does not
    matter in subscription mode. A missing speed leaves the pair out of the speed ladder.
12. **A pair that loses its index.** `profile set` and `profile validate` reject it and name the pair. At run time
    the ladder skips it and `doctor` warns. A role with no usable rung stops the run at start, never midway.
13. **Hand-written facts stay in the repo.** `catalog/models.json` keeps capabilities, billing mode, plan weight and
    the backend-to-model mapping. Efforts and context come from the proxy.

### Surface

14. **Backends:** Codex, opencode, Claude Code (native and headless) and Cursor. Cursor's models match Slopalytics
    by name, and unmatched ones (its own Composer) do not appear. Cursor is verified by the owner's team; 2.0 moves it
    to the new core. Grok and Antigravity (`agy`) are removed, and git keeps them.
15. **The TUI stays.** With the daemon it is the live view of a run.
16. **The skill shrinks** to starting, watching and answering a run.

### Ported from t3herd (the 1.6 items)

17. **Prompts:** each headless role gets its role text, its team and its done-when rules in its brief. The
    reviewer, fixer, worker and verifier get the rules the 1.6 plan 28 lists. New reply lines: `HEAD:`, `EXTRA:` and
    `REJECTED:`.
18. **Gate evidence:** a verdict must name the commit it lands. catherd runs the milestone check itself. Failures
    the base already has do not block, and a failure with new lines gets one rerun. A gitleaks scan runs, and heavy
    slots wait while the machine is overloaded.
19. **Recovery:** a lane check that fails only in a sibling's files counts as done. An answer re-runs the stopped
    unit. A finding survives only when a fix ran between reviews.
20. **Knowledge and digest:** standing rules are tagged per role and reviewed after each run. A research lane's
    answer reaches the lanes that wait on it. Known issues are quoted word for word. Plan lint runs as preflight
    warnings.
21. **A milestone per branch:** a worktree from `origin/<base>`, base integration, "landed" meaning origin's base
    contains the branch, and parallel milestones. A run without `base` behaves as 1.5. Pushes and MRs still need the
    user's authorization. In a squash-merging repo, dependants are unblocked by hand.

### The plan is the input

22. **A run starts from a reviewed, code-level plan.** The evidence (catherd's payment and auth runs against
    t3herd's shop run, 2026-10-21) puts most of catherd's output quality in the plan written before the run, not in
    the orchestrator. The ledger plan was 232 KB, with real signatures, a "what already exists" list, a separate
    contracts file owning every name, and every decision approved by the owner. Workers implemented a reviewed
    design. In the t3herd run, workers designed the code from short prose lanes.
    - `run_start` takes `plan: <path>[, <path>…]`. Every lane maps to plan tasks and is told to implement them as
      written, with a `DESIGN:` reply on any conflict.
    - Without a plan, the architect first writes one to that depth: exact signatures and data shapes, an inventory
      of existing code with paths, a contracts section for shared names, decisions with rejected alternatives, and a
      test per task. The run waits for the owner's approval of that plan before the first lane. This is the run's
      one planned stop.
    - Preflight refuses a lane that has no plan task behind it, or a plan task with neither a signature nor a test.
    - Coding workers never run below medium effort, and routing does not put cost ahead of that floor.

## Measurement

The run scorecard is the gate for 2.0. It is not the catalog benchmarks, which are deleted.

- **Four fixed tasks:** a small raqam task, a catherd milestone, a past Sanitell task replayed at its original
  commit on a throwaway branch, and an injected-failure task (a fake quota limit plus a broken test).
- **Recorded per task:** whether it finished with no intervention, the number of interventions, review rounds,
  wall-clock time, quota used, and whether the MR passed on the first try. Built on `outcomes.jsonl` and
  `summary.ts`.
- **Pass bar:** all four tasks finish with zero interventions; the injected-failure task recovers by itself; and
  wall-clock time is no worse than 1.5. Quota is reported, not gated.
- **Baseline:** taken on 1.5.0 before any 2.0 change, then after each plan.
