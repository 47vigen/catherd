# catherd 1.3: Cursor, Grok Build and Antigravity backends

Date: 2026-09-29. Status: **draft for the owner's review.** Implementation is on hold until the owner says go. §9
lists the decisions that are the owner's; each carries a recommendation, and the plans follow the recommendation
until the owner rules otherwise.

Builds on the 1.2 spec (`2026-09-28-catherd-1.2-design.md`), the 1.1 spec and the 1.0 spec. They stay binding where
this one is silent. Authority order for 1.3 work: this spec → 1.2 → 1.1 → 1.0 → the plan → rulings.

This spec **supersedes spec 1.0's D5 phasing** ("1.1 = Cursor. 1.2 = Grok") and its §6.4 and §6.5. 1.1 and 1.2 shipped
without either backend, and the research below refutes parts of both sections.

Evidence: `docs/research/2026-09-29-cursor-grok-antigravity.md`, cited as "research §n". It ran the real binaries
(Cursor 2026.09.28-64d2043, grok 1.0.44, agy 1.2.13) on the owner's Mac and read the docs of those versions. None of
the three was signed in, so every behaviour of a real model turn is still unverified. Research §8 lists those checks,
and each is a live-verification step in the plans.

## 1. Why

- **Cursor** serves models catherd already routes (GPT-6, Claude, Gemini, Grok) from another billing pool, plus
  Composer. It is a second path to the same rungs when a vendor's own plan runs out.
- **Grok Build** is xAI's own agent, on SuperGrok / X Premium+ or an API key. Grok 4.5–4.7 have measured Arena and
  Epoch values in 1.2's sources (research §5).
- **Antigravity CLI** (`agy`) is Google's agent CLI. It replaced Gemini CLI for consumer tiers on 2026-06-18, and it is
  the only local, headless path to Gemini 3.x on a Google plan (research §4.1).

Success: each backend passes the adapter contract suite and its simulator in CI. The owner's live kit passes on a
signed-in machine. A profile can put any role on any of the three, and routing scores its rungs from public sources,
with no hand scores.

## 2. Scope

In 1.3:

1. The generic groundwork every new backend needs (§3).
2. The Cursor adapter (§4), the Grok adapter (§5), and the Antigravity adapter (§6).
3. The catalog families that make 1.2's sync score these vendors' models (§7).
4. `doctor`, `init`, TUI, profile and docs surfaces (§8).

Out of 1.3:
- A web or cloud agent API (Cursor background agents, the Gemini API Antigravity agent), and Gemini CLI.
- The superagent-ai community `grok-cli`.
- Cursor's `agent worker` / `persist` modes.

**Release (replaces D5):** plan 15 (groundwork and Cursor), plan 16 (Grok) and plan 17 (Antigravity) each open one PR.
Only the last to merge carries the `minor` changeset, so the three ship together as **1.3.0**, held for the owner's
live acceptance (§10). See §9 Q1 for the alternative.

## 3. Groundwork common to the three

### 3.1 The adapter contract after 1.2

A backend is still one folder `src/adapters/<id>/` (`events.ts`, `models.ts`, `index.ts`, plus `home.ts` where it has an
isolated home), registered in `src/adapters/all.ts`, and implementing `BackendAdapter` (`src/adapters/backend.ts`).
Each new adapter provides, beyond 1.0 §3.2:

- `finalize()` returns the status, reply, tokens, cost and thread. The **push notice** (1.1 §3) and **failover on
  `limit`** (1.1 §3.4) are generic: the notifier acts on the record, and an adapter only has to classify `limit`
  correctly and never as `failed`.
- The reply the finalizer returns is what the **reply contract** (1.1 §6) is parsed from: the `STATUS:` last line.
  Each adapter's reply is the worker's final assistant message only. Concatenated multi-message text breaks the
  STATUS line (Cursor's `result.result` does this; research §2.3).
- `resume.sameAccessOnly` is honoured (§3.2).
- `accessShell()` runs doctor's five probes where the CLI offers a sandbox runner, else returns why not (§3.4).
- `isolationNote` names what the native mode loads from the user's other tools (research §7.2).
- `failoverFor` is not implemented; failover stand-ins come from the profile and 1.1 §11's defaults (§7.3).

### 3.2 Admission enforces `sameAccessOnly`

Declared in 1.0 and never checked (research §6.3 B5). Admission refuses to resume a thread whose last record ran under
another access, with `E_ADMIT_THREAD` and the fix "dispatch a fresh thread (omit `thread`)". The check runs before
anything is written. Grok needs it; Antigravity declares it until a live check shows otherwise.

### 3.3 Other generic changes

- `ADAPTER_IDS` gains `antigravity`. Every enum derived from it (`RUNG_BACKENDS`, `MODEL_KEYS`, `BILLING_KEYS`,
  `DEFAULT_BILLING`, the harness keys) follows. `cursor` and `grok` are already there.
- `capture-fixtures` passes stdin only when the adapter's `plan()` sets `stdinPath` (`src/services/capture.ts` passes
  it to every CLI today).
- **Probes never open a browser or block on login.** An unsigned `agy -p` opens the browser and waits 60 s (research
  §4.8). Each adapter's `probe()` uses a call that fails fast when logged out:
  - Cursor: `models` (exit 1, "Authentication required").
  - Grok: `grok models` ("You are not authenticated.").
  - agy: `agy models` (exit 1, "Please sign in").

  Admission refuses a rung whose backend probes as logged out (`E_BACKEND_NOT_LOGGED_IN`, with the login command),
  so a dispatch never reaches the browser path.
- **An installed binary that cannot run** is a probe problem, not "not installed". The owner's grok is a Linux ELF on
  macOS (research §3.1). A spawn that fails with `ENOEXEC` / "exec format error" reports "installed but cannot run on
  this OS", with the reinstall command.
- Each adapter sets its CLI's auto-update off for workers:
  - Cursor: hidden `--disable-auto-update`.
  - Grok: `GROK_DISABLE_AUTOUPDATER=1` and `--no-auto-update`.
  - agy: `AGY_CLI_DISABLE_AUTO_UPDATE=true`.

  A mid-run update must not swap the binary under a lane.
- Hidden CLI flags (Cursor's `--disable-auto-update`, grok's `--trust`, `--no-auto-update` and `--no-memory`) are used
  only where no documented one exists. Each is pinned by a simulator case and a live case, so a vendor removing one
  fails CI's live kit loudly, not silently.

### 3.4 Access probes where no sandbox runner exists

1.1 §5 runs five probes (lock dir, temp, loopback, outbound HTTPS, Docker) "with the exact flags workers get".
- Codex has `codex sandbox`.
- Cursor has the hidden `agent sandbox run` (research §2.6), which runs a command in its sandbox with no model turn.
- Grok and agy have no such runner.

For them, `accessShell` returns "no way to run a shell in <backend>'s sandbox without a model turn", and doctor's
`access:<backend>` row is `skip` / `not tested`. The live kit's step for that backend runs the five probes as one
cheap worker turn. See §9 Q5 for a doctor that spends one turn.

## 4. Cursor (`cursor`)

### 4.1 Binary, version, auth

- Probe `cursor-agent`. Accept `agent` only when `--version` prints Cursor's `YYYY.MM.DD-<hash>`: on the owner's
  machine `agent` is grok's (research §2.1).
- `minVersion` is `2026.09.28`, the version whose help and bundle were read. The owner's 2026.06.04 lacks `--add-dir`
  and `--new-session-id`; the fix is `cursor-agent update`.
- Logged in means `models` answered. `status` reports token presence and said "authenticated" on a machine where
  every call failed (research §2.9). `login` is "API key" when `CURSOR_API_KEY` is set, else "Cursor login".
- Billing key `cursor`: `metered` by default, as today. Cursor bills non-Cursor models at API rates once a plan's
  included usage is spent (research §2.4). See §9 Q4.

### 4.2 Argv, prompt, thread

```
cursor-agent -p --output-format stream-json --trust --workspace <repo> --model <slug>
             --disable-auto-update <access flags> [--resume <thread>]
stdin: the brief (resume: the fix brief); no positional prompt
env:   CURSOR_* from the user; NO_OPEN_BROWSER=1
```

- The thread is `system/init.session_id`. A resume passes the record's thread and the same `repo`. Cursor looks an
  explicit chat id up by the cwd, and **silently starts an empty chat** for an id it does not find (research §2.5).
  catherd always resumes with the recorded repo, and the live kit pins the behaviour.
- `resume.sameAccessOnly: false`: each run applies its own flags (research §2.5).

### 4.3 Access and writable roots

| catherd access | Cursor flags | Enforcement |
|---|---|---|
| `read-only` | `--mode ask --sandbox enabled` (no `--force`; headless rejects every approval) | advisory (tool-level). Isolated runs add `sandbox.json` `type: workspace_readonly`, still reported advisory until the live kit shows the CLI honours it |
| `workspace-write` | `--sandbox enabled` (no `--force`: `--force` turns the sandbox **off**, research §2.6) | enforced (Seatbelt / Landlock) |
| `full` | `--force --sandbox disabled --approve-mcps` | — |

- **Writable roots and network** (1.1 §5): Cursor reads them only from `sandbox.json`: `additionalReadwritePaths` =
  `writableRoots()`, and `networkPolicy.default: "allow"`, or the defaults when the role has `network: false`.
  - The repo's `.cursor/sandbox.json` belongs to the repo, and `~/.cursor/sandbox.json` to the user; catherd writes
    neither.
  - So **native** `workspace-write` gets Cursor's defaults (workspace, tmp, package registries), and doctor's access
    row says which probes fail.
  - **Isolated** gets catherd's own `sandbox.json` in its Cursor home.
  - See §9 Q3.
- Whether plain edits apply without `--force` is unverified (the docs disagree). If the live kit shows they don't,
  `workspace-write` becomes `--force --sandbox enabled` with a `permissions.deny` list, and enforcement drops to
  advisory. That is Ruling C-edit in plan 15.

### 4.4 Isolation

`HOME=<data>/cursor-home` plus `CURSOR_API_KEY`, with `prepare` refusing without the key (1.0 plan 8 A9, confirmed).
Nothing else isolates: `CURSOR_CONFIG_DIR` does not stop the hard-coded `~/.claude`, `~/.codex`, `~/.grok` and
`~/.agents` reads (research §2.8). `isolationNote`: "native Cursor loads your Claude Code hooks, skills, plugins and
permission rules, and your Cursor User Rules; isolation cannot remove the User Rules".

### 4.5 Stream, status, limits

- `parse`: `system/init` gives the thread. An `assistant` event gives activity and a reply candidate. `tool_call`
  gives item open/close and activity. `result` is `final`. Unknown types (`thinking`, `retry`, `connection`, …) are
  ignored; a `retry` event sets `retrying`.
- Reply: the last `assistant` message's text.
- Tokens: `input = inputTokens + cacheReadTokens + cacheWriteTokens`, `cached = cacheReadTokens`,
  `output = outputTokens` (inputTokens is uncached only; research §2.3). `costUsd: null`.
- Status:
  - `ok` when a `result` with `is_error: false` arrived, whatever the exit (the grace kill).
  - `cli-too-old` on `unknown option` or `OUTDATED_CLIENT`.
  - `limit` on `usage limit|rate limit|too many requests|ActionRequiredError|USAGE_LIMIT|RATE_LIMIT`, unless the text
    says `administrator has disabled`, which is `failed`.
  - `failed` on "Authentication required" (with the login fix), and on no `result`.
- `graceAfterFinalMs: 30_000`. Cursor waits for background shells with no limit after its last turn.

### 4.6 Discovery and catalog

`listModels()` parses `models` (`<id> - <Name>` lines, markers stripped). It folds effort-suffixed slugs into one model
with efforts (1.0 plan 8 A7). Bracket variant strings are not listed and are not built. The families gain `on.cursor`
entries (§7), with ids confirmed from the owner's listing in the live kit. `auto` has no family and is used only by the
live kit.

### 4.7 Doctor, validation, tests

- Doctor:
  - `backend:cursor` (installed, version, logged in, discovery).
  - `access:cursor` through `agent sandbox run` (hidden; a string when it is missing).
  - `isolation:cursor` (the note above).
  - `name:agent`: `agent` on PATH is not Cursor, as information.
- Profile validation: a Cursor rung on a model the last listing lacks is the existing "last listing does not offer X"
  warning.
- Contract suite cases:
  - ok with lingering exit;
  - no result;
  - auth required;
  - limit vs team policy;
  - unknown option;
  - resume.
- Simulator: `test/sim/cursor-agent`.
- `capture-fixtures` cases: read/write/shell, resume, ask-mode rejection, sandbox outside-write.
- Live tests: `test/live/cursor.live.test.ts` (`CATHERD_LIVE=1`, rung `cursor:auto#default`).

## 5. Grok Build (`grok`)

### 5.1 Binary, version, auth

- Probe `grok` (`grok --version`). `minVersion` is `1.0.44`.
- Logged in means `grok models`' first line: "You are logged in with …" or "You are using XAI_API_KEY." give `login`
  "Grok login" or "API key".
- **Never copy or link `~/.grok/auth.json`.** Refresh tokens rotate, and a permanent refresh failure deletes the file
  (research §3.9).
- Billing key `grok`: `subscription` under a Grok login, `metered` under an API key (the probe's `billing`).

### 5.2 Argv, prompt, thread

```
grok --prompt-file <brief> --output-format streaming-json --cwd <repo> -m <model> [--effort <e>]
     --always-approve --trust --no-auto-update --no-memory <access flags>
     new:    -s <uuid>
     resume: -r <thread>          (no --sandbox, no --tools change: the session keeps its profile)
stdin: none (stdinPath null)
env:   GROK_DISABLE_AUTOUPDATER=1
```

- The thread is the `-s` UUID, confirmed by `end.sessionId`. `resume.sameAccessOnly: true` (§3.2).
- `#default` passes no `--effort`. The efforts come from the family's `on.grok.efforts` (grok lists none; research
  §3.4). An effort grok rejects fails the run with its message.

### 5.3 Access and writable roots

| catherd access | grok flags | Enforcement |
|---|---|---|
| `read-only` | `--sandbox read-only`; **where it cannot apply** (§ below): `--sandbox workspace --tools read_file,grep,list_dir,web_search,web_fetch` | enforced (kernel) / advisory (tool allowlist) |
| `workspace-write` | `--sandbox catherd-ws` (a custom profile, below) | enforced for files; network not controlled on macOS |
| `full` | `--sandbox off` | — |

- **The socket refusal.** Grok refuses `read-only`, `strict` and any profile extending them on a Mac whose
  `/var/run/docker.sock` is a symlink (Docker Desktop, OrbStack, Colima; research §3.6). `prepare` detects this case
  (macOS and a symlinked socket), picks the tool-allowlist form, and doctor shows read-only as advisory there.
- **`catherd-ws`** is `[profiles.catherd-ws] extends = "workspace"`, `read_write = writableRoots()`, and
  `restrict_network = true` when the role has `network: false` (Linux only; macOS has no child-network control). Grok
  reads custom profiles only from `$GROK_HOME/sandbox.toml` or the repo's `.grok/sandbox.toml`.
  - **Isolated:** catherd writes it in its own grok home.
  - **Native:** see §9 Q3. The recommendation is that catherd adds only `[profiles.catherd-*]` tables to the user's
    `~/.grok/sandbox.toml`, marked as catherd's, the way it installs `catherd-*` agents into opencode's config.
  - Without that, native `workspace-write` uses the built-in `workspace`, and doctor reports the lock-dir and cache
    probes as failing.
- Trust: `--trust` is passed on every run. A sandboxed run cannot save the grant (research §3.7); the trust applies
  for the session either way.

### 5.4 Isolation

`HOME=<data>/grok-home` (so `.grok`, `.claude` and `.cursor` there are catherd's), `GROK_HOME=$HOME/.grok`,
`XAI_API_KEY` required (`prepare` refuses without it), the ten `GROK_{CLAUDE,CURSOR}_*_ENABLED=0`, and `GROK_MEMORY=0`.
`GROK_HOME` alone does not isolate (research §3.8). `isolationNote`: "native grok loads your Claude Code plugins,
agents, skills, hooks and permission rules, and your Cursor rules and MCP".

### 5.5 Stream, status, limits

- `parse`: `tool_call` / `tool_call_update` give items and activity, `text` gives a reply candidate, `usage` gives
  `requestInput`, and `end` or a terminal `error` is `final`.
- Reply: the `text` after the last tool call.
- Tokens: `end.usage` (`input = input_tokens + cache_read + cache_creation`, `cached = cache_read`,
  `output = output_tokens`), else the sum of `usage` events. `costUsd = end.total_cost_usd ?? null`. The cost is absent
  under a subscription login, and it is never read as 0.
- Status:
  - `ok` when `end.stopReason` is `end_turn`.
  - `failed` with "stopped: <reason>" on `max_tokens`, `max_turn_requests`, `refusal` or `cancelled`.
  - `cli-too-old` on exit 2 or `unexpected argument`.
  - `limit` on an `error` matching the rate-limit texts (research §3.10), except "requires a Grok subscription".
  - `failed` with the login fix on "Not signed in".
  - `failed` on no `end` otherwise.
- `graceAfterFinalMs: 30_000`. A one-shot run may drain uploads for ~150 s after `end` (research §3.3); the grace
  kill cuts it short, and the record is already complete.

### 5.6 Discovery, catalog, doctor, tests

- `listModels()` parses `grok models`. Families Grok 4.7, 4.6 and 4.5 gain `on.grok` (§7).
- Doctor:
  - `backend:grok`, including the ELF-on-macOS case.
  - `access:grok` as `skip` (§3.4).
  - `isolation:grok`.
  - `sandbox:grok`: whether `read-only` applies here, from a no-turn check (the refusal comes before auth, research
    §3.6).
- Contract suite:
  - end_turn;
  - error without end;
  - not signed in;
  - exit 2;
  - limit texts;
  - max turns;
  - resume same access and refused access change.
- Simulator: `test/sim/grok`.
- Capture cases, and live tests `test/live/grok.live.test.ts` (rung: the listing's default model at `#low`).

## 6. Antigravity (`antigravity`, binary `agy`)

### 6.1 Binary, version, auth

- Probe `agy` on PATH (the cask's link or the install script's `~/.local/bin/agy`; catherd does not look outside PATH). `minVersion` is
  `1.2.13`. Releases are near-daily, so the floor moves only when a plan needs a newer flag.
- Logged in means `agy models` answered. It fails fast when logged out (exit 1, "Please sign in"). **`agy -p` must
  never run while logged out**, because it opens a browser (research §4.8).
- Auth:
  - A Google login (Keychain) bills plan quota: weekly on Free/Plus, 5-hour plus weekly on Pro/Ultra.
  - `GEMINI_API_KEY` works only with `modelProvider: "gemini"` in the settings file, and bills the Gemini API project.
- Billing key `antigravity`: `subscription` under a login, `metered` under the key.

### 6.2 Argv, prompt, thread

```
agy -p "<fixed line: read and follow the brief in <briefPath>; your final message is your reply>"
    --output-format stream-json --model <slug> [--effort low|medium|high|max]
    --disable-slash-commands <access flags> [--conversation <thread>]
cwd: the repo; stdin: none
env: AGY_CLI_DISABLE_AUTO_UPDATE=true
```

- The brief stays in its file, and argv carries only its path (1.0 §4.4's rule is about the brief's text). The
  alternative is `--input-format stream-json` with a one-line NDJSON file on stdin; plan 17's first task picks one live
  (research §7.3).
- The thread is `result.conversation_id` (also on `step_update`). Resume with `--conversation <id>` from the same
  repo; conversations are scoped by cwd. `resume.sameAccessOnly: true` until the live kit shows a resume takes the new
  run's permissions.
- No `--print-timeout`: catherd's own wall timeout governs. An expired print timeout would exit 0 with partial output
  (research §4.4).

### 6.3 Access and writable roots

| catherd access | agy | Enforcement |
|---|---|---|
| `read-only` | **isolated only**: deny `write_file(*)`, `command(*)` in catherd's agy home `settings.json`. Native: see §9 Q2 | advisory (CLI permission rules) |
| `workspace-write` | `--sandbox --dangerously-skip-permissions` (file tools are auto-allowed in the workspace; shell runs under Seatbelt / nsjail) | enforced for shell; advisory for file tools |
| `full` | `--dangerously-skip-permissions` | — |

- Writable roots and network come only from permission rules: `write_file(<root>)` allow rules are "mounted
  read-write" in the sandbox, and `read_url(...)` rules open domains. Those rules live in
  `~/.gemini/antigravity-cli/settings.json`, which the **desktop app shares** (research §4.7).
  - catherd writes them only in its isolated agy home.
  - Native `workspace-write` gets agy's defaults ("workspace, temp and build caches"), with no network unless the
    user's own rules grant it. Doctor says so.
- Whether `--sandbox` still confines shell under `--dangerously-skip-permissions` is unverified. Plan 17 rules it
  "yes" pending the live kit; if it is "no", `workspace-write` uses `toolPermission: "proceed-in-sandbox"` in the
  isolated settings, and native `workspace-write` becomes advisory.

### 6.4 Isolation

`HOME=<data>/agy-home` (a moved `HOME` relocates every agy file, research §4.7) plus `GEMINI_API_KEY`, with catherd's
`settings.json` there (`modelProvider: "gemini"`, the access rules). `prepare` refuses without the key. The native mode
reads the user's `~/.gemini` and `.agents`. `isolationNote`: "native Antigravity shares its settings and permission
rules with the Antigravity desktop app".

### 6.5 Stream, status, limits

- `parse` (events keyed by `event`):
  - `init`: nothing yet.
  - `step_update`: the thread; activity from `tool_name` / `tool_info`; items from `state` ACTIVE/DONE on `tool`
    steps; `requestInput` from `usage`.
  - `result`: `final`.
- Reply: `result.response`. The live kit confirms that it is the final message only.
- Tokens: `input = input_tokens` (plus `cache_read_tokens` if the live capture shows `input_tokens` is uncached),
  `cached = cache_read_tokens`, `output = output_tokens + thinking_tokens`. `costUsd: null`.
- Status:
  - `ok` only when `result.status` is `SUCCESS`.
  - `cancelled` on `CANCELED` / `INTERRUPTED`.
  - `cli-too-old` on exit 2 or `flags provided but not defined`.
  - `limit` when the `AGY_ERROR:` stderr line's canonical status is `RESOURCE_EXHAUSTED` or its text names a quota,
    spend cap or credits.
  - `failed` with the login fix on "authentication failed".
  - Otherwise `failed`, with the `AGY_ERROR` message.
- `graceAfterFinalMs: 30_000`. agy leaves daemon background tasks (dev servers) running (research §4.4); the grace
  kill of the process group stops them.

### 6.6 Discovery, catalog, doctor, tests

- `listModels()` parses `agy models` text. Its format is unverified: `--output-format` is rejected by 1.2.13 though
  the changelog lists it. Slugs can embed the effort (`gemini-3.8-flash-high`); the same fold as Cursor's applies.
- Families Gemini 3.8, 3.7 and 3.6 Flash and Gemini 3.1 Pro (§7) gain `on.antigravity`. Claude Sonnet/Opus 4.6 and
  GPT-OSS on Antigravity get no family: they are older than the shipped families, and `catalog list` shows them as
  unmapped.
- Doctor:
  - `backend:antigravity`.
  - `access:antigravity` as `skip` (§3.4).
  - `isolation:antigravity`.
  - `quota:antigravity`, from `agy -p "/usage" --output-format json`, which spends no turn (research §4.4), only when
    logged in.
- Contract suite:
  - SUCCESS;
  - ERROR with `AGY_ERROR`;
  - auth timeout;
  - exit 2;
  - the partial output of a print timeout;
  - resume.
- Simulator: `test/sim/agy`.
- Capture cases, and live tests `test/live/antigravity.live.test.ts` (rung: `antigravity:gemini-3.8-flash#low`,
  or the cheapest listed).

ids and efforts:

| Family | on | Notes |
|---|---|---|

### 7.2 Stand-ins

stand-ins, shown as "stand-in to confirm". That is a warning, never an error.

### 7.3 Failover

The same model on two backends bills to two pools: Grok 4.7 through `grok` or `cursor`, and Gemini through
`antigravity` or `cursor`. These pairs are a same-model stand-in table that `standInFor` falls back to when the profile names none (not `DEFAULT_FAILOVER` entries, which would make the default profile warn about backends the user does not run). The new backends' rungs are
never default stand-ins for the shipped Codex/Claude/opencode rungs: that would move a user's spend to a vendor they
did not choose. Profiles can add them.

## 8. Surfaces

- `init`: detects each CLI and asks nothing new. A new backend is off in the default profile until the user puts a
  rung on it (research: none was usable logged-out). The API-key prompts are not added; the env vars are read.
- The profile's harness toggles gain `antigravity`. The TUI's harness row shows each backend's isolation note, and
  that isolation needs the API key.
- `profile validate`:
  - Isolated with no API key is an error, with the export line (the existing `E_BACKEND_NOT_LOGGED_IN` shape).
  - Read-only on native Antigravity follows §9 Q2.
  - A Grok `workspace-write` role on native with no `catherd-ws` profile is a warning.
- `README.md` backends table, `docs/dev/live-verification.md` §11 (Cursor), §12 (Grok), §13 (Antigravity) from research
  §8, `MIGRATION.md` (nothing to migrate; a note), and the changelog.

## 9. Open questions for the owner

Each has a recommendation, which the plans follow until the owner rules otherwise.

**Q1. One release or three?**
- **Recommendation:** one 1.3.0 with all three, held for the live kit.
- The tradeoff: the three plans share the groundwork (§3) and the catalog work (§7), so one release means one
  acceptance run. But a backend whose live check fails holds the others back. The alternative, 1.3.0 Cursor, 1.4.0
  Grok, 1.5.0 Antigravity (the old D5 shape), costs three acceptance runs and three release PRs.

**Q2. Read-only on native Antigravity.** agy has no read-only flag (research §4.7).
- **Recommendation:** refuse read-only roles on native agy (`profile validate` error: "isolate antigravity, or put
  this role on another backend"). Isolated agy gets deny rules.
- The tradeoff: the verifier, reviewer and ui-reviewer defaults (read-only or full) cannot use a native Gemini rung.
  The alternative is to allow it as advisory and rely on catherd's out-of-lane write detection after the run. That is
  cheaper to use, but a reviewer could still run shell commands that write outside the repo.

**Q3. May catherd write into the user's vendor config for native runs?**
- Grok's `catherd-ws` profile needs `~/.grok/sandbox.toml`. Cursor's writable roots need `~/.cursor/sandbox.json`,
  which is global and would affect the user's own interactive Cursor. agy's roots need the shared
  `~/.gemini/antigravity-cli/settings.json`.
- **Recommendation:**
  - Grok: yes, only `[profiles.catherd-*]` tables, which change nothing unless selected. That is the opencode-agents
    precedent.
  - Cursor and agy: no. Native `workspace-write` gets the vendor's defaults, doctor reports which probes fail, and
    isolation gets the full 1.1 §5 intent.
- The tradeoff: on native Cursor/agy a worker may be unable to take the heavy lock or warm the Go/pnpm caches, which
  is exactly 1.1's "workers cannot run their checks" problem.

**Q4. Billing modes.**
- **Recommendation:**
  - Cursor: `metered` (its non-Cursor models bill at API rates after included usage, and Composer and Grok bill from
    its own pool).
  - Grok and Antigravity: `subscription` under a login, `metered` under an API key, from the probe.
- The tradeoff: a `subscription` rung ranks cheap in routing. If the owner's Cursor plan has large included usage,
  `subscription` would route more work there.

**Q5. A doctor access probe that spends a model turn** for Grok and agy (§3.4).
- **Recommendation:** no. Doctor stays free and offline-safe, and the live kit covers it.
- The tradeoff: `doctor` cannot tell a user that a Grok or agy worker will fail its checks until a real lane does.

**Q6. Isolation keys.** Isolation of Cursor, Grok and agy each requires an API key (a login cannot be moved safely:
research §3.9, §2.8).
- **Recommendation:** accept that. Isolation is opt-in per backend, and the TUI says so.
- The tradeoff: a user with only a subscription login cannot isolate that backend, so native harness is the only
  mode for them.

**Q7. Antigravity plan terms.** Whether Google's Antigravity terms allow an orchestrator to drive `agy` on a consumer
plan could not be read (403 here).
- **Recommendation:** ship the adapter. The README says the API-key route is the one intended for automation, and
  the owner checks the terms before relying on a plan login.
- The tradeoff: account risk on the plan route, which the owner can assess and catherd cannot.

**Q8. Hidden flags.**
- **Recommendation:** use Cursor's hidden `--disable-auto-update` and `agent sandbox run`, and grok's `--trust`,
  `--no-auto-update` and `--no-memory`, each pinned by a live case (§3.3).
- The tradeoff: a vendor can remove a hidden flag without notice. The live kit catches it, but only when run.

**Q9. The owner's machine.** It needs:
- `grok login` and a reinstall (the installed grok is a Linux build);
- `cursor-agent update` and `cursor-agent login`;
- `agy` installed and signed in once.

Then the live kit runs. The installers fight over `~/.local/bin/agent`; nothing in catherd depends on who wins.

## 10. Testing and acceptance

- Per backend: event and model parsers against fixtures, the contract suite, the simulator, and the admission,
  doctor and profile tests, all written to fail first. No test reaches the network or a real CLI.
- The fixtures are synthetic until the owner's `capture-fixtures` run replaces them (the 1.2 AA precedent). Every
  synthetic fixture names the doc or `[bin]` evidence it follows.
- CI green on the macOS and Linux matrix.
- **Owner acceptance (the release PR is held for it):** research §8's checks, as live-verification §11–§13. Then one
  `/catherd` run on a scratch repo with a lane on each new backend: routed, reviewed and verified, with push notices
  and STATUS lines.
